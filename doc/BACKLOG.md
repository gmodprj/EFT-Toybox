# 나중에 할 일

작업 중에 "이건 이번 범위가 아니다" 로 미룬 것만 적는다. 하기로 정한 것이지 후보 목록이 아니다.
끝내면 줄을 지우고 어디에 들어갔는지(커밋·문서) 한 줄 남긴다.

| 할 일 | 왜 미뤘나 | 손댈 자리 |
| --- | --- | --- |
| **야시경·실드 휠의 남은 인게임 점검 3건** — ① 휠을 띄운 채(N 누른 상태) 죽거나 레이드를 끝냈을 때 입력이 잠기지 않고 아무 것도 여닫히지 않는지 ② 왼손에 나침반을 들고 N 을 눌렀을 때 UI Fixes 가 나침반을 치운 뒤 야시경이 여닫히고 휠이 뜨지 않는지 ③ 제스처 휠(`B`)이 멀쩡히 도는지. **머지 시점에 이 셋은 확인되지 않았다** | 2026-10-31, 사용자가 건너뛰고 머지하기로 정했다. ①은 코드상 `ShouldApplySelection` 으로 막아 두고 시험 4개로 묶었으나 게임에서 본 적은 없다. ②는 설계 §6-2 의 공존 경로이고 COTI 쪽(§7-9)은 역컴파일로 확인했지만 UI Fixes 경로는 못 봤다. ③은 우리가 제스처 휠을 건드리지 않게 만들었다는 전제의 확인이다 | 설계 §7 의 7·8·10 항. 레이드에서 셋 다 한 번에 볼 수 있다. ①이 틀리면 치명적이다(시점이 잠긴 채 레이드가 끝난다) — 그 경우 [GogglesPatch.cs](../src/GogglesWheel/GogglesPatch.cs) 의 `finally` 와 `LookBlocker.Release()` 를 먼저 본다 |

| **제스처 명령 넷 — `SILENCE`·`KNIVES ONLY`·`SPREADOUT`·`GET BACK`** (메뉴 18개 중 처리하지 않는 마지막 넷. 지금은 `hideUnsupportedCommands` 를 켜면 숨고, 끄면 보이지만 포크는 아무것도 안 하고 바닐라 수신기가 받는다) | 2026-11-02 계획 3 은 교전 통제 손잡이가 이미 있는 셋(`FIRE`·`HOLD FIRE`·`TAKE COVER`)만 골랐다. 이 넷은 대응할 기존 AI 손잡이가 코드에 없다 — `SILENCE` 는 메뉴 목록에서 주석 처리돼 있고, `SPREADOUT` 은 팀원이 **말하기만**(트립와이어) 하며 명령으로는 처리되지 않고, `KNIVES ONLY`·`GET BACK` 은 클라이언트에 처리가 없다. 없는 AI 동작을 지어내지 않았다 | [`GestureCommandPolicy`](../src/SptTeamManager/shared/GestureCommandPolicy.cs) 의 `Translate`·`CommandGroupPhrases`(메뉴 목록의 유일한 출처 — 번역 없이 목록에만 넣으면 테스트가 걸린다, 번역 개수 3 고정), `AIBossPlayer.PhraseSaid`/`ApplyEngagementGesture`, `GestureMenuPatch`, `BotReceiverPhraseOverridePatch`(`ForkHandlesEngagementFor` 가 건너뛰는 조건). 처리하기 시작하면 바닐라 건너뛰기에 같은 조건이 걸리는지도 함께 본다 |
| **`HOLD FIRE`·`FIRE`·`TAKE COVER` 의 정밀화** — 인게임 관문(WORKLOG 19~21번)의 결과를 보고 정한다. 알려진 한계: `HOLD FIRE` 는 공격성 0 이라 방아쇠 잠금이 아닐 수 있고, `FIRE` 는 저장된 전술이 이미 소극적이면 변화가 없고, `TAKE COVER` 는 임의 엄폐물을 찾지 않고 "보스 곁으로 붙기" 근사이며 교전 중이 아닌 팀원에게는 조용하다(누락과 구별되지 않는다) | 계획 3 은 기존 손잡이를 재사용했고 없는 AI 동작을 지어내지 않았다. 확인 표시 UI 도 일부러 만들지 않았다 | `AIBossPlayer.ApplyEngagementGesture`(공격성 오버라이드, `SetCombatComeToBossCover(8f)`). |
| **편집기의 격자 배치** — 가방·리그 **칸**에 놓기, 스태시 안 가방으로의 이동, 같은 부모 안에서 칸 위치만 바꾸기. 지금은 슬롯(장비 칸)에만 입힐 수 있고 격자로는 스태시 루트로 **벗기기**만 된다. 사용자가 느끼는 것: **여분 탄창·의료품을 리그에 넣어 줄 수 없어** 팀원이 탄창 하나로 레이드에 간다. 칸 위치만 바꾼 편집은 저장되지 않고 개수로 알려 준다 | 요청 레코드(`GearEditRequest`)에 `Location` 이 없다. 좌표 없이 격자에 넣으면 서버가 자리를 지어내야 하고, 서버가 자리를 계산해 쓰는 코드를 아직 믿을 근거(인게임 관문 8번)가 없다 | [`ProfileGearEditPolicy.Validate`](../src/SptTeamManager/shared/ProfileGearEditPolicy.cs)(목적지 판정), `GearEditBatchPlanner`(`LayoutKey`: 칸 위치만 바뀐 건 제외), `StmGearEditService`(벗기기는 SPT `PlaceItemInContainer` 가 자리를 찾는다 — 같은 호출이 입히기 쪽 격자에도 쓸 수 있다). 관문 8번이 통과한 뒤에 한다 |
| **편집이 수량을 바꾸게 하기** — 부분 장전 탄창에 탄 채우기, 더미 쪼개기·합치기. 지금은 부분 장전 탄창을 **벗고 가득 찬 탄창을 끼우는** 것만 된다 | 편집은 아이템을 **옮기기만** 한다(`Upd.StackObjectsCount` 를 읽지도 쓰지도 않는다). 수량을 바꾸는 순간 "집합이 같다" 는 디스크 대조가 성립하지 않고, 복제가 사는 자리다 | `ProfileGearEditPolicy.CheckItemSetUnchanged`(id 집합 대조)가 먼저 수량을 아는 형태로 확장돼야 한다. 점유 검사가 `cartridges` 를 예외로 두지 않는 것도 같은 이유 |
