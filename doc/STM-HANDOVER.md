# SPT Team Manager — 인계 문서

작성 2026-11-02. 계획 1(기반)과 계획 2(레이드 투입)가 끝난 시점의 상태다.
**다음 사람이 계획 3·4 를 집어들 때 먼저 읽을 문서**이고, 세부 기록은 [WORKLOG](WORKLOG.md) 의
"2026-11-01 — STM 계획 2" 구간(맨 앞에 읽는 법 요약이 있다)과 설계 [specs/2026-10-31-spt-team-manager-design.md](specs/2026-10-31-spt-team-manager-design.md) 에 있다.

---

## 1. 이 모드가 무엇인가

PIT Fireteam 1.0.0 의 **포크**다. PIT 는 모드가 소유한 **용병**을 팀원으로 쓰는데, STM 은 거기에
**SPT 런처의 다른 프로필**을 팀원으로 쓰는 길을 더한다. 두 기능이 한 분대에 섞여도 된다.

핵심 차이가 설계 전체를 지배한다: **용병의 장비는 모드 안에만 있고, 프로필 팀원의 장비는 플레이어가
실제로 플레이하는 캐릭터의 재산이다.** 그래서 PIT 에서 무해한 동작이 STM 에서는 복제나 파괴가 된다.
이 문서에서 "PIT 와 갈라진다" 고 적힌 곳은 거의 전부 이 한 가지 이유다.

## 2. 지금 되는 것 / 안 되는 것

**된다**
- 다른 런처 프로필을 팀원으로 등록 → 명단·친구 목록에 뜬다(지금 로그인한 프로필은 절대 후보가 아니다)
- 초대하면 파티에 합류한다. **최대 4명** — 다섯째는 클라이언트가 "파티가 가득 찼습니다" 로 막는다
- **그 프로필의 실물 장비로** 레이드 투입. 쓸 장비가 없으면 **생성된 임시 장비**로 나가되
  레벨·체력·스킬은 그 프로필의 것을 유지한다(두 경로는 **인벤토리 하나만** 다르다)
- **실물로 나갔다 돌아오지 못하면** 착용 장비를 그 프로필에서 지운다.
  스태시·보안 컨테이너 내용물·주머니 컨테이너·완장·칼집은 **남는다**
- 플레이어가 시체에서 털어 나온 것은 **플레이어가 가진다**(그 아이템의 보호를 풀어 준다)
- 같은 레이드를 두 번 처리하지 않는다(영수증)

**일부러 안 한다**
- **프로필에 더하는 것은 전부 안 한다** — 경험치·스킬·전적·전리품. 계획 2 는 **빼는 쪽만** 쓴다.
  더하는 쪽이 복제 버그가 사는 자리이고, 경험치 적립은 **레벨 재계산**을 불러 그 프로필로 로그인했을 때
  레벨이 어긋난다(설계 §4). → **계획 4**
- 장비 편집, 팀원 상세 화면 → **계획 3**
- 임시 장비로 죽은 팀원의 시체에서 털어 온 것은 레이드 종료 때 **사라진다**. 풀어 주면 맨몸 프로필을
  초대해 죽게 두고 터는 **무한 장비 공급원**이 열린다. 소멸이 버그처럼 보이므로 로그로 알린다

## 3. 반드시 지켜야 할 불변식

새 코드를 쓰기 전에 이 넷을 읽어라. 계획 2 에서 **실제로 깨뜨렸다가 인게임에서 발견한** 것들이다.

1. **`StmResolvedMember.Pmc` 는 `SaveServer` 가 들고 있는 살아 있는 객체다.** 복제 없이 만지면
   플레이어의 저장된 프로필이 바뀐다. 모든 스폰 경로는 `cloner.Clone`(FastCloner, 깊은 복제) 위에 선다.
   PIT 의 보정 헬퍼(`EnsureFollowerHasPockets`·`...ScabbardKnife`·`Refill...`)는 **더하기만 하지 않는다** —
   아이템 더미를 지우고 수량을 다시 쓰고 부모를 바꾼다. 복제본이라서 안전한 것이지 순한 함수라서가 아니다.
2. **의심스러우면 쓰지 않는다.** 삭제 앞에 가드가 14개 있고 전부 닫힌 쪽으로 떨어진다. 읽지 못하면
   "아직 안 된다" 로 치고, 모르는 enum 값은 삭제하지 않는 쪽으로 간다(허용 목록이지 제외 목록이 아니다).
3. **호출부는 STM 해석기를 먼저 묻는다.** PIT 를 먼저 물으면, 용병과 프로필이 Aid 를 공유할 때
   명단에는 프로필이 보이는데 **보이지 않는 용병이 초대·스폰된다.** 네 경로 전부 이 순서다.
4. **PIT 자신의 파일은 `private` → `internal` 승격만** 한다. 구조를 바꾸면 업스트림 병합면이 넓어진다.

## 4. 코드 지도

```
src/SptTeamManager/
  shared/     순수 정책 — SPT 타입 없음, 테스트가 여기만 닿는다(138개)
              ProfileMemberLookup      Aid → 프로필, 충돌이면 막는다
              SpawnGearPolicy          실물이냐 임시냐 + 슬롯 어휘
              WornGearLossPolicy       죽을 때 무엇을 지우는가  ← 가장 위험한 판단
              RaidOutcomePolicy        지울까 말까
              RaidReceiptKeyPolicy     멱등 키
              RaidProtectionReleasePolicy  지운 것만 플레이어에게 넘긴다
              FollowerAiProfilePolicy  진영 → AI 역할·난이도
  server/     SPT 에 닿는 쪽 — 테스트 불가(테스트 프로젝트가 SPT 어셈블리를 일부러 참조하지 않는다)
              StmProfileMemberResolver 3값 계약: 참 / 거짓+사유 / 거짓+널(= PIT 경로로)
              StmSpawnProfileFactory   스폰 BotBase 를 만든다
              StmRaidOutcomeService    프로필에 쓰는 유일한 곳
              StmRaidReceiptStore      TryReserve 만 쓴다(먼저 예약하고 그 다음 지운다)
  client/     계획 2 는 한 줄도 안 건드렸다
```

**순수/비순수 경계가 이 설계의 중심이다.** "무엇을 할까" 는 `shared/` 에서 테스트로 고정하고,
"어떻게 할까" 만 `server/` 에 둔다. 판단이 `server/` 에 남으면 아무도 그것이 틀린 줄 모른다 —
계획 2 에서 두 판을 들여 발견한 결함이 정확히 그런 자리에 있었다.

## 5. 열린 항목

| | 무엇 | 비고 |
|---|---|---|
| 1 | ~~`/singleplayer/pitfireteam/teammate/profile` 이 프로필 팀원을 모른다~~ | **메웠다 (2026-11-02, `fix/stm-profile-view-fourth-path`).** 다만 **지금은 닿지 않는 코드다** — 그 경로를 부르는 유일한 자리가 auto-join 로더이고, 그 로더가 쓰는 **목록 쪽이 아직 프로필 팀원을 모른다**(아래 1-c). 수정은 맞고 전제 조건이지만 단독으로는 보이는 변화가 없다 |
| 1-c | auto-join 이 프로필 팀원에게 동작하지 않는다 | **인게임에서 확인된 미동작.** auto-join 은 "지난 분대 복원" 이 아니라 **출격 화면에서 자동 합류**시키는 팀원별 토글이다(기본 꺼짐). 필요한 세 곳 중 **토글 저장**(`SetTeammateAutoJoin`, 프로필 팀원이면 throw)과 **목록 조회**(`GetAutoJoinTeammateAccountIds`, PIT 만 열거)가 남았다. `StmProfileMemberStore` 에 **갱신 경로가 없어** 저장 계층도 손대야 하고, 로스터 와이어에 `autoJoin` 도 실어야 한다 → 결이 **계획 3** 에 가깝다. 대조표가 WORKLOG 정정 항목에 있다 |
| 1-b | `/client/profile/view`(`MergeProfileView`)도 프로필 팀원을 모른다 | 같은 성격의 **다섯 번째 경로**, 1번을 메우다 발견. 친구 목록에서 프로필 팀원을 눌렀을 때 무엇이 보이는지는 **SPT 가 다른 런처 프로필을 aid 로 돌려주는지에 달렸고 미판정이다**(추측하지 않았다). 고칠 자리면 `StmProfileViewFactory.TryBuildView` 를 그대로 부르면 된다 |
| 2 | 라이선스·`SptVersion` 표기 | 모드 페이지는 MIT 라는데 LICENSE 파일이 없고, 서버가 `SptVersion = "~4.1.0"` 을 선언하는데 클라이언트는 4.1.6 기준으로 컴파일한다. **배포 전에 정리해야 한다**(개인용이면 무관) |
| 3 | 제스처 명령 `FIRE`·`HOLD FIRE`·`TAKE COVER` 미대응 | 메뉴 18개 중 11개만 처리한다. 교전 통제 손잡이라 **계획 3 후보**. 대조표가 WORKLOG 에 있다 |
| 4 | 탄창 리필은 몸에 지닌 탄만 쓴다 | 2026-11-02 결정. 그러니 **프로필에 장비를 채울 때 탄도 함께** 넣어야 한다 |

## 6. 다음 사람에게 주는 조언

- **인게임 확인을 건너뛰지 마라.** 계획 2 에서 단위 테스트 141개와 Task 별 리뷰를 **전부 통과한 뒤에**
  결함 셋이 드러났다 — 빈 탄창, AI 역할·난이도, 시체 전리품 소멸. 셋 다 설계 지시가 **확인하지 않은 전제**를
  깔고 있었고, 실제 프로필 JSON 을 한 번 열어 봤으면 둘은 설계 단계에서 잡혔다.
- **테스트 요약줄을 믿지 마라.** 중단된 실행도 "통과!" 로 찍힌다. **총 개수**를 기대값과 맞춰라.
- **프로필을 건드리기 전에 백업하라.** `backup/2026-11-01-before-*` 에 전례가 있다. 비교는 로그가 아니라
  **프로필 JSON 대조**로 하는 것이 결정적이었다 — 아이템 `_id` 는 레이드를 거쳐도 유지되므로
  "사라진 id 가 플레이어에게 있는가" 를 그대로 물을 수 있다.
- **설치본과 레포가 어긋나지 않게 하라.** 설치한 DLL 의 md5 가 빌드 산출물과 같은지, 그보다 새로운
  `.cs` 가 없는지 매번 확인했다. 인게임 결과를 어느 코드의 것인지 말할 수 있어야 한다.
