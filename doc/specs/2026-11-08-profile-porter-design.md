# ProfilePorter — 프로필 사이로 물건을 베끼는 관리 도구 (설계)

작성 2026-11-08. **사용자 요청 4**(계획 6 §0 의 "새 export/import 모드")다. 선례 모양은
[2026-10-28-airdrop-caller-design.md](2026-10-28-airdrop-caller-design.md) — 서버 모드 + 창,
안전장치는 [SptTeamManager](../../src/SptTeamManager) 에서 가져온다.

**이름은 임시다.** 더 나은 이름이 나오면 구현 전에 바꾼다.

## 0. 범위 — 사용자가 정한 셋 (2026-11-08)

| 물음 | 정해진 것 |
| --- | --- |
| **무엇을** | **스태시 아이템**과 **장비 한 벌(로드아웃)** |
| **어디에서 어디로** | **같은 설치본의 프로필 사이** |
| **조작은 어디서** | **WPF 창** (AirdropCaller 와 같은 모양) |

나머지(프로필 전체, 팀원 묶음, 다른 PC 로 들고 나가기)는 **이 설계의 범위가 아니다.**

## 1. 의도

프로필이 아홉 개 있다. 한 프로필에 있는 물건이나 입고 있는 한 벌을 **다른 프로필에도 그대로**
두고 싶다. 지금은 길이 둘뿐이고 둘 다 맞지 않는다.

- **STM 의 스태시 교환**은 **옮긴다** — 주면 내 것이 없어진다.
- **AirdropCaller 의 프리셋**은 상자에 **새로 만들어** 떨어뜨린다. 레이드를 돌아야 하고,
  이미 가진 물건의 상태(내구도·탄·부착물)가 아니라 tpl 로 다시 세운 새 물건이다.

요청 4 는 그 사이다 — **가진 것을 그대로, 레이드 없이, 원본을 남긴 채** 다른 프로필에 둔다.

## 2. 성격을 먼저 못박는다 — 이것은 **복제 도구**다

**이 모드는 물건을 늘린다.** 게임 안 경제의 규칙을 따르지 않는다. 그것이 결함이 아니라
**이 도구의 정의**다. 그래서 STM 의 안전장치를 **그대로 쓰면 안 된다** — 그쪽은 늘어나는 것을
결함으로 보고 막도록 만들어져 있다.

### 2.1 저널을 태우면 import 가 **전부** 거절된다 (실측으로 확인)

[`StmStashTransferService.VerifyFromDisk`](../../src/SptTeamManager/server/Services/StmStashTransferService.cs)
가 디스크를 다시 읽어 두 가지를 본다.

```
옮긴 id 가 받는 쪽에 없으면        → 실패
옮긴 id 가 빼는 쪽에도 남아 있으면 → 실패 ("복제")
```

그리고 그 앞(같은 파일 161~168줄)에서 **받는 쪽에 같은 id 가 이미 있으면 거절**한다
(`옮기려는 아이템과 같은 식별자가 받는 쪽에 이미 있어 옮기지 않았습니다`).

import 는 원본을 **남긴 채** 베끼는 일이므로 이 두 검사에 정면으로 걸린다. 그래서:

> **ProfilePorter 는 STM 의 전송 저널을 쓰지 않는다.** 3단 저널은 "한쪽에서 빠지고 한쪽에
> 생긴다" 를 지키는 장치이고, 여기서는 지킬 그 불변식이 없다.

### 2.2 그 대신 무엇으로 지키나

저널이 없다고 안전장치가 없는 것은 아니다. 다른 불변식을 둔다.

| STM 이 지키던 것 | ProfilePorter 가 지키는 것 |
| --- | --- |
| 총량 보존(늘지도 줄지도 않는다) | **원본 불변** — 내보내는 쪽 프로필은 **한 바이트도 고치지 않는다** |
| 같은 id 가 양쪽에 있으면 거절 | **id 는 들여올 때 전부 새로 매긴다** — 같은 id 가 두 프로필에 생기지 않는다 |
| 3단 저널 + 디스크 재독 | **들여오기는 한 프로필만 고친다** — 반만 끝난 상태가 두 파일에 걸치지 않는다. 쓰기 전 **그 프로필의 백업**을 뜬다 |

## 3. 확인된 사실 (설치본 실측, 2026-11-08)

### 3.1 프로필 아홉의 규모

| 프로필 | 아이템 전체 | 스태시 바닥 | 장비 1단 슬롯 |
| --- | --- | --- | --- |
| Nomad (플레이어) | 1,806 | 56 | 15 |
| Banshee | 302 | 63 | 13 |
| Knox | 297 | 99 | 12 |
| Hawk | 533 | 110 | 13 |
| Buck | 337 | 105 | 4 |
| Mace | 402 | 163 | 13 |
| Raptor | 290 | 105 | 14 |
| Wraith | 403 | 153 | 13 |
| Talon | 199 | 82 | 12 |

"스태시 바닥" 은 스태시 루트의 자식 중 `hideout` 칸에 놓인 것이다(STM 의 `StashTransferPolicy`
가 쓰는 것과 같은 정의). 한 벌을 통째로 베껴도 **수백 개 단위**이지 수천이 아니다.

### 3.2 id 는 이미 프로필을 가로질러 겹쳐 있다 — 11건

```
5fe49444ae6628187a2e78b8   Banshee / Knox / Hawk / Buck / Mace / Raptor / Talon
676db384777490e23c45b657   Banshee / Knox / Hawk / Buck / Mace / Raptor / Wraith / Talon
… 모두 11건
```

**플레이어(Nomad)는 한 건도 끼지 않는다.** 팀원 프로필을 같은 틀에서 만들면서 생긴 것이고,
전송 이전부터 그대로였다(2026-11-08 전송 감사에서 이미 확인된 수치와 같다).

이것이 뜻하는 바가 둘이다.

1. **"id 가 겹치면 큰일" 이라는 전제는 이미 사실이 아니다.** 겹친 채로 게임이 돌고 있다.
2. 그래도 **우리가 더 만들지는 않는다.** 들여올 때 새로 매기는 것이 공짜이기 때문이다
   (§4.2). 이미 있는 11건을 핑계로 규칙을 느슨하게 할 이유가 없다.

### 3.3 장비 트리를 파일로 옮기는 코드는 **이미 있다**

[`AirdropCaller.Server/EquipmentExtractor.cs`](../../src/AirdropCaller.Server/EquipmentExtractor.cs)
(334줄)가 로그인 프로필의 장비 트리를 `ItemSpec` 트리로 바꾼다 — §18. 2026-11-06 실측에서
**장비 트리 200개를 전부 훑고 못 닿은 것 0**, 탄 226=226 이었다.

**그러나 그대로 쓸 수 없다.** `ItemSpec` 은 "tpl 과 몇 개" 의 설계도라서 **물건의 상태를 잃는다** —
내구도, 남은 탄, 수리 횟수, 검사 여부(`Upd`). AirdropCaller 는 새로 만들어 떨어뜨리는 쪽이라
그것으로 충분했지만, 요청 4 는 **가진 것 그대로**가 요구사항이다(§1).

> 그래서 ProfilePorter 의 파일 형식은 `ItemSpec` 이 아니라 **프로필의 `Items` 배열을 거의 그대로**
> 담는다(§4.1). `EquipmentExtractor` 에서 가져오는 것은 **트리를 빠짐없이 훑는 방법**이지
> 자료 구조가 아니다.

## 4. 결정된 사항

### 4.1 파일 형식 — 프로필의 `Items` 를 거의 그대로 담는다

```jsonc
{
  "format": "profile-porter/1",
  "kind": "stash" | "loadout",
  "createdUtc": "2026-11-08T05:42:54Z",
  "from": { "profileId": "6adc…", "nickname": "Nomad" },
  "rootIds": ["…"],          // 고른 것들의 id(파일 안 기준). 자손은 items 에 함께 들어 있다
  "items": [ /* 프로필의 Item 객체 그대로 — _id, _tpl, parentId, slotId, location, upd */ ]
}
```

- **`upd` 를 그대로 싣는다.** 이것이 "가진 것 그대로" 의 전부다.
- `kind` 를 나누는 이유는 들여올 때 **가는 곳이 다르기** 때문이다 — `stash` 는 스태시 바닥,
  `loadout` 은 §4.4 를 본다.
- **설치본 표시를 넣지 않는다.** 범위가 "같은 설치본" 이므로 비교할 상대가 없다. 나중에
  범위가 넓어지면 그때 더한다(§8).

### 4.2 들여올 때 **id 를 전부 새로 매긴다**

파일 안의 모든 `_id` 에 새 `MongoId` 를 하나씩 만들어 **옛 id → 새 id** 표를 만들고,
`parentId` 도 그 표로 옮긴다. 표에 없는 `parentId`(= 파일 밖을 가리키는 것)는 **들여오기를
거절하는 사유**다 — 조용히 떼어 내면 부모 없는 아이템이 프로필에 남는다.

이것이 §2.2 의 두 번째 안전장치이고, 값이 거의 없다(문자열 사전 하나).

### 4.3 자리 찾기 — 받는 쪽 스태시에 **들어갈 자리가 없으면 거절한다**

쪼개서 넣지 않는다. **전부 들어가거나 하나도 안 들어간다.** 반만 들어간 스태시는 사람이
되돌리기 어렵다.

격자 배치는 AirdropCaller 의 `CrateBuilder` 가 푸는 것과 같은 문제다 — 그리고 2026-11-07 에
**용기의 격자를 전부 여는 고침**이 들어갔다(§20). 베낄 때 그 교훈을 같이 가져온다:
**격자가 여럿인 용기는 격자마다 지도를 따로 만든다.**

### 4.4 장비 한 벌은 **입히지 않는다. 스태시에 넣는다**

받는 프로필이 이미 무언가를 입고 있으면 덮어쓰는 셈이 되고, 덮어쓴 것은 사라진다.
한 벌은 **받는 쪽 스태시 바닥에** 그대로 풀어 놓고, 입는 것은 사람이 게임에서 한다.

> 이 결정은 뒤집을 수 있다. 다만 뒤집으려면 "덮어쓰이는 쪽을 어디에 두나" 를 먼저 정해야 한다.

### 4.5 내보내지 않는 것

| 빼는 것 | 왜 |
| --- | --- |
| **보안 컨테이너와 그 안** | AirdropCaller §18.3 이 같은 결정을 했다(혼자 178개). 게임이 특별 취급하는 칸이다 |
| **퀘스트 물품** | 그 프로필의 퀘스트 진행에 묶여 있다. 베끼면 어느 쪽 진행이 맞는지 알 수 없다 |
| **장착된 보험·우편함·은신처의 것** | 스태시 바닥이 아니다. 범위 밖이다 |

빼는 것은 **조용히 빼지 않는다** — `skipped` 로 몇 개를 왜 뺐는지 말한다(AirdropCaller §7.5
와 같은 규칙).

### 4.6 쓰기 전에 **그 프로필을 백업한다**

들여오기는 되돌릴 수 없는 쓰기다. `backup/porter-<UTC>/<profileId>.json` 으로 먼저 뜬다.
2026-11-08 의 끊김 실험이 가르친 것이 이것이다 — **백업까지가 작업이다.**

## 5. 안티목표 — 이것이 일어나면 실패다

1. **내보내는 쪽 프로필이 바뀐다.** 읽기 전용이어야 한다.
2. **반만 들여와진다.** 전부 아니면 아무것도.
3. **같은 id 가 두 프로필에 새로 생긴다.** §4.2 가 막는다.
4. **부모 없는 아이템이 프로필에 남는다.** 그 프로필로 로그인한 게임이 망가진다.
5. **조용히 빠진다.** 뺀 것은 반드시 말한다.

## 6. 만들 것

```
src/ProfilePorter.Server/      net10.0, SPT 서버 모드
  ModMetadata.cs
  ProfilePorterRouter.cs       /profile-porter/{profiles,export,import,preview}
  ProfileReader.cs             프로필 읽기(읽기 전용). 디스크가 진실이다
  ExportBuilder.cs             고른 id → 자손까지 훑어 파일 꾸러미로
  ImportPlanner.cs             id 재매김 + 자리 찾기. 거절 사유를 말로 돌려준다
  PorterFiles.cs               내보낸 파일 읽기·쓰기(`porter/` 폴더)
src/ProfilePorter.Tests/       ImportPlanner·ExportBuilder 단위 테스트
src/ProfilePorter.App/         net10.0 WPF — 왼쪽 프로필·오른쪽 프로필·가운데 파일 목록
tools/install-profileporter.ps1
```

**플러그인(BepInEx)은 만들지 않는다.** 레이드 중에 할 일이 없다 — 이것이 AirdropCaller 와
가장 다른 점이다.

**순수한 것을 테스트로 덮는다**: id 재매김(표가 빠짐없는가), 자손 수집(총 개수), 자리 찾기
(격자가 여럿인 용기). 게임 없이 검증할 수 있는 전부가 거기다.

## 7. 단계

| 단계 | 무엇 | 끝났다고 보는 근거 |
| --- | --- | --- |
| **P1** | **재는 것** — 한 프로필의 스태시 바닥 한 벌을 실제로 훑어, 자손까지 몇 개이고 `upd` 에 무엇이 들어 있는지 센다 | 숫자가 문서에 적힌다. 추측으로 넣은 난간은 난간이 아니다(2026-11-08 §4-2 의 교훈) |
| **P2** | **순수 판정** — `ImportPlanner`(id 재매김·자손 수집·거절 사유) + 테스트 | 일부러 부모를 빼면 그 시험만 빨개진다 |
| **P3** | **서버 라우트** — export/import. 백업이 **먼저**고 쓰기가 나중이다 | 디스크 재독으로 "받는 쪽에 다 있고, **보내는 쪽은 그대로**" 를 본다 |
| **P4** | **창** | 사람이 골라서 내보내고 들여온다 |
| **P5** | **인게임 관문** | 들여온 프로필로 로그인해 물건이 멀쩡히 보이고 게임이 안 깨진다 |

**P1 이 먼저인 이유**는 A5 에서 값을 치르고 배운 것과 같다 — 재지 않고 상한을 넣으면 그 상한이
조용히 물건을 깎는다.

## 8. 미확인 사항 — 이 설계의 약한 곳

- **`upd` 를 그대로 옮겨도 되는지 재지 않았다.** 보험 표시·검사 여부처럼 **그 프로필에만 뜻이
  있는 필드**가 섞여 있을 수 있다. P1 이 그것을 센다.
- **스택이 묶인 물건을 베낄 때의 최대치.** AirdropCaller 가 "묶음을 깎고 말해 준다" 로 푼 자리와
  같은 문제인지 확인하지 않았다.
- **받는 쪽 스태시의 크기 제한**(은신처 등급에 따라 다르다)을 어디서 읽는지 확인하지 않았다.
- **다른 설치본으로 들고 나가기**는 범위 밖이지만, 그렇게 되면 **tpl 이 그 설치본에 있는지**
  검사하는 층이 하나 더 필요하다. 파일에 `format` 을 둔 것은 그때를 위한 자리다.
