# ProfilePorter — 프로필 사이로 물건을 베끼는 관리 도구 (설계)

작성 2026-11-08. **사용자 요청 4**(계획 6 §0 의 "새 export/import 모드")다. 선례 모양은
[2026-10-28-airdrop-caller-design.md](2026-10-28-airdrop-caller-design.md) — 서버 모드 + 창,
안전장치는 [SptTeamManager](../../src/SptTeamManager) 에서 가져온다.

**이름은 임시다.** 더 나은 이름이 나오면 구현 전에 바꾼다.

## 0. 범위 — 사용자가 정한 셋 (2026-11-08)

| 물음 | 정해진 것 |
| --- | --- |
| **무엇을** | **스태시 아이템**과 **장비 한 벌(로드아웃)** |
| **어디에서 어디로** | **같은 설치본의 프로필 사이** |
| **조작은 어디서** | **WPF 창** (AirdropCaller 와 같은 모양) |

나머지(프로필 전체, 팀원 묶음, 다른 PC 로 들고 나가기)는 **이 설계의 범위가 아니다.**

## 1. 의도

프로필이 아홉 개 있다. 한 프로필에 있는 물건이나 입고 있는 한 벌을 **다른 프로필에도 그대로**
두고 싶다. 지금은 길이 둘뿐이고 둘 다 맞지 않는다.

- **STM 의 스태시 교환**은 **옮긴다** — 주면 내 것이 없어진다.
- **AirdropCaller 의 프리셋**은 상자에 **새로 만들어** 떨어뜨린다. 레이드를 돌아야 하고,
  이미 가진 물건의 상태(내구도·탄·부착물)가 아니라 tpl 로 다시 세운 새 물건이다.

요청 4 는 그 사이다 — **가진 것을 그대로, 레이드 없이, 원본을 남긴 채** 다른 프로필에 둔다.

## 2. 성격을 먼저 못박는다 — 이것은 **복제 도구**다

**이 모드는 물건을 늘린다.** 게임 안 경제의 규칙을 따르지 않는다. 그것이 결함이 아니라
**이 도구의 정의**다. 그래서 STM 의 안전장치를 **그대로 쓰면 안 된다** — 그쪽은 늘어나는 것을
결함으로 보고 막도록 만들어져 있다.

### 2.1 저널을 태우면 import 가 **전부** 거절된다 (실측으로 확인)

[`StmStashTransferService.VerifyFromDisk`](../../src/SptTeamManager/server/Services/StmStashTransferService.cs)
가 디스크를 다시 읽어 두 가지를 본다.

```
옮긴 id 가 받는 쪽에 없으면        → 실패
옮긴 id 가 빼는 쪽에도 남아 있으면 → 실패 ("복제")
```

그리고 그 앞(같은 파일 161~168줄)에서 **받는 쪽에 같은 id 가 이미 있으면 거절**한다
(`옮기려는 아이템과 같은 식별자가 받는 쪽에 이미 있어 옮기지 않았습니다`).

import 는 원본을 **남긴 채** 베끼는 일이므로 이 두 검사에 정면으로 걸린다. 그래서:

> **ProfilePorter 는 STM 의 전송 저널을 쓰지 않는다.** 3단 저널은 "한쪽에서 빠지고 한쪽에
> 생긴다" 를 지키는 장치이고, 여기서는 지킬 그 불변식이 없다.

### 2.2 그 대신 무엇으로 지키나

저널이 없다고 안전장치가 없는 것은 아니다. 다른 불변식을 둔다.

| STM 이 지키던 것 | ProfilePorter 가 지키는 것 |
| --- | --- |
| 총량 보존(늘지도 줄지도 않는다) | **원본 불변** — 내보내는 쪽 프로필은 **한 바이트도 고치지 않는다** |
| 같은 id 가 양쪽에 있으면 거절 | **id 는 들여올 때 전부 새로 매긴다** — 같은 id 가 두 프로필에 생기지 않는다 |
| 3단 저널 + 디스크 재독 | **들여오기는 한 프로필만 고친다** — 반만 끝난 상태가 두 파일에 걸치지 않는다. 쓰기 전 **그 프로필의 백업**을 뜬다 |

## 3. 확인된 사실 (설치본 실측, 2026-11-08)

### 3.1 프로필 아홉의 규모

| 프로필 | 아이템 전체 | 스태시 바닥 | 장비 1단 슬롯 |
| --- | --- | --- | --- |
| Nomad (플레이어) | 1,806 | 56 | 15 |
| Banshee | 302 | 63 | 13 |
| Knox | 297 | 99 | 12 |
| Hawk | 533 | 110 | 13 |
| Buck | 337 | 105 | 4 |
| Mace | 402 | 163 | 13 |
| Raptor | 290 | 105 | 14 |
| Wraith | 403 | 153 | 13 |
| Talon | 199 | 82 | 12 |

"스태시 바닥" 은 스태시 루트의 자식 중 `hideout` 칸에 놓인 것이다(STM 의 `StashTransferPolicy`
가 쓰는 것과 같은 정의). 한 벌을 통째로 베껴도 **수백 개 단위**이지 수천이 아니다.

### 3.2 id 는 이미 프로필을 가로질러 겹쳐 있다 — 11건

```
5fe49444ae6628187a2e78b8   Banshee / Knox / Hawk / Buck / Mace / Raptor / Talon
676db384777490e23c45b657   Banshee / Knox / Hawk / Buck / Mace / Raptor / Wraith / Talon
… 모두 11건
```

**플레이어(Nomad)는 한 건도 끼지 않는다.** 팀원 프로필을 같은 틀에서 만들면서 생긴 것이고,
전송 이전부터 그대로였다(2026-11-08 전송 감사에서 이미 확인된 수치와 같다).

이것이 뜻하는 바가 둘이다.

1. **"id 가 겹치면 큰일" 이라는 전제는 이미 사실이 아니다.** 겹친 채로 게임이 돌고 있다.
2. 그래도 **우리가 더 만들지는 않는다.** 들여올 때 새로 매기는 것이 공짜이기 때문이다
   (§4.2). 이미 있는 11건을 핑계로 규칙을 느슨하게 할 이유가 없다.

### 3.3 장비 트리를 파일로 옮기는 코드는 **이미 있다**

[`AirdropCaller.Server/EquipmentExtractor.cs`](../../src/AirdropCaller.Server/EquipmentExtractor.cs)
(334줄)가 로그인 프로필의 장비 트리를 `ItemSpec` 트리로 바꾼다 — §18. 2026-11-06 실측에서
**장비 트리 200개를 전부 훑고 못 닿은 것 0**, 탄 226=226 이었다.

**그러나 그대로 쓸 수 없다.** `ItemSpec` 은 "tpl 과 몇 개" 의 설계도라서 **물건의 상태를 잃는다** —
내구도, 남은 탄, 수리 횟수, 검사 여부(`Upd`). AirdropCaller 는 새로 만들어 떨어뜨리는 쪽이라
그것으로 충분했지만, 요청 4 는 **가진 것 그대로**가 요구사항이다(§1).

> 그래서 ProfilePorter 의 파일 형식은 `ItemSpec` 이 아니라 **프로필의 `Items` 배열을 거의 그대로**
> 담는다(§4.1). `EquipmentExtractor` 에서 가져오는 것은 **트리를 빠짐없이 훑는 방법**이지
> 자료 구조가 아니다.

## 4. 결정된 사항

### 4.1 파일 형식 — 프로필의 `Items` 를 거의 그대로 담는다

```jsonc
{
  "format": "profile-porter/1",
  "kind": "stash" | "loadout",
  "createdUtc": "2026-11-08T05:42:54Z",
  "from": { "profileId": "6adc…", "nickname": "Nomad" },
  "rootIds": ["…"],          // 고른 것들의 id(파일 안 기준). 자손은 items 에 함께 들어 있다
  "items": [ /* 프로필의 Item 객체 그대로 — _id, _tpl, parentId, slotId, location, upd */ ]
}
```

- **`upd` 를 그대로 싣는다.** 이것이 "가진 것 그대로" 의 전부다.
- `kind` 를 나누는 이유는 들여올 때 **가는 곳이 다르기** 때문이다 — `stash` 는 스태시 바닥,
  `loadout` 은 §4.4 를 본다.
- **설치본 표시를 넣지 않는다.** 범위가 "같은 설치본" 이므로 비교할 상대가 없다. 나중에
  범위가 넓어지면 그때 더한다(§8).

### 4.2 들여올 때 **id 를 전부 새로 매긴다**

파일 안의 모든 `_id` 에 새 `MongoId` 를 하나씩 만들어 **옛 id → 새 id** 표를 만들고,
`parentId` 도 그 표로 옮긴다. 표에 없는 `parentId`(= 파일 밖을 가리키는 것)는 **들여오기를
거절하는 사유**다 — 조용히 떼어 내면 부모 없는 아이템이 프로필에 남는다.

이것이 §2.2 의 두 번째 안전장치이고, 값이 거의 없다(문자열 사전 하나).

### 4.3 ~~자리 찾기~~ — **§14 로 대체됐다 (2026-11-08)**

> 아래는 "스태시에 꽂아 넣던" 때의 결정이다. 우편 전달로 바꾸면서 **자리 찾기가 사라졌다.**
> 읽을 때 §14 를 먼저 본다.

쪼개서 넣지 않는다. **전부 들어가거나 하나도 안 들어간다.** 반만 들어간 스태시는 사람이
되돌리기 어렵다.

격자 배치는 AirdropCaller 의 `CrateBuilder` 가 푸는 것과 같은 문제다 — 그리고 2026-11-07 에
**용기의 격자를 전부 여는 고침**이 들어갔다(§20). 베낄 때 그 교훈을 같이 가져온다:
**격자가 여럿인 용기는 격자마다 지도를 따로 만든다.**

### 4.4 장비 한 벌은 **입히지 않는다** (놓는 곳은 §14 로 대체)

받는 프로필이 이미 무언가를 입고 있으면 덮어쓰는 셈이 되고, 덮어쓴 것은 사라진다.
한 벌은 **받는 쪽 스태시 바닥에** 그대로 풀어 놓고, 입는 것은 사람이 게임에서 한다.

> 이 결정은 뒤집을 수 있다. 다만 뒤집으려면 "덮어쓰이는 쪽을 어디에 두나" 를 먼저 정해야 한다.

### 4.5 내보내지 않는 것

| 빼는 것 | 왜 |
| --- | --- |
| **보안 컨테이너와 그 안** | AirdropCaller §18.3 이 같은 결정을 했다(혼자 178개). 게임이 특별 취급하는 칸이다 |
| **퀘스트 물품** | 그 프로필의 퀘스트 진행에 묶여 있다. 베끼면 어느 쪽 진행이 맞는지 알 수 없다 |
| **장착된 보험·우편함·은신처의 것** | 스태시 바닥이 아니다. 범위 밖이다 |

빼는 것은 **조용히 빼지 않는다** — `skipped` 로 몇 개를 왜 뺐는지 말한다(AirdropCaller §7.5
와 같은 규칙).

### 4.6 쓰기 전에 **그 프로필을 백업한다**

들여오기는 되돌릴 수 없는 쓰기다. `backup/porter-<UTC>/<profileId>.json` 으로 먼저 뜬다.
2026-11-08 의 끊김 실험이 가르친 것이 이것이다 — **백업까지가 작업이다.**

## 5. 안티목표 — 이것이 일어나면 실패다

1. **내보내는 쪽 프로필이 바뀐다.** 읽기 전용이어야 한다.
2. **반만 들여와진다.** 전부 아니면 아무것도.
3. **같은 id 가 두 프로필에 새로 생긴다.** §4.2 가 막는다.
4. **부모 없는 아이템이 프로필에 남는다.** 그 프로필로 로그인한 게임이 망가진다.
5. **조용히 빠진다.** 뺀 것은 반드시 말한다.


**순수한 것과 SPT 를 쓰는 것을 파일로 가른다.** 테스트 프로젝트는 `SptTeamManager.Tests` 와
같은 방식으로 순수 소스를 **한 줄씩 링크**한다(와일드카드 금지). 그래야 나중에 Server 에 SPT 를
쓰는 파일이 생겨도 **조용히 딸려 들어오지 않는다.** 별도 Core 프로젝트는 두지 않는다 — 이
저장소에 선례가 둘 다 있는데, 링크 쪽이 더 가볍다.

**플러그인(BepInEx)은 만들지 않는다.** 레이드 중에 할 일이 없다 — 이것이 AirdropCaller 와
가장 다른 점이다.

**순수한 것을 테스트로 덮는다**: id 재매김(표가 빠짐없는가), 자손 수집(총 개수), 자리 찾기
(격자가 여럿인 용기). 게임 없이 검증할 수 있는 전부가 거기다.

## 7. 단계

| 단계 | 무엇 | 끝났다고 보는 근거 |
| --- | --- | --- |
| **P1** | **재는 것** — 한 프로필의 스태시 바닥 한 벌을 실제로 훑어, 자손까지 몇 개이고 `upd` 에 무엇이 들어 있는지 센다 | 숫자가 문서에 적힌다. 추측으로 넣은 난간은 난간이 아니다(2026-11-08 §4-2 의 교훈) |
| **P2** | **순수 판정** — `ImportPlanner`(id 재매김·자손 수집·거절 사유) + 테스트 | 일부러 부모를 빼면 그 시험만 빨개진다 |
| **P3** | **서버 라우트** — export/import. 백업이 **먼저**고 쓰기가 나중이다 | 디스크 재독으로 "받는 쪽에 다 있고, **보내는 쪽은 그대로**" 를 본다 |
| **P4** | **창** | 사람이 골라서 내보내고 들여온다 |
| **P5** | **인게임 관문** | 들여온 프로필로 로그인해 물건이 멀쩡히 보이고 게임이 안 깨진다 |

**P1 이 먼저인 이유**는 A5 에서 값을 치르고 배운 것과 같다 — 재지 않고 상한을 넣으면 그 상한이
조용히 물건을 깎는다.

## 8. 미확인 사항 — 이 설계의 약한 곳

- **`upd` 를 그대로 옮겨도 되는지 재지 않았다.** 보험 표시·검사 여부처럼 **그 프로필에만 뜻이
  있는 필드**가 섞여 있을 수 있다. P1 이 그것을 센다.
- **스택이 묶인 물건을 베낄 때의 최대치.** AirdropCaller 가 "묶음을 깎고 말해 준다" 로 푼 자리와
  같은 문제인지 확인하지 않았다.
- **받는 쪽 스태시의 크기 제한**(은신처 등급에 따라 다르다)을 어디서 읽는지 확인하지 않았다.
- **다른 설치본으로 들고 나가기**는 범위 밖이지만, 그렇게 되면 **tpl 이 그 설치본에 있는지**
  검사하는 층이 하나 더 필요하다. 파일에 `format` 을 둔 것은 그때를 위한 자리다.

### 9.1 베낄 단위의 크기

```
프로필      아이템  바닥  바닥+안  깊이   한벌  보안함  퀘스트   묶음
Nomad        1802    56     1358     7    419     189       0    290
Banshee       302    63      133     4    160       9       0     28
Knox          297    99      160     4    111       2       8     57
Hawk          533   110      368     4    156      11       0     44
Buck          337   105      294     4     18       6       7     31
Mace          402   163      229     4    155      13       0     16
Raptor        290   105      105     0    167      12       0     12
Wraith         403   153      284     3    113       1       0     38
Talon         199    82       82     0     99       1       0      5
```

- **"바닥" 과 "바닥+안" 이 많이 갈린다.** Nomad 는 56개를 고르면 **1,358개**가 따라온다(깊이 7).
  한편 Raptor·Talon 은 바닥 아이템에 자손이 **하나도 없다**(깊이 0). 고른 개수로 상한을 두면
  뜻이 없다 — **자손까지 센 수**로 둬야 한다.
- **한 벌에서 보안 컨테이너가 차지하는 몫이 크다** — Nomad 419개 중 **189개**. §4.5 가 보안함을
  빼기로 한 결정이 숫자로도 맞다.
- **퀘스트 물품은 스태시 바닥과 섞이지 않는다.** `questRaidItems`·`questStashItems` 가 **별도
  루트**이고 거기 달린 것은 8개·7개다(Knox·Buck). §4.5 의 전제가 확인됐다.

> 퀘스트 제출에 쓰일 수 있다는 점을 알고 두는 것이다. **유지로 정한다** — 이 도구는 이미
> 복제 도구이고(§2), 여기서만 깐깐해지는 것은 일관되지 않는다.

### 9.3 값을 치른 것 — **아이템 DB 를 파일로 재면 틀린다**

`SPT_Data/database/templates/items.json` 으로 재면 거짓이 나온다. 두 자리에서 확인했다.

| 재는 것 | 파일 | **돌고 있는 서버** |
| --- | --- | --- |
| 5.7x28 AP Tracer 최대 묶음 | 60 | **900** |
| 크리켄트 라이터 최대 묶음 | 1 | **200** |
| 은닉처(스태시) 칸 수 | 680 | **800** |

파일 기준으로는 **157종의 묶음이 "최대치 초과"** 로 잡혔지만, 전부 거짓 경보다 — 스택을 올리는
모드와 스태시를 키우는 모드가 지나간 뒤의 DB 가 진짜다. AirdropCaller 의 `config.jsonc` 주석이
이미 같은 말을 적어 두었다("어느 설정 파일도 진실이 아니다").

**그래서 ProfilePorter 의 검사는 전부 서버 DB(`ItemHelper`/`templateTable`)에서 읽는다.**
파일을 읽는 코드를 두지 않는다 — 두면 다음 사람이 그것을 쓴다.

> 덧붙여 **같은 설치본 안에서는 묶음 검사가 사실상 필요 없다.** 원본이 들고 있는 값은 그
> 설치본의 DB 가 이미 허용한 값이다. 검사가 필요해지는 것은 §8 의 "다른 설치본으로 들고
> 나가기" 가 범위에 들어올 때다.

### 9.4 §8 에서 닫힌 것 / 남은 것

| §8 의 항목 | 상태 |
| --- | --- |
| `upd` 를 그대로 옮겨도 되는지 | **닫혔다** — 20종을 셌고 위험한 필드가 없다(§9.2). `SpawnedInSession` 은 유지로 정했다 |
| 스택이 묶인 물건의 최대치 | **닫혔다** — 서버 DB 를 본다. 같은 설치본 안에서는 검사 자체가 필요 없다(§9.3) |
| 받는 쪽 스태시의 크기 제한 | **닫혔다** — 아홉 프로필이 같은 스태시 tpl 이고 서버 기준 **800칸**이다. 가장 많이 찬 Wraith 가 392칸 |
| 다른 설치본으로 들고 나가기 | 그대로 **범위 밖** |

남은 P1 거리는 없다. **다음은 P2(순수 판정 + 테스트)** 다.

## 10. P2 — 순수 판정과 시험 (2026-11-08)

`PorterBundle`·`ExportSelection`·`ImportPlanner` 셋이고 전부 **순수**다 — SPT 타입도, 프로필
파일도, DB 도 건드리지 않는다. 시험 **20건**이 붙었다(`dotnet test src/ProfilePorter.Tests`).

### 10.1 판정이 지키는 것

| 자리 | 규칙 |
| --- | --- |
| `ExportSelection.PlanStash` | 스태시 바닥에 놓인 것만 고를 수 있다. 가방을 고르면 **안의 것이 따라간다** |
| | 막힌 종류가 **안에** 들어 있으면 **뿌리째 거절**한다 — 안에서만 빼면 "잃어버렸다" 로 읽힌다 |
| | 상한은 **자손까지 센 수**(`MaxItems = 2048`). §9.1 이 그렇게 정하게 했다 |
| `ExportSelection.PlanLoadout` | 보안 컨테이너는 **통째로** 빼고, 몇 개를 뺐는지 말한다 |
| `ImportPlanner.Plan` | **id 를 전부 새로 매긴다**. 뿌리의 자리는 비워 둔다(자리 찾기가 채운다) |
| | 부모가 꾸러미 밖을 가리키면 거절. 뿌리에서 닿지 않는 것이 있어도 거절 |
| | `upd` 는 **손대지 않고 그대로** 간다 — 시험이 `Assert.Same` 으로 본다 |

### 10.2 값을 치른 것 — **통과만으로는 시험이 무엇을 지키는지 모른다**

20건이 전부 녹색이었다. 그대로 넘기지 않고 **일부러 망가뜨려** 봤다.

| 망가뜨린 것 | 바란 것 | 처음 받은 것 |
| --- | --- | --- |
| 부모가 꾸러미 밖인지 보는 검사를 통째로 들어냄 | 그 시험만 빨개진다 | **20건 전부 통과** |
| 상한을 "자손까지" 에서 "고른 개수" 로 바꿈 | 그 시험만 빨개진다 | 그 시험만 빨개짐 ✓ |
| id 재매김을 없애 옛 id 를 그대로 씀 | 빨개진다 | 3건이 빨개짐 ✓ |

**첫 줄이 문제였다.** 그 꾸러미는 뒤따르는 "뿌리에서 닿지 않는다" 검사에도 걸리므로, 앞의
검사를 들어내도 **여전히 거절**되어 시험이 녹색으로 남았다. 거절된다는 것만 보고 있었던 것이다.

고친 것은 코드가 아니라 **시험**이다 — 이제 **어느 검사가 잡았는지**를 사유로 확인한다
(`Assert.Contains("부모가 꾸러미 밖", plan.Reason)`). 고친 뒤 같은 돌연변이를 다시 넣으니
그 시험 하나만 빨개졌다.

> 겹치는 검사가 둘 있을 때, "거절되는가" 만 보는 시험은 **둘 중 하나를 지우는 것을 못 잡는다.**
> 사유까지 봐야 한 검사가 한 시험에 묶인다.

**P3(서버 라우트)**. 거기서 처음으로 SPT 를 쓴다 — 프로필 읽기, 자리 찾기(**서버 DB**, §9.3),
백업, 쓰기. 순수한 것과 SPT 를 쓰는 것은 §6 대로 **파일로 가른다.**

## 11. P3 — 서버 라우트 (2026-11-08, **코드까지**)

처음으로 SPT 를 쓴다. 파일 여덟 개이고 빌드 **경고 0 / 오류 0**, 순수 시험 20건은 그대로 녹색이다.

| 파일 | 하는 일 |
| --- | --- |
| `ProfilePorter.Server.csproj`·`ModMetadata.cs`·`Config.cs`·`config.jsonc`·`ConfigStore.cs` | AirdropCaller 와 같은 모양의 배선. 설정이 깨지면 **꺼진 채로** 돈다 |
| `ProfileReader.cs` | 프로필을 **읽기만** 한다 — 쓰는 메서드가 없다(안티목표 1) |
| `PorterFiles.cs` | `porter/` 읽기·쓰기, 들여오기 전 **백업** |
| `StashPlacer.cs` | 자리 찾기. `InventoryHelper.PlaceItemInContainer` 를 쓴다 |
| `ProfilePorterService.cs` | 내보내기·들여오기 조립 |
| `ProfilePorterRouter.cs` | `/profile-porter/{profiles,stash,files,export,import}` |
| `Startup.cs` | 켜질 때 한 줄. 하는 일은 기록뿐이다 |

### 11.1 들여오기의 순서 — 터질 수 있는 것을 먼저 끝낸다

```
순수 판정(id 재매김)  →  복제본에서 자리까지 찾아 보기  →  백업  →  실물에 쓰기  →  저장
```

앞의 둘에서 실패하면 **실물은 손대지 않은 채** 끝난다. STM 의 전송이 "저널을 열기 전에 끝낸다"
로 쓰는 규율과 같고, 저널이 없는 자리를 이 순서가 메운다(§2.2).

**백업이 실패하면 들여오지 않는다.** 되돌릴 길이 없는 채로 나아가지 않는다.

### 11.2 자리 찾기에서 조심한 것 둘

1. **좌표를 지어내지 않는다.** 빈 자리를 찾아 `ParentId`·`SlotId`·`Location` 을 쓰는 것은 SPT
   자신의 `PlaceItemInContainer` 다. 판정이 두 곳에 생기면 한쪽만 고쳐져 아이템이 겹쳐 놓인다.
2. **격자 지도를 놓을 때마다 다시 만든다.** 한 번 만들어 돌려 쓰면 **앞서 놓은 것이 지도에
   없어** 둘이 같은 칸에 겹친다.

### 11.3 아직 확인하지 않은 것 — **빌드가 된다고 도는 것은 아니다**

설치본 md5 가 빌드와 같은 것까지만 봤다(`bb15a38f`). **서버는 다시 켜지 못했다** — 사용자가
레이드 중이었다. 그래서 다음 셋은 **전혀 확인되지 않았다.**

| 확인할 것 | 어떻게 |
| --- | --- |
| DI 가 해석되는가(`unable to resolve` 0건) | 기동 로그 |
| 모드가 올라왔는가 | 기동 로그에 `[ProfilePorter] 프로필 N개, 내보낸 파일 M개` |
| 라우트가 답하는가 | `node tools/call-airdrop.mjs` 와 같은 왕복(zlib+쿠키)으로 `/profile-porter/profiles` |

그 뒤라야 **P3 의 끝났다는 근거**(디스크 재독으로 "받는 쪽에 다 있고 보내는 쪽은 그대로")를 잴
수 있다. 지금은 **코드와 설치까지**다.

## 12. 기동 확인 — 돌려 보니 둘이 틀렸다 (2026-11-08)

§11.3 이 "전혀 확인되지 않았다" 로 남긴 것을 닫았다. 서버를 세 번 켰고(150~165초, **포트로**
기다린다), **빌드가 되는데도 틀린 것이 둘** 나왔다.

### 12.1 요청 본문의 열쇠 이름이 대소문자를 가린다

```
{"profileId": "6aee…"}  → {"ok": false, "reason": "그 프로필을 찾지 못했습니다."}
{"ProfileId": "6aee…"}  → {"ok": true, ...}
```

`[JsonPropertyName]` 을 안 달면 **PascalCase 로만** 받는다. 창(P4)은 AirdropCaller 의
`ServerClient` 처럼 익명 객체를 보내므로 camelCase 가 나가고, 서버는 그것을 **조용히 null 로**
받아 "프로필을 찾지 못했습니다" 라는 **엉뚱한 사유**로 거절한다. 사유가 그럴듯해서 더 나쁘다 —
열쇠 이름 문제를 프로필 문제로 읽게 된다.

AirdropCaller 의 `QueueRequest` 가 모든 속성에 이것을 달고 있는 이유가 이것이었다. 요청 둘과
응답 둘(`ProfileSummary`·`PorterResult`)에 전부 달았다 — `record` 는 그냥 두면 PascalCase 로
나가고 익명 객체는 camelCase 로 나가, 한 모드가 **두 모양을 섞어** 내보내고 있었다.

### 12.2 `upd` 를 그대로 담으면 빈 필드까지 적힌다

| | 필드 수 |
| --- | --- |
| 원본 프로필의 그 아이템 | **2** (`Repairable`·`FireMode`) |
| 내보낸 파일의 같은 아이템 | **28** (26개가 `null`) |

SPT 의 `Upd` 는 쓰지 않는 필드까지 들고 있는 타입이라, 해석하지 않고 통째로 담으면 스키마가
전부 펼쳐진다. 값은 보존되니 기능은 맞지만 §4.1 이 파일 형식을 정할 때 든 이유 — "사람이 열어
보고 프로필과 견줄 수 있어야 한다" — 가 무너진다.

`DefaultIgnoreCondition = WhenWritingNull` 로 고쳤고, **담을 때와 적을 때가 같은 설정을 쓰게**
했다(다르면 한쪽에서 들어온 빈 필드가 다른 쪽에서 빠진다).

### 12.3 확인된 것

| 본 것 | 결과 |
| --- | --- |
| 모드가 올라오는가 | `모드 Profile Porter 버전 0.1.0 … 불러옴` + `[ProfilePorter] 프로필 9개, 내보낸 파일 0개` |
| DI·예외 | `unable to resolve`·`exception`·`fatal` **0건** |
| 라우트가 답하는가 | `/profile-porter/profiles`·`/stash`·`/export` 전부 200 |
| 세는 것이 P1 과 맞는가 | 바닥 개수가 §9.1 과 같다(Talon 82, Knox 99, Mace 163, Buck 105) |
| 자손이 따라가는가 | Hawk 의 한 뿌리를 내보내니 `count: 34` — 직접 센 34와 같다 |
| **원본이 안 바뀌는가** | export 전후 프로필 **md5 동일**(`9b9bce1e…`) — 안티목표 1 |

### 12.4 아직 하지 않은 것 — **들여오기**

`import` 는 **프로필에 실제로 쓴다.** 백업이 자동으로 뜨고 되돌릴 수 있지만, 사용자의 프로필에
아이템을 늘리는 일이라 **묻기 전에는 하지 않는다.** 그 전까지 P3 의 "받는 쪽에 다 있고 보내는
쪽은 그대로" 중 **보내는 쪽만** 확인된 상태다.

## 13. 들여오기까지 재 봤다 — P3 의 관문을 닫았다 (2026-11-08)

§12.4 가 "묻기 전에는 하지 않는다" 로 남긴 것을 사용자 승인을 받아 실제로 했다.
**Hawk → Talon**, 파일 `p3-시험-hawk-2`(뿌리 1개 / 자손까지 34개).

### 13.1 본 것

| 재는 것 | 바란 것 | **받은 것** |
| --- | --- | --- |
| 받는 쪽 아이템 수 | 199 → 233 | **233** (+34) |
| 파일의 **옛 id** 가 받는 쪽에 | 0건 | **0건** — id 를 전부 새로 매겼다 |
| **보내는 쪽**에 그 34개가 그대로 | 34/34 | **34/34** |
| **보내는 쪽 프로필 md5** | 안 바뀐다 | **`8ccd3f16…` 그대로** |
| 뿌리의 자리 | 좌표·회전이 정해진다 | `{x:6, y:10, r:"Vertical"}` |
| 자손이 따라왔는가 | 34 | 뿌리에서 세어 **34** |
| 백업 | 쓰기 **전에** 뜬다 | `backups/20261108-074833/<프로필>.json`, 아이템 **199개**(= 쓰기 전 수) |

### 13.2 "겹치는 id 6건" 은 우리가 만든 것이 아니다

들여온 뒤 보니 Talon 과 Hawk 이 **같은 id 6개**를 함께 들고 있었다. 그대로 보면 복제처럼 읽힌다.
**백업(= 들여오기 전 Talon)으로 같은 것을 세어 보니 그때도 6건**이었다 — §3.2 의 "프로필을
가로질러 이미 겹쳐 있는 11건" 가운데 Talon 이 낀 것이 정확히 그 여섯이다.

> 숫자가 놀랍게 나오면 **그 숫자를 만든 쪽**(백업·이전 스냅샷)에서 같은 것을 한 번 더 센다.
> 2026-11-08 의 전송 감사가 쓴 방법과 같다 — 프로필 백업이 "그 전" 스냅샷이다.

### 13.3 되돌렸다

시험이 실제로 아이템을 늘렸으므로 백업으로 되돌렸다. **서버를 먼저 껐다** — 서버가 프로필을
메모리에 들고 있어서, 켜 둔 채 파일만 바꾸면 다음 저장에 덮인다.

복원 뒤 md5 가 **들여오기 전과 글자까지 같다**(`57db84e3…`, 아이템 199개).

### 13.4 P3 의 상태

§7 의 P3 가 "끝났다고 보는 근거" 로 적은 **"디스크 재독으로 받는 쪽에 다 있고, 보내는 쪽은
그대로"** 를 양쪽 다 확인했다. **P3 은 끝났다.** 남은 것은 P4(창)와 P5(인게임 관문)다.

## 14. 들여오기를 **우편 전달**로 바꾼다 (2026-11-08, 사용자 요청)

§4.3·§4.4 가 정했던 "받는 쪽 스태시에 자리를 찾아 꽂는다" 를 **뒤집는다.**

> 사용자 요청: "스태시에 바로 꽂아 넣는 게 아니라 **인게임 메시지 아이템 전달 기능**을 이용해
> 해당 프로필에 전달할 수 있어야 한다."

### 14.1 왜 이쪽이 나은가 — 세 가지가 한꺼번에 풀린다

| 꽂아 넣기(옛) | **우편으로 보내기(새)** |
| --- | --- |
| 받는 쪽 스태시에 **자리가 있어야** 한다. 없으면 통째로 거절(§4.3) | 우편함이 받아 준다. **스태시가 꽉 차 있어도 보낸다** |
| 격자 지도를 놓을 때마다 다시 만들어야 한다(§11.2) — 틀리면 겹쳐 놓인다 | **자리 찾기가 아예 없다.** 틀릴 자리가 사라진다 |
| 들여오는 순간 프로필 재산이 된다. 무르려면 백업 복원뿐 | **사람이 우편에서 꺼낼 때** 재산이 된다. 안 꺼내면 그만이다 |

세 번째가 특히 크다. 이 도구는 복제 도구라(§2) 잘못 눌렀을 때 되돌릴 길이 중요한데,
우편은 **받는 사람이 한 번 더 확인하는 관문**을 공짜로 준다.

### 14.2 쓰는 것

```
MailSendService.SendSystemMessageToPlayer(
    MongoId sessionId, string message, List<Item> items,
    int? maxStorageTimeSeconds, List<ProfileChangeEvent> profileChangeEvents)
```

어셈블리에서 직접 읽은 시그니처다(`MetadataLoadContext` 로 확인). STM 의
`FriendlyPostRaidService` 가 보험 반환물을 보낼 때 쓰는 것과 같은 서비스다.

- **시스템 메시지**로 보낸다. 상인을 흉내 내지 않는다 — 이것은 게임 안 거래가 아니라
  관리 도구의 전달이다.
- 보관 기간은 설정에 둔다(`MailStorageDays`, 기본 **7일**). 짧으면 못 받고 사라진다.

### 14.3 바뀌지 않는 것

- **id 는 여전히 전부 새로 매긴다**(§4.2). 우편 아이템도 받으면 그 프로필의 것이 된다.
- **뿌리의 자리를 비워 두는 것**(§P2)은 그대로 맞다 — 오히려 우편 쪽에 더 맞는다.
  우편 아이템은 부모가 없는 채로 목록에 담긴다.
- **백업은 그대로 뜬다.** 우편도 프로필(`DialogueRecords`)에 쓰이므로 되돌릴 길을 남긴다.
- **전부 아니면 하나도.** 우편 하나에 전부 담는다.

### 14.4 지우는 것

`StashPlacer.cs` 는 **쓰이지 않게 되므로 지운다.** 남겨 두면 다음 사람이 "자리를 찾는 길도
있다" 고 읽는다 — §9.3 에서 파일 읽는 코드를 두지 않기로 한 것과 같은 이유다.

그래서 §4.3(자리 찾기)과 §4.4(한 벌은 스태시에 푼다)는 **이 절로 대체된다.** 한 벌도 우편으로
간다 — 입히지 않는 이유(§4.4)는 그대로 유효하고, 우편이면 "어디에 풀지" 조차 정할 필요가 없다.

### 15.1 값을 치른 것 — **md5 가 같아도 "최신" 이라는 뜻은 아니다**

`PorterFiles.cs` 에 `fileName` 을 더하고 **재빌드 없이** 설치했다. 설치본과 빌드의 md5 는
일치했고 서버도 멀쩡히 떴지만, 라우트 응답에 `fileName` 이 없었다. 파일 시각을 보니
**소스가 빌드보다 64초 새것**이었다 — 둘이 사이좋게 옛것이었던 것이다.

> 설치 확인은 md5 한 줄로 끝내지 않는다. **설치본 시각 > 고친 소스의 시각**인지 함께 본다.

## 16. 창을 고쳤다 — 이름·중복·격자 (2026-11-08, 사용자 요청)

사용자가 화면을 보고 셋을 짚었다.

| 요청 | 한 것 |
| --- | --- |
| 이름을 안 적으면 **프로필명+날짜_시각**으로 짓고, 같으면 묻거나 바꿔서 올린다 | 기본 이름은 **서버가** 짓는다(`프로필명-종류-날짜_시각`). 창과 서버가 각자 지으면 규칙이 둘로 갈린다 |

### 16.1 덮어쓰지 않는다

`PorterFiles.Write` 는 같은 이름이 있으면 **거절**한다(`NameTakenReason`). 창이 그 사유를
알아보고 묻는다 — **예**(덮어쓰기) / **아니요**(`-2`·`-3` 을 붙여 새 파일) / **취소**.
내보낸 파일은 사람이 만든 것이라, 조용히 덮으면 앞의 것이 사라진 줄도 모른다.

### 16.2 격자 — 자리는 맞고 크기는 아직 다 맞지 않는다

`Item.Location` 이 **`object`** 라서 처음에는 좌표를 통째로 놓쳤다. 칸에 놓인 것은 `{x,y,r}`,
슬롯에 꽂힌 것은 정수 색인이라 SPT 가 한 타입으로 묶지 않았고, **읽어 온 프로필은
`JsonElement`**, 서버가 만든 것은 `ItemLocation` 이다. `as ItemLocation` 만 쓰면 읽기 경로에서
조용히 null 이 되어 **110개가 전부 (0,0)** 에 겹쳤다(448칸). 둘 다 받도록 고쳤다.

회전은 `r == "Vertical"` 로 본다. 같은 자리에 `rotation` 이라는 bool 도 있지만 **둘이 다르다** —
실측에서 `rotation=true` 는 2개, `r=Vertical` 은 30개였고, 겹침이 적은 쪽은 `r` 이다(78 대 99).

**남은 오차: 겹침 88건 / 차지한 칸 402.** 크기를 `ItemHelper.GetItemSize` 로 받는데, 그것은
부착물까지 센 값이라 무기에는 맞지만 **삽입물로 커지는 방어구**는 게임보다 한 칸 크게 나온다
(Siege-R 플레이트 캐리어: DB 기본 4x4 → 받은 4x5). tpl 기본 크기로 바꿔도 78건이 남아
**둘 중 하나로는 안 맞는다** — 게임이 쓰는 계산을 더 봐야 한다.

그동안 창은 **큰 것부터 그린다.** 나중에 그린 것이 위로 오므로 작은 것이 큰 것에 가려져
못 누르는 일은 없다. 자리와 모양은 알아볼 수 있고, 고르기·내보내기에는 지장이 없다.

### 16.4 화면을 또 고쳤다 — 글자·여백·단추 (2026-11-08, 사용자 제보)

**1. 아이콘이 글자에 가렸다.** 1칸이 46px 밖에 안 되는데 아이콘과 이름을 겹쳐 얹었다.
이제 **아이콘이 오면 이름을 치운다** — 이름은 툴팁으로 가고, 칸에는 아이콘과 **묶음 수**만
남는다(인게임과 같은 모양: 수는 오른쪽 아래). 아이콘을 못 구한 것만 이름을 그대로 둔다 —
빈 칸을 그리면 무엇인지 알 수 없다.

**2. 격자 옆 여백에서 끌기가 안 먹었다.** 캔버스 너비를 격자 폭(`cellsH × 46`)에 딱 맞췄더니
창을 넓혔을 때 생기는 **오른쪽 여백이 캔버스 밖**이라, 거기서 시작한 끌기가 아무 데도 닿지
않았다. 캔버스를 **격자와 보이는 영역 중 큰 쪽**에 맞추고 `SizeChanged` 에서 다시 늘린다.

**3. 단추가 한 줄에 섞여 있었다.** 고르는 것과 내보내는 것을 **줄로 나눴다.**

```
[스태시 전체선택]  [선택 취소]
[고른 것 내보내기]  [착용장비 내보내기]
```

「착용장비 내보내기」는 **고른 것과 무관하게** 입은 장비 전체를 내보낸다 — 한 줄에 섞여
있으면 고르기 단추처럼 읽힌다. 툴팁에도 그렇게 적었다.

### 16.5 격자가 깨진 두 원인 (2026-11-08, 사용자 제보)

**1. 칸을 눌러도 아무 일이 없었다.** 아이템 상자에 `MouseLeftButtonUp` 을 걸어 두었는데,
캔버스가 `MouseLeftButtonDown` 에서 **마우스를 붙잡아(`CaptureMouse`)** `Up` 이 상자까지 가지
않았다. 끌기(여러 개 고르기)를 넣으면서 생긴 것이다. 이제 **캔버스가 눌린 자리를 직접 찾는다**
(`HitTest`) — 겹쳐 있으면 **작은 것**이 이긴다(위에 그려진 것과 같은 규칙).

**2. 상자가 터무니없이 크게 그려졌다.** `ItemHelper.GetItemSize` 를 썼는데, 그것은 "이 트리를
격자에 **펼쳐 놓으면** 얼마나 필요한가" 를 재는 함수라 **컨테이너 안에 든 것까지 더한다.**

| 같은 `Item Case` | 안에 든 것 | `GetItemSize` |
| --- | --- | --- |
| 하나 | 383개 | **38x4** |
| 둘 | 77개 | 11x5 |
| 셋 | 161개 | 5x3 |

스태시에서 상자는 안이 비었든 찼든 **같은 칸**을 차지한다. **tpl 기본 크기**(DB 의 Width/Height)로
바꿨다. 고친 뒤 그 여섯이 전부 **5x3** 으로 같아졌다.

| 프로필 | 겹침(고치기 전 → 뒤) |
| --- | --- |
| Nomad | 88 → **2** |
| Mace | → **0** |
| Wraith | → **0** |
| Hawk | → 59 |

**Hawk 의 59건은 우리 탓이 아니다.** 범인은 `RUSH 100` 가방 하나인데, 좌표·회전이 프로필과
글자까지 같고 크기도 **서버 DB 가 6x7 이라고 답한다**(파일이 아니라 돌고 있는 서버에 물었다).
즉 **그 프로필의 스태시 배치가 실제로 겹쳐 있다** — 팀원 프로필은 사람이 아니라 모드가 채운
것이라 그럴 수 있다. 창은 작은 것을 위에 그려, 겹쳐도 가려져 못 누르는 일은 없다.

## 17. 설치 — 창은 설치본 루트에 둔다 (2026-11-08)

창을 `Give Ui.exe`·`AirdropCaller.exe` 와 **같은 자리**에 둔다. 도구는
**[tools/install-profileporter-app.ps1](../../tools/install-profileporter-app.ps1)** 이고,
AirdropCaller 의 같은 이름 스크립트를 본떴다.

```
E:\Spt\ProfilePorter.exe              237KB (런타임 의존 게시)
E:\Spt\profile-porter.config.json     처음 띄울 때 만들어진다
E:\Spt\icon-cache\                    **AirdropCaller 와 함께 쓴다**
```

### 17.1 선례에서 가져온 것 — **묵은 게시본을 조용히 깔지 않는다**

`dotnet build` 만 하고 `publish` 를 빠뜨리면 지난번 게시본이 그대로 복사되고 **바이트 수까지
같아** 눈치채기 어렵다. 소스가 게시본보다 새로우면 **멈춘다.** (같은 함정을 이 세션에서도
서버 쪽에서 한 번 밟았다 — §15.1.)

창이 떠 있으면 exe 가 잠겨 복사가 실패하므로 **열어 보고 멈춘다.** 그냥 두면 "설치됨" 도 안
찍히면서 exit 0 이라 깔린 줄 알게 된다.

### 17.2 선례와 **다르게** 한 것 — 아이콘 캐시를 지우지 않는다

`<SptDir>\icon-cache` 는 **AirdropCaller 와 함께 쓰는** 자리다(2026-11-08 기준 2,341개).
AirdropCaller 쪽 스크립트는 `-Remove` 에서 그것을 자기 것으로 알고 지우는데, 그쪽이 먼저
생겼기 때문이다. **ProfilePorter 는 지우지 않는다** — 여기서 치우면 남의 창이 다시 받아야 한다.

`-Remove` 는 exe 만 지우고 설정을 남긴다. `-Purge` 가 설정까지 지운다. **내보낸 파일과
백업은 서버 모드 폴더**에 있어 이 스크립트가 손대지 않는다.
