## 1. 의도

레이드 **안에 있는 동안**, 밖에 띄워 둔 창에서 보급품 내용을 고르고 버튼을 누르면,
**내 머리 위로 에어드롭 상자가 떨어진다.** 상자 안에는 내가 고른 것만 들어 있다.

지금은 `Give Ui.exe` 로 아이템을 **인벤토리에 바로 꽂는다.** 물건은 생기지만 레이드의 사건이
되지는 않는다. 이 모드는 같은 "밖에서 넣어 준다" 를 **게임 안의 사건**으로 바꾼다 — 비행기
소리, 연막, 낙하, 상자를 열어 꺼내는 과정이 그대로 남는다.

### 왜 `Give Ui` 구조를 따르는가

사용자가 그 구조를 지목했고, 이 설치본에서 이미 **증명된 구조**다.

- `E:\Spt\Give Ui.exe` + `E:\Spt\give-ui.config.json` (`sptUrl: https://127.0.0.1:6969`)
- 게임 밖의 별도 창이라 **레이드 중에 알트탭으로 쓸 수 있다.** 게임 안 UI 였다면 레이드
  중에 설정을 고치는 것이 훨씬 번거롭다.
- 외부 프로세스의 HTTP 요청을 서버가 이미 받고 있다는 뜻이다. 새로 뚫을 길이 없다.

### 왜 서버 웹 페이지(`WebConfigBridge`)가 아닌가

`WebConfigBridge` 로 `/airdrop-caller` 페이지를 만드는 쪽이 파일은 하나 적다. 하지만
사용자가 외부 실행 파일을 지목했고, 브라우저 탭보다 **항상 위에 띄워 두는 전용 창**이
레이드 중 조작에 낫다. 웹 페이지는 나중에 같은 서버 라우트를 그대로 써서 얹을 수 있다
— 라우트가 공용이므로 둘 중 하나를 버릴 필요가 없다.

## 2. 확인된 사실 (설치본 실측, 2026-10-28)

이 설계는 추측이 아니라 설치본을 뒤져 확인한 것 위에 선다.

| 확인한 것 | 근거 |
| --- | --- |
| 외부 exe 가 서버와 붙는다 | `Give Ui.exe`(11.6MB, Go+WebView2) + `give-ui.config.json` 의 `sptUrl` |
| 서드파티 모드가 **자기 HTTP 라우트**를 만든다 | `SPTarkov.Server.Core.dll` 에 `StaticRouter`·`DynamicRouter`·`RouteAction` |
| 그 라우트를 **게임 플러그인이 호출**한다 | `LogOutput.log` 의 `[REQUEST]: /moe-trade-marker/markers`, `/utae/editor/assort/<id>` |
| 서버에 에어드롭 기능이 있다 | `AirdropService`, `GetAirDropLoot`, `AirdropLootResult`, `AirdropConfig`, `AirdropTypeEnum` |
| 에어드롭 설정 파일 | `SPT_Runtime/SPT_Data/configs/airdrop.json` (`airdropTypeWeightings`, `loot.<type>` 별 품목 화이트리스트·개수) |
| 게임에 에어드롭 객체가 있다 | `Assembly-CSharp.dll` 에 `AirdropSynchronizableObject`, `AirdropManager`, `AirdropParameters`, `AirdropTrajectoryCalculator` |
| **플레어로 내 위치에 부르는 경로가 이미 있다** | `AirdropTimeByFlare`, `AirdropFlareEvent`, `AirdropFlareParameters`, `AirdropFlareSuccessEvent`, 서버 config 의 `AirdropFlareWait` |
| SPT 가 그 경로를 이미 건드린다 | `spt-custom.dll` 의 `AirdropManager`, `AirdropCrashPatch`, `AirdropFlareDisposePatch` |
| 서버→클라 푸시 수단도 있다 | `SptWebSocketConnectionHandler`, `WebSocketManager`, `notifierServer` |
| **레이드당 보급기는 1회다** | `locations/<맵>/base.json` 의 `AirdropParameters[0].PlaneAirdropMax: 1` (확률 `PlaneAirdropChance: 0.2`, 쿨다운 600~700초) |
| 플레어에서 비행기까지 30초 | `globals.json` 의 `config.Airdrop.PlaneAirdropFlareWait: 30` (`PlaneAirdropDuration: 60`) |
| 보급기가 **안 오는 맵이 있다** | `AirdropParameters` 가 비어 있는 맵: Factory(주·야), Labs, Terminal, Town, Suburbs, Hideout. 있는 맵: Customs·Interchange·Reserve·Lighthouse·Shoreline·Streets·Woods·Ground Zero·Labyrinth |

**가장 중요한 발견은 플레어다.** 바닐라에 이미 "**플레이어가 쏜 지점으로 보급기를 부른다**"
가 구현돼 있다. 우리가 만들려는 것은 그 사건을, 플레어 탄 없이, 외부 버튼으로, 내가 정한
내용물로 일으키는 것이다. **없는 기능을 새로 만드는 것이 아니라 있는 기능의 방아쇠와
내용물을 바꾸는 것**이다 — 이 설계의 난이도를 가르는 지점이다.

## 3. 목표

1. 레이드 중, 외부 창의 버튼 하나로 **내게 가장 가까운 보급 지점**에 에어드롭이 떨어진다.
   (초안은 "머리 위" 였다. 낙하 지점이 맵에 미리 박혀 있어 임의 좌표가 안 된다 — §7.4)
2. 상자 안에는 **내가 정한 품목과 수량만** 들어간다. 무작위 보급 생성기를 타지 않는다.
3. 품목 묶음을 **프리셋**으로 저장해 두고 고른다 (예: "의료", "탄약 보충", "7.62 풀세트").
4. 외부 창에서 **한국어 아이템 이름으로 검색**해 프리셋을 짠다.
5. 레이드 밖에서 버튼을 누르면 **조용히 거절**하고 왜 안 되는지 알려 준다.
6. **플레어 탄은 평소대로 바닐라 보급을 부른다.** 우리 드롭과 공존한다 — 플레어를 내 프리셋으로
   바꾸는 것은 **토글로만** 되고 기본은 꺼짐 (§7.14, 사용자 결정).

## 4. 비목표

- 봇·다른 플레이어에게 보이는 멀티플레이 동기화 (SPT 싱글이다. Fika 는 쓰지 않는다)
- 바닐라 에어드롭의 **설정·확률·내용물 변경.** `airdrop.json` 과 바닐라 보급기의 전리품
  생성은 건드리지 않는다.
  (단 §7.4 경로 1 을 타면 **그 레이드의 보급기 예산은 우리 드롭이 쓴다** — §7.10 에서 정했다.
  "별개로 하나 더 온다" 가 아니다)
- 보급 상자 모델·연출 신규 제작. 바닐라 에셋만 쓴다
- 레이드 기록·통계·업적 연동
- 서버 웹 페이지 UI (라우트는 공용으로 두되 이번에 페이지는 만들지 않는다)

## 5. 안티목표 — 이것이 일어나면 실패다

1. **프로필이 깨진다.** 넣은 아이템이 프로필에 반쯤 쓰여 레이드 종료 시 저장이 터지는 것.
   이 설치본은 결속 모드가 여럿이라 프로필 사고의 대가가 크다.
2. **바닐라 에어드롭이 망가진다.** 우리 패치 때문에 평소 보급기가 안 오거나 두 번 오는 것.
3. **레이드가 튕긴다.** 특히 `AirdropSynchronizableObject` 를 잘못된 상태로 만들어
   `AirdropCrashPatch` 가 막던 바로 그 crash 를 되살리는 것.
4. **게임이 꺼져 있을 때 외부 창이 서버를 괴롭힌다.** 1초 폴링이 서버 로그를 덮어 진짜
   오류를 묻어 버리는 것 — 이 설치본은 이미 `Could not add` 48건으로 로그가 시끄럽다.
5. 설치 기록에 안 남는 파일이 생겨 나중에 제거가 지저분해지는 것.

- 서버 모드: **net10.0**, `SPTarkov.Server.Core`·`SPTarkov.Common`·`SPTarkov.DI` 참조,

- 설치·제거 후 `node tools/gen-installed-mods.mjs` 로 `doc/INSTALLED-MODS.md` 재생성.
- **Forge 모드가 아니므로 설치 기록에 안 잡힌다.** `INSTALLED-MODS.md` 에 손으로 올리는
  대신 **생성기(`tools/gen-installed-mods.mjs`)에 추가**한다 — 그 파일은 직접 고치지 않는다.
- 결속 아님. 프로필에 우리 흔적을 남기지 않는다 (§7.6).
- 게임·서버 모두 **한국어**가 기본. 외부 창 UI 도 한국어.

## 7. 결정된 사항

### 7.1 세 조각

| 조각 | 종류 | 설치 위치 | 역할 |
| --- | --- | --- | --- |
| `AirdropCaller.Server` | SPT 서버 모드 (net10.0) | `SPT_Runtime\user\mods\AirdropCaller\` | 라우트, 프리셋 저장, 아이템 조립, 대기열 |
| `AirdropCaller.Plugin` | BepInEx 플러그인 (net472) | `BepInEx\plugins\AirdropCaller\` | 레이드 상태 보고, 대기열 폴링, 드롭 실행 |
| `AirdropCaller.App` | 외부 실행 파일 | `E:\Spt\AirdropCaller.exe` + `airdrop-caller.config.json` | 프리셋 편집, 드롭 버튼 |

**서버가 가운데에 있다.** 외부 exe 는 플러그인과 직접 말하지 않는다. 게임이 HTTP 서버를
열지 않으므로 그럴 수도 없고, 서버를 거치면 게임이 꺼져 있어도 프리셋 편집이 된다.

```
AirdropCaller.exe  ──HTTP──▶  서버 모드  ◀──HTTP──  BepInEx 플러그인
   (프리셋 편집)                (대기열)              (폴링 → 드롭 실행)
   (드롭 버튼)                  (조립)                (레이드 상태 보고)
```

### 7.2 서버 라우트

`StaticRouter` 로 `/airdrop-caller/*` 아래에 붙인다 — `Moe-TradeMarker` 가
`/moe-trade-marker/*` 로 하는 것과 같은 방식.

| 메서드·경로 | 쓰는 쪽 | 하는 일 |
| --- | --- | --- |
| `GET /airdrop-caller/state` | exe | 게임이 붙어 있나, 레이드 중인가, 맵은 어디인가, 대기열에 몇 개 |
| `GET /airdrop-caller/items?q=&limit=` | exe | 아이템 검색. **한국어 이름**(`locales/global/kr.json` — 이 설치본의 파일 이름은 `ko` 가 아니라 `kr` 이다)으로 찾아 tpl·이름·크기·기본 스택을 돌려준다 |
| `GET /airdrop-caller/presets` | exe | 프리셋 목록 |
| `PUT /airdrop-caller/presets/<id>` | exe | 프리셋 저장 |
| `DELETE /airdrop-caller/presets/<id>` | exe | 프리셋 삭제 |
| `POST /airdrop-caller/queue` | exe | **드롭 1회 예약.** 본문은 프리셋 id 또는 품목 목록 + 옵션 |
| `POST /airdrop-caller/heartbeat` | 플러그인 | 레이드 상태·맵·경과 시간 보고 (2초마다) |
| `GET /airdrop-caller/pending` | 플러그인 | **대기 중인 드롭을 꺼내 간다(pop).** 없으면 빈 응답. 돌려주는 것은 `{ dropId }` 뿐 — 좌표는 플러그인이 플레이어에서 읽고, **아이템 트리는 담지 않는다** (§7.5) |
| `POST /client/airdrop/loot` | **게임(바닐라)** | 우리 라우트가 아니라 **바닐라 라우트**다. 우리 `dropId` 면 우리가 답하고, 아니면 바닐라가 답한다 (§7.5) |
| `POST /airdrop-caller/cancel` | exe | 아직 안 꺼내 간 예약을 취소 |

`pending` 은 **꺼내면 사라진다.** 플러그인이 한 번 받으면 서버 대기열에서 지운다 — 응답을
못 받았을 때 두 번 떨어지는 것보다 한 번 안 떨어지는 쪽이 낫다 (§5 안티목표 2).

### 7.3 폴링. 웹소켓이 아니다

플러그인은 **레이드 중에만** `GET /pending` 을 **1초**마다 친다. 레이드 밖에서는 멈춘다.

- 서버에 `SptWebSocketConnectionHandler` 가 있어 푸시도 된다. 하지만 **모드가 끼어드는
  방법이 검증되지 않았고**, 폴링은 이 설치본에서 `Moe-TradeMarker` 가 이미 하고 있는
  선례가 있다.
- 1초 지연은 "버튼 누르고 하늘을 본다" 에 충분하다.
- 서버 로그를 덮지 않도록 **`pending` 라우트는 로그를 남기지 않는다** (§5 안티목표 4).
  `SptLoggerMiddleware` 가 찍는다면 그 경로만 빼는 길을 찾고, 없으면 주기를 2초로 늘린다.
- 웹소켓은 **나중에 바꿔도 되는 결정**이다. 라우트 모양은 그대로 두고 전송만 갈아 끼운다.

### 7.4 드롭 실행 — 공개 메서드 하나다 (2026-10-29 조사로 확정)

~~경로 1·2·3 중 무엇으로 될지 구현자가 찾는다~~ → **찾았다. 사다리는 필요 없다.**
근거는 [조사 문서 §1](2026-10-29-airdrop-stage1-findings.md) 에 있다.

```csharp
// EFT.ClientGameWorld — public, virtual. Harmony 패치도 리플렉션도 필요 없다
InitAirdrop(string lootTemplateId, bool takeNearbyPoint, Vector3 position)
```

바닐라의 플레어 갈래와 시간 기반 갈래가 **둘 다 이 메서드로 모인다.** 우리는 같은 메서드를
직접 부른다.

```csharp
clientGameWorld.InitAirdrop(ourDropId, takeNearbyPoint: true, playerPosition);
```

- 연출·소리·비행기·낙하산·상자 생성은 **전부 바닐라가 한다.**
- `lootTemplateId` 가 상자 생성 때 서버로 올라간다 → 내용물도 이 한 인자로 정해진다 (§7.5).
- **비행기 자리(`PlaneAirdropMax`)를 먹지 않는다.** 카운터·타이머 증가는 `ManualUpdate`
  안에서 일어나고 `InitAirdrop` 자신은 건드리지 않는다 → 플레어와 **완전히 공존**한다
  (§7.10, §7.14).

#### 낙하 지점은 "머리 위" 가 아니다 — 약속을 고친다

```csharp
// AirdropManager.Init
_airdropPoints = LocationScene.GetAll<AirdropPoint>().ToList();
// AirdropManager.TakeAirdropPoint(takeNearbyPoint: true, position)
//   → position 에서 가장 가까운 점을 고른다. 쓰면 목록에서 빠지고, 50m 안의 점들도 비활성
```

낙하 지점은 **맵에 미리 박힌 `AirdropPoint` 중 하나**다. 임의 좌표에 떨어뜨리는 길은 없다.

| 초안의 약속 | 실제 |
| --- | --- |
| 내 **머리 위**에 떨어진다 | 내게 **가장 가까운 보급 지점**에 떨어진다 |
| 수평 오프셋 15m 를 우리가 정한다 | 오프셋 개념이 없다. 지점은 맵이 정한다 |
| 실내·지하면 거부한다 (§7.12) | 거부가 아니라 **바깥 어딘가**에 떨어진다 |

**쟀다 (2026-10-29, Customs).** 지점 **608개**, 가장 가까운 것이 **9~13m** 다. 상자가 보이는
거리고 걸어서 몇 초다 — **"머리 위" 라는 약속이 사실상 지켜진다.** 걱정했던 "300m 면 다른
물건" 은 해당되지 않았다. 다른 맵은 아직 안 쟀다.

한 가지 딸려 온 성질: `AirdropPointDeactivateDistance: 50` 이라 **한 번 쓰면 50m 안의
지점이 통째로 비활성**된다(Customs 기준 11~13개). 그래서 연달아 부르면
**9m → 52m → …** 으로 멀어진다. 막을 필요 없이 바닐라가 이미 그렇게 만들어 놨다 (§7.10).

그래도 exe 는 "떨어뜨렸다" 가 아니라 **떨어진 자리까지의 거리·방향**을 알려 준다 (§7.7) —
9m 든 52m 든 어느 쪽인지는 알아야 한다.

### 7.5 내용물 — 서버가 조립하고, **바닐라의 보급 전리품 요청에 답한다**

무작위 생성기(`AirdropService` 의 loot 생성)를 **타지 않는다.** 내가 정한 것만 들어가야 한다.

**어디서 끼어드는가** — 이것이 조각 나누기를 가르는 결정이므로 못박아 둔다.

바닐라는 **상자가 생길 때 클라이언트가 서버에 그 상자의 전리품을 물어본다**
(`GetAirdropLootRequest` / `GetAirdropLootResponse` / `GetAirDropLoot`). 우리는 **그 요청에
답하는 쪽**으로 끼어든다.

1. exe 가 `POST /queue` → 서버가 프리셋을 `Item[]` 로 조립해 `dropId` 와 함께 들고 있는다.
2. 플러그인이 `GET /pending` 으로 `{ dropId, position }` 만 받아 **드롭을 일으킨다**.
3. 상자가 생겨 클라이언트가 전리품을 물어보면, 우리 서버 모드가 **그 상자가 우리 것인지
   확인하고** 1번에서 조립해 둔 트리를 돌려준다.
4. **우리 것이 아닌 상자는 손대지 않는다.** 바닐라 생성기가 그대로 답한다 (§4 비목표).

**클라이언트에서 아이템을 만들지 않는다.** 그쪽은 (ㄱ)아이템 DB·로케일·스택 규칙을
net472 쪽에 또 들고 있어야 하고, (ㄴ)**서버가 발행하지 않은 `_id`·`upd` 를 레이드 종료 시
서버가 받아 줄지 알 수 없다.** (ㄴ)이 §5 안티목표 1 과 정면으로 부딪힌다. 서버가 발행하면
그 위험 자체가 없다 — §7.6 의 "바닐라 전리품과 똑같은 경로" 는 **이 경로에서만** 성립한다.

**"우리 상자인지" 는 풀렸다** (2026-10-29 조사). 알아볼 방법을 찾을 필요가 없다 —
**우리가 이름을 붙여 보낸다.**

```
exe → 서버: 드롭 예약          서버가 dropId 를 발급하고 Item[] 를 조립해 쥔다
서버 → 플러그인: { dropId }     GET /pending
플러그인 → 게임: InitAirdrop(dropId, true, playerPos)
게임 → 서버: POST /client/airdrop/loot { containerId: dropId }   ← 같은 값이 돌아온다
서버 → 게임: { icon, container: FlatItem[] }                      ← 우리가 조립한 것
```

바닐라도 **이미 `containerId` 로 전리품을 가른다.** 플레어 탄의
`AmmoTemplate.AirDropTemplateId` 가 그 값이고, `airdrop.json` 의 `customAirdropMapping`
(`66da1b49099cf6adcc07a36b`·`66da1b546916142b3b022777` → `radar`)이 그 표다. 우리는
**그 표에 없는 값**을 쓰고, 그 값에 대해 **우리가 먼저 답한다.** 우리 것이 아닌 값은
바닐라가 그대로 답한다 (§4).

`airdrop.json` 자체는 고치지 않는다. 우리 매핑은 서버 모드가 메모리에서 쥔다.

조립 규칙:

- 프리셋은 `{ tpl, count, stackSize? }` 의 목록이다.
- 서버가 **아이템 트리**(`Item[]`, `_id`·`_tpl`·`parentId`·`slotId`·`location`)로 조립한다.
  컨테이너는 바닐라 에어드롭 상자 tpl 을 쓴다.
- **격자에 안 들어가면 넣지 않고 거절한다.** 배치는 서버가 계산하고, 넘치면 `POST /queue`
  응답에 "N개가 안 들어갔다" 를 담아 exe 가 보여 준다. 조용히 버리지 않는다.
  **못 담은 것(`skipped`)과 고친 것(`adjusted`)은 따로 센다** — 한데 묶었더니 창이
  "못 담은 것 1개" 라면서 정작 상자에는 들어 있는 꼴이 됐다(2026-10-29 실측).
  같은 말이 여러 줄이면 `… ×14` 로 묶는다. 방탄복 20개를 넣었더니 "자리 없음" 이
  열네 줄로 돌아왔다.
- 탄약 등 스택 품목은 `upd.StackObjectsCount` 로 묶는다. **최대 스택은 런타임에 아이템 DB
  에서 읽고, 넘으면 거기까지만 받는다** — `OnLoadOrder.PostLoad` 이후, 즉 스택을 쓰는 서버
  모드 13개가 전부 지나간 뒤의 값이다. 이 설치본에서 루블은 `items.json` 에 1,000,000 으로
  적혀 있는데 **서버가 들고 있는 값은 50,000,000** 이었다(2026-10-29 실측). 파일을 보고
  판단했으면 틀렸을 자리다. 깎으면 `adjusted` 로 말해 준다 — 조용히 고치지 않는다. `src/StackUnify/config.jsonc` 를 보지 않는다: 그 파일은 **지금 비어 있고**
  (`StackByCaliber: {}`), 실제 값은 `BarterItemsStacks` 등 다른 모드가 쥐고 있다. DB 가
  유일한 진실이다.
- `_id` 는 드롭마다 새로 만든다 (MongoId 형식). 재사용하지 않는다.
- 테스트(`AirdropCaller.Tests`)는 **가짜 DB 를 주입**해 격자 배치와 스택 분할을 검증한다.
  DB 를 읽는다고 해서 게임 없이 못 볼 이유는 없다 — 읽는 경로를 인터페이스로 끊어 둔다.

#### 상자 종류(`icon`)는 겉모습뿐이다 — 용량을 늘리지 못한다 (2026-10-29 조사로 확정)

위 응답의 `icon` 이 창의 "상자" 드롭다운(`Common`·`Supply`·`Medical`·`Weapon`)이다.
**용량을 고르는 값이 아니다.** 바꾸는 것은 둘뿐이다.

**(ㄱ) 상자 겉면의 마크.** 클라이언트가 문자열을 그대로 받아 데칼 재질을 갈아 끼운다
(`ServerAirdropManager.InitContainerLoot` → `ClientAirDrop.UpdateContainerType`).

```csharp
Enum.TryParse<EAirdropType>(value.Icon, ignoreCase: true, out var result);
container.AirdropType = result;
...
case EAirdropType.Common:  SwitchAirdropContainerDecals(_syncObject, null);               // 민짜
case EAirdropType.Supply:  SwitchAirdropContainerDecals(_syncObject, _syncObject.SupplyDecal);
case EAirdropType.Medical: SwitchAirdropContainerDecals(_syncObject, _syncObject.MedicineDecal);
case EAirdropType.Weapon:  SwitchAirdropContainerDecals(_syncObject, _syncObject.GunDecal);
```

떨어지는 동안에도 보이므로 멀리서 어느 상자인지 가늠하는 쓸모가 있다.

**(ㄴ) 루팅 창 제목.** `CrateBuilder.CrateTemplateFor` 가 고르는 루트 템플릿의 이름을
게임이 그대로 쓴다(`LootItem.CreateLootContainer(…, item.ShortName.Localized(), …)`).

**용량은 넷이 똑같다.** 아이템 DB 에서 직접 떠서 확인했다.

| `icon` | 루트 tpl | 이름 | 격자 |
|---|---|---|---|
| Common | `6223349b3136504a544d1608` | `air_drop_common` | 10×12 = 120칸 |
| Supply | `622334fa3136504a544d160c` | `air_drop_supply` | 10×12 = 120칸 |
| Medical | `622334c873090231d904a9fc` | `air_drop_medical` | 10×12 = 120칸 |
| Weapon | `6223351bb5d97a7b2c635ca7` | `air_drop_weapon` | 10×12 = 120칸 |

그래서 `Weapon` 으로 둔다고 무기가 더 들어가지 않는다. 120칸을 넘기는 길은 둘이다 —
§7.5 의 **중첩**(격자를 가진 품목 안에 담기)과, 아래의 **큰 상자**.

로케일도 네 이름 모두 영어 그대로다(`kr.json` 에 번역이 없다). 창에서 한국어로
보이게 하려면 우리가 이름을 들고 있어야 한다 — 지금은 하지 않는다.

모르는 문자열은 여기까지 오지 않는다. `CrateBuilder` 가 먼저 `Enum.TryParse` 로 걸러
`상자 종류 '…' 을 모른다.` 로 거절한다. 게임 쪽 `TryParse` 는 실패해도 조용히
`default`(= `Common`)로 넘어가므로, 거르는 자리를 서버에 둔 것이 맞다.

#### 큰 상자 — 베껴서 **우리 것만** 키운다 (2026-10-30)

상자 크기를 정하는 것은 `icon` 이 아니라 **루트 아이템의 tpl** 이다. 조립기는 120을
어디에도 박아 두지 않았다 — `itemHelper.GetContainerMapping(tpl)` 로 DB 에서 격자를
읽는다. 그래서 tpl 만 바꾸면 상자가 커진다.

바닐라 상자 넷의 격자를 키우는 길도 있지만 **그렇게 하지 않는다.** 우리가 부르지 않은
보급, 플레어로 부른 보급, 맵에 원래 떨어지는 보급까지 전부 커진다. §5 안티목표 2
("끄면 바닐라와 구별되지 않는다")에 바로 걸린다.

대신 `air_drop_common` 을 **깊게 베껴** 격자만 30×30 = 900칸으로 바꾼 아이템을 서버가
켜질 때 DB 에 하나 집어넣는다(`BigCrate`). 깊게 베끼는 것이 중요하다 — 얕게 베끼면
`Grids` 가 같은 객체라 바닐라 상자까지 함께 커진다.

게임이 이 아이템을 알아야 한다. `GET /client/items` 가 `templateTable.Items` 를
**그때그때 그대로 흘려보내므로**(`DataCallbacks.GetTemplateItems`, 캐시 없음) 서버
시작 때 넣어 두면 게임이 받아 간다.

**넣는 자리는 `OnLoadOrder.Preload` 여야 한다.** 다른 라우트처럼 `PostLoad` 에 뒀다가
서버를 못 켰다 — 4.1.6 의 `DatabaseIntegrityService` 가 프로필을 읽은 뒤에 늘어난
아이템을 찾아내 서버를 통째로 멈춰 세운다.

```
DatabaseModifiedAfterCutoffException: 1 item(s) were added to the database
after profiles loaded: a1d0caffe0000000000c0de1. Add items during
OnLoadOrder.Preload, the database is fully loaded by then …
```

메시지가 할 일을 그대로 적어 준다. `Preload` 에도 DB 는 이미 다 올라와 있다.

tpl 은 `a1d0caffe0000000000c0de1` 로 고정했다. MongoId 는 24자리 16진수여야 해서
아무 글자나 쓸 수 없다.

겉모습과 창 제목은 그대로 `icon` 이 정한다. 커지는 것은 안 격자뿐이다.

**못 만들었으면 거절한다.** 작은 상자로 조용히 내려보내면, 900칸을 믿고 적어 둔
품목이 "자리 없음" 으로 쏟아진다 — 조용히 버리지 않는다는 약속(§7.5)과 같은 이유다.

이름(로케일)은 붙여 보고 **붙었는지 확인해서 로그에 적는다.** 로케일은 `LazyLoad`
뒤에 있어 `GetLocaleDb` 가 돌려주는 것이 살아 있는 표인지 베낀 것인지 밖에서는
알 수 없다. 이름이 없어도 상자는 열린다(창 제목은 상자 종류에서 온다).

#### 방어구는 비워서 보내지 않는다 (2026-10-30)

조립기는 품목마다 아이템을 하나 만들고 끝냈다. 딸린 칸(`Slots`)은 쳐다보지도 않았다.
그래서 방탄복을 넣으면 **삽입물이 하나도 없는 껍데기**가 갔다. 게임에서 그 방탄복은
보호력이 0이다. 적어 낸 사람이 바란 물건이 아니다.

DB 에서 뜬 IOTV Gen4(완전형)의 칸은 이렇게 생겼다.

| 칸 | `_required` | 후보 | 비고 |
|---|---|---|---|
| `Soft_armor_front` 외 8개 | `true` | 1개 (아라미드 삽입물) | 없으면 보호력 0 |
| `Front_plate` · `Back_plate` | `false` | 18개 | 방어 3~6등급이 섞여 있다 |
| `Left_side_plate` · `Right_side_plate` | `false` | 2개 | |

품목마다 `Fill` 을 둔다. 비우면 `Auto`.

- **`Auto`** — 방어구(헤드기어·바디아머·택티컬 리그)에만 손대어 삽입물과 방어판을
  채운다. 무기 따위는 건드리지 않는다.
- **`All`** — 모든 칸을 채운다. 헬멧이면 야시경·마운트·바이저까지.
- **`None`** — 빈 몸으로 둔다.

##### SPT 의 `AddChildSlotItems` 를 쓰지 않은 이유

SPT 에도 같은 일을 하는 `ItemHelper.AddChildSlotItems` 가 있다. 쓰지 않았다 —
**후보 중에서 무작위로** 고르기 때문이다(`GetCompatibleTplFromArray` →
`randomUtil.GetArrayValue`). 방탄복 열 벌을 넣으면 방어 등급이 3에서 6까지 제각각
나오고, 같은 프리셋을 두 번 불러도 다른 것이 나온다. 부르는 쪽이 고른 물건을 서버가
주사위로 바꿔 버리는 셈이다.

고르는 규칙을 우리가 쥔다 — **핸드북 값이 가장 비싼 것.** 값이 같으면 tpl 순서로
끊는다(같은 프리셋은 두 번 불러도 같아야 한다). 이 설치본의 DB 로 재 보니 이 한 줄이
세 자리 모두 바라는 답을 냈다.

| 칸 | 후보 | 고른 것 |
|---|---|---|
| IOTV `Front_plate` | 18개 | GAC 4sss2 (85,002원, 방어 6등급) |
| FAST MT `mod_nvg` | 3개 | GPNVG-18 (145,004원) |
| FAST MT `mod_equipment_000` | 3개 | 멀티 히트 안면 보호 바이저 (39,961원) |

**방어 등급을 먼저 보는 규칙은 틀렸다.** `mod_nvg` 후보 중 Tac-Kek 마스크만 등급(2)을
들고 있어서, 야시경 대신 마스크가 뽑힌다. 값만 보는 쪽이 맞았다.

##### 걸려 넘어진 것 두 가지

**같은 것을 두 번 달지 않기 — 를 반드시 있어야 하는 칸에 적용하면 안 된다.** 아라미드
삽입물 하나가 깃·어깨·사타구니에 똑같이 들어간다. 중복을 막으면 첫 칸만 채워진다.
그래서 `_required` 가 아닌 칸에만 중복을 막는다.

**크기는 붙인 뒤에 잰다.** 개머리판을 단 총은 빈 총보다 넓다(`GetItemSize` 는 자식까지
받아야 제값을 낸다). 빈 몸으로 재 놓고 채워 넣으면 격자 지도가 실제와 어긋난다.

**담은 것과 붙은 것을 따로 센다.** 예전처럼 `items.Count - 1` 로 세면 방어판까지 품목
수에 섞여, 30개를 담았는데 창이 78개라고 말한다.

### 7.6 프로필에 쓰지 않는다

**우리 모드는 프로필을 건드리지 않는다.** 상자는 레이드 안의 월드 오브젝트로 생기고,
플레이어가 꺼내 가방에 넣는 순간부터는 **바닐라 레이드 전리품과 똑같은 경로**를 탄다.
레이드를 살아서 나와야 남는다.

- §5 안티목표 1 을 막는 가장 확실한 방법이다.
- 오늘 문서에 적은 "지운 모드가 프로필에 남긴 유령 상인" 같은 잔류물이 **원리적으로 안 생긴다.**
- 부작용: **죽으면 잃는다.** 그것이 맞다 — 보급을 "사건" 으로 만드는 것이 이 모드의 의도다.
  인벤토리에 바로 꽂고 싶으면 `Give Ui` 가 이미 있다.

### 7.7 외부 실행 파일

- **WPF, .NET 10, 단일 파일 자체 포함 게시** (`PublishSingleFile` + `--self-contained`).
  `Give Ui` 는 Go+WebView2 지만 이 저장소는 이미 C#/.NET 체인을 갖추고 있다. 새 언어를
  들이지 않는다.
- `E:\Spt\AirdropCaller.exe`, 설정은 `E:\Spt\airdrop-caller.config.json`
  (`sptUrl`, `pollSeconds`, `dropOffsetMeters`, `alwaysOnTop`) — `give-ui.config.json` 과
  같은 자리·같은 모양.
- **자체 서명 인증서**를 받아들여야 한다. 서버는 `https://127.0.0.1:6969` 에서 자체 서명
  인증서를 쓴다 (`Loaded self-signed certificate`). `127.0.0.1` 에 한해 검증을 건너뛴다.
- 화면 세 칸: ①프리셋 목록 ②고른 프리셋의 품목 편집(한국어 검색 → 추가, 수량 조정)
  ③상태줄 + **드롭 버튼**. 상태줄은 `GET /state` 를 2초마다 받아 "레이드 중 (Customs,
  12:3x)" / "레이드 아님" / "게임 안 켜짐" 을 보여 준다.
- **레이드가 아니면 드롭 버튼이 꺼진다.** 눌러도 되게 두고 서버가 거절하는 것보다 낫다.
- 항상 위(`Topmost`) 기본 켜짐. 알트탭 대신 창을 띄워 둔 채 쓴다.

### 7.9 단계

1. **1단계 — 길이 뚫리는지만 본다.** 서버 라우트 `GET /pending` 하나, 플러그인이 폴링해
   로그만 찍기, exe 없이 `curl` 로 밀어 넣기. 여기서 §7.4 의 1→2→3 을 시험해 **빈 상자라도
   떨어지는지** 확인한다. 안 떨어지면 나머지는 의미가 없다.
2. ~~**2단계 — 내용물.**~~ → **통과.** 서버 모드가 바닐라 전리품 라우트에 뒤에서 끼어들어
   우리 상자에만 우리 내용물로 답한다 ([2단계 결과](2026-10-29-airdrop-stage2-result.md)).
   프리셋 저장과 격자 배치 테스트는 아직 — 지금은 `config.jsonc` 를 손으로 고친다.
3. **3단계 — 외부 창.** WPF, 한국어 검색, 드롭 버튼. 대기열 라우트(`POST /queue`·
   `GET /pending`)도 여기서 붙는다 — 2단계는 측정기가 id 를 직접 넘기는 것으로 때웠다.
4. **4단계 — 다듬기.** 레이드 상태 표시, 거절 메시지, F12 설정, 설치 스크립트, 문서.

**1단계에서 막히면 멈추고 보고한다.** §10-1 의 약한 대안(레이드 시작 때 미리 정한 좌표에
예약)을 **묻지 않고 만들지 않는다.** 그것은 이 모드의 의도("지금 내 위에")가 아니라 다른
물건이고, 만들 가치가 있는지는 사용자가 정할 일이다. 2~4단계를 먼저 만들어 두고 1단계에서
좌절하는 것이 가장 아까운 진행이므로, **1단계는 2~4단계와 병행하지 않고 먼저 끝낸다.**

**1단계 합격 기준** — 아래를 모두 만족해야 통과다.

| 결과 | 판정 |
| --- | --- |
| 야외에서 상자가 떨어지고 열린다 | **합격** |
| 비행기 소리·연막·낙하에 바닐라만큼 시간이 걸린다 (`AirdropFlareWait` 수준) | **합격.** 즉시 떨어지는 것이 목표가 아니다 |
| ~~그 상자를 우리 것으로 식별할 수 있다~~ | **확인됨** (조사, §7.5). 더 볼 것 없다 |
| ~~비행기 자리를 먹는지 측정했다~~ | **확인됨** (조사, §7.10). 안 먹는다 |
| ~~보급 지점 개수·거리를 로그로 찍었다~~ | **쟀다.** Customs 608개, 가장 가까운 것 9~13m (§10-9) |
| 실내·지하에서 **바깥 지점에 떨어지고 거리를 알려 준다** | **합격** (거부가 아니다 — §7.12 를 고쳤다) |
| 실내·지하에서 지형에 박힌다 | **불합격.** 지점은 지면보다 +0.7~2.9m 위라 원래 안 박혀야 한다 |
| 레이드가 튕긴다 | **불합격.** 경로를 바꾼다 (§7.4 의 다음 번호) |

### 7.10 비행기 자리를 안 먹는다 (2026-10-29 조사로 확정). 한 번에 하나만

~~경로 1·2 를 타면 자리를 쓴다~~ → **안 쓴다.** `_currentAirdropsCount += 1f` 와
`UpdateAirdropTimers(...)` 는 `ManualUpdate` 안에서 일어나고, 우리가 부르는 `InitAirdrop`
자신은 카운터도 타이머도 건드리지 않는다
([조사 문서 §3](2026-10-29-airdrop-stage1-findings.md)).

- 바닐라 예산(`PlaneAirdropMax: 1`)을 소모하지 않는다.
- 플레어 쿨다운(`_nextAirdropTimeByFlare`)을 밀지 않는다.
- **플레어와 우리 드롭이 한 레이드에서 둘 다 된다** (§7.14 의 걸림돌 둘이 사라졌다).
- 설정은 여전히 **고치지 않는다.** 고칠 이유가 없어졌다.

대신 **보급 지점**이 소모된다. 쓴 지점은 목록에서 빠지고 50m 안의 지점도 비활성되며, 다
쓰면 되살아난다. 그래서 **같은 자리에 연달아는 안 온다.**

**대기열은 한 칸이다.**

- 이미 예약이 있거나 **상자가 공중에 있으면** `POST /queue` 를 거절한다. 플러그인이
  heartbeat 에 "상자 비행 중" 을 함께 보고한다.
- 착지 뒤 **쿨다운 30초** (설정 가능). 레이드당 총 횟수 제한은 두지 않는다 — 치트 방지가
  목적이 아니다. 막는 것은 §5 안티목표 2·3 으로 이어지는 **동시 드롭**뿐이다.
- exe 의 드롭 버튼은 비행 중·쿨다운 중에도 꺼진다. 이유를 상태줄에 쓴다.

### 7.11 대기열 수명과 프로필

- **레이드가 끝나면(탈출·사망·연결 종료) 대기열을 비운다.** 안 꺼내 간 예약이 다음 레이드에
  떨어지는 것은 놀라운 일이고 §5 안티목표 2 쪽이다. 플러그인의 heartbeat 가 끊기면
  **15초 뒤 서버가 대기열을 비운다**(게임이 꺼진 경우도 같이 걸린다).
- **프리셋과 대기열은 프로필 id 로 키를 둔다.** **(프리셋은 2026-11-06 에 뒤집혔다 — §17 을 본다. 전역이 된다. 대기열은 그대로 프로필 키다.)** 프로필 하나를 가정하지 않는다 — 비용이
  거의 없고, 나중에 프로필을 늘렸을 때 설계를 다시 보지 않아도 된다.
  프리셋 파일은 `presets/<profileId>/<id>.json`.
- exe 에는 **"예약 취소"** 가 있다(`POST /cancel`). 이미 떨어지는 상자는 취소하지 않는다 —
  바닐라 연출 중간에 끼어들 생각을 하지 않는다.

### 7.12 "레이드 중" 의 정의와 거절

상태는 네 가지다: **게임 안 켜짐 / 레이드 아님 / 레이드 중(드롭 가능) / 레이드 중이지만
불가**. 넷째를 쓰는 이유는 **아무 일도 안 일어나면 왜 안 됐는지 모르기 때문**이다.

| 상황 | 판정 |
| --- | --- |
| PMC 레이드 | 가능 |
| **스캐브 레이드** | **가능.** 레이드는 레이드다 |
| 맵 전환(transit) 중 | 불가 |
| 바닐라가 보급을 안 하는 맵 | **불가.** 그 맵의 `AirdropParameters` 가 비어 있으면 거절한다. 실측으로 **Factory(주·야)·Labs·Terminal·Town·Suburbs** 가 그렇다 |
| 완전 실내·지하 | ~~불가~~ → **가능하다. 바깥 지점에 떨어진다** (§7.4). 거부할 일이 아니라 **거리를 알려 줄** 일이다 |

- 가능한 맵 판정은 **하드코딩하지 않는다.** 그 레이드의 `AirdropParameters`·에어드롭 포인트
  유무를 플러그인이 보고 heartbeat 에 담는다. 맵 목록을 적어 두면 모드가 맵을 추가할 때
  틀린다 (이 설치본은 WTT·ISB 계열이 콘텐츠를 넣는다).
- 거절 사유는 **문장으로** exe 상태줄에 뜬다. "불가" 만 띄우지 않는다.

### 7.13 인증 — 면제하지 않는다

§10-4 에서 "커스텀 라우트가 세션 헤더를 요구하는지" 는 1단계에서 밝힌다. **요구할 경우의
분기를 여기서 정한다.**

- **`/airdrop-caller/*` 를 인증에서 빼지 않는다.** 전리품을 생성하는 라우트다. 이 설치본의
  서버는 웹 인증이 켜져 있고, 그 결정을 우리가 뒤집지 않는다.
- exe 는 세션을 **런처 상태 또는 `SPT_Runtime\user\profiles` 에서 읽어** 쓴다. 그것으로
  안 되면 `Give Ui` 가 하는 로그인 왕복을 따른다 — `Give Ui` 가 되고 있으므로 길은 있다.
- **exe 가 세션을 못 얻으면 프리셋 편집까지 전부 막힌다.** 그 경우 상태줄에 "서버에 붙지
  못했다" 를 띄우고, 설정 파일에 세션을 적어 넣는 수동 경로를 둔다.

### 7.14 플레어와의 공존 — 방아쇠와 내용물은 별개 축이다 (사용자 결정)

이것은 **사용자가 정했다.** 설계 초안이 두 축을 섞어 두는 실수를 했고, 질문을 받아 갈랐다.

| | 플레어 탄 | 외부 버튼 |
| --- | --- | --- |
| **바닐라 무작위** | **기본.** 손대지 않는다 | 쓰지 않는다 |
| **내 프리셋** | 토글을 켤 때만 | **기본.** 이 모드의 목적 |

#### 결정: 둘 다 쓸 수 있다. 플레어는 기본적으로 손대지 않는다

- 플레어로 온 보급은 **평소대로 바닐라 무작위**다.
- 외부 버튼으로 부른 보급만 **내 프리셋**이다.
- F12 토글 **`HijackFlareDrops`(기본 꺼짐)** 를 켜면 플레어로 부른 보급도 내 프리셋을 받는다.

**가로채지 않는 것이 공짜로 기본값이 된다.** §7.5 의 식별이 "우리가 예약했는가" 로 되어
있으므로, 플레어로 온 상자는 우리가 예약한 것이 아니니 자동으로 바닐라 전리품을 받는다.
가로채지 않기 위해 코드를 더 쓸 일이 없다. 토글은 그 판정에 "또는 플레어 드롭이고 토글이
켜져 있다" 를 **더하는** 것이다.

#### 왜 "플레어 가로채기 전용" 으로 하지 않았나

1. **그러면 외부 exe 가 필요 없어진다.** 쏘면 내 프리셋이 온다면 레이드 중에 밖에서 버튼을
   누를 이유가 없다. 미리 프리셋만 정해 두면 된다. 사용자가 지목한 구조(§1)가 통째로
   무의미해지고, **다른 물건이 된다.**
2. **플레어 탄은 게임 안에서 번 자원이다.** 그걸 쏘면 바닐라 보급이 오는 것이 플레이의
   일부인데, 내 프리셋으로 바꾸면 플레어를 쏘는 의미가 사라진다. §5 안티목표 2.

#### 공존의 걸림돌 두 개

**하나 — 식별이 안 되면 공존이 불가능하다.** 플레어로 온 상자와 버튼으로 온 상자를 구분할
수 없으면 **둘 다 내 프리셋을 받거나 둘 다 바닐라를 받는다.** 선택의 여지가 없어져 사실상
"가로채기 전용" 이 강요된다. §7.9 1단계 합격 조건의 "우리 것으로 식별할 수 있다" 가 바로
이 요구를 지키기 위한 것이다. 첫 단서는 `customAirdropMapping`(§7.5).

**둘 — 비행기 자리는 레이드당 하나다** (`PlaneAirdropMax: 1`). §7.4 **경로 1**(플레어 이벤트
재사용)을 타면 우리 드롭이 그 자리를 쓴다. 그러면 **먼저 쓴 쪽이 이긴다** — 버튼으로 불렀으면
그 뒤에 쏜 플레어는 아무 일도 하지 않고, 플레이어는 왜 안 오는지 모른다.

- **경로 1·2** → 자리를 나눠 쓴다. 공존은 "내용물" 축에서만 성립하고, "한 레이드에 둘 다" 는
  안 된다.
- **경로 3**(직접 스폰) → 예산과 무관하다. **완전히 공존한다.**

따라서 **1단계에서 경로 1이 성공하면 곧바로 "예산을 먹는가" 를 측정한다**(§8). 먹으면
경로 3을 다시 본다. 순서를 바꾸어 처음부터 경로 3으로 가지는 않는다 — 1단계의 목적은
"애초에 띄울 수 있나" 를 가장 싸게 답하는 것이고, 성립 여부도 모른 채 가장 위험한 길을
뚫는 것이 더 나쁘다.

#### 자리를 먹는 경우 사용자에게 보이는 것

상태줄에 **"이 레이드의 보급기 자리: 남음 / 씀"** 을 띄운다. 자리를 쓴 뒤에는 드롭 버튼이
꺼지고 "이 레이드의 보급기를 이미 썼다" 가 뜬다. 플레어를 쏴도 안 오는 이유를 **거기서
알 수 있어야 한다** — 아무 설명 없이 안 오는 것이 가장 나쁘다.

| **우리가 부른 레이드의 바닐라 보급기** | 레이드 | 오는가 안 오는가. 어느 쪽이든 **관찰해 적는다** (§7.10 — 안 와도 합격) |
| 다른 상자를 안 건드리는가 | 레이드 | 우리 드롭 뒤에 온 바닐라 보급기 내용이 **무작위인가** (우리 프리셋이 새어 나가지 않았는가) |
| **플레어 드롭이 바닐라인가** | 레이드 | 토글 끈 상태로 플레어를 쏴서 온 상자가 **무작위인가** (§7.14 기본값) |
| **토글이 듣는가** | 레이드 | `HijackFlareDrops` 를 켜고 플레어를 쏘면 **내 프리셋이 오는가** |
| **비행기 자리** | 레이드 | 우리 드롭 뒤에 플레어를 쏘면 오는가 안 오는가. 안 오면 상태줄이 그 이유를 말하는가 |
| 동시 드롭 거절 | exe | 상자 비행 중·쿨다운 중 버튼이 꺼지고 이유가 뜨는가 |
| 레이드 종료 시 대기열 | 서버 | 예약을 남긴 채 나갔다 다시 들어가면 **떨어지지 않는가** |
| 상자 내용 | 게임 | 프리셋에 적은 것과 **정확히 같은가**. 더도 덜도 없이 |
| 프로필 영향 | 프로필 해시 vs 백업 | 드롭만 하고 레이드를 나가지 않았을 때 **내용이 같아야** 한다 |
| 제거 | `tools/install-airdropcaller.ps1` 기록 | 적힌 파일만 지우면 잔류 0 (모드 이름으로 전수 검색) |

### 8-A. 여기까지 실제로 본 것 (2026-10-29)

창에서 프리셋을 짜고 레이드에서 눌러 상자를 열어 보는 **전 과정이 한 번 닫혔다.**

```
서버   11:52:29.507  드롭 예약 6ae3337dd6a3efa8b8bfb073 → Common 상자에 30개.
게임                 예약 6ae3337dd6a3efa8b8bfb073 실행
서버   11:52:32.927  6ae3337dd6a3efa8b8bfb073 → 예약된 상자를 보낸다.
```

프리셋(`monster drink`)은 1×1 아이템 두 종류 15개씩 = 30개, 120칸 중 30칸.
서버가 담은 것도 30개, `못 담은 것`·`고친 것` 모두 없음. 상자를 열어 보니 그대로
들어 있었다(사용자 확인). **예약에서 전리품이 건네지기까지 3.4초**였고, 그중
대부분은 보고 주기(창이 켜져 있어 2초)가 한 번 돌기를 기다린 시간이다.

아이템 두 종류는 `items.json` 원본에 없는 id 였다 — **모드가 넣은 아이템도 그대로
담긴다**는 뜻이다.

거절 두 갈래도 레이드 없이 `POST /client/airdrop/loot` 로 돌려 확인했다.

| 넣으라고 한 것 | 결과 |
| --- | --- |
| 4×4 방탄복 20개(320칸) → 120칸 상자 | 6개만 담김(10÷4=2, 12÷4=3), 나머지는 `자리 없음 ×14` |
| 모르핀 묶음 50 (최대 1) | `묶음 50 → 1 로 깎았다` — 담기되 `고친 것` 으로 알림 |
| 루블 묶음 9,999,999 | 안 깎임이 **정답** — 이 설치본 서버의 최대는 50,000,000 |

보고 주기 전환도 양쪽을 다 쟀다 — 창을 닫으면 10초, 켜면 2초.

### 8-B. 방어구 채우기와 큰 상자 (2026-10-30)

레이드 없이 `POST /client/airdrop/loot` 를 흉내 내 조립기를 돌려 확인한 것이다.

**방어구 채우기** (`Drops.aabbccdd0000000000000004`)

| 넣으라고 한 것 | 결과 |
| --- | --- |
| IOTV Gen4 완전형, `Fill` 없음 | 자식 13개 — 아라미드 삽입물 9 + 방어판 4 |
| Crye AVS 리그, `Fill` 없음 | 자식 5개 — 삽입물 3 + 방어판 2 |
| Ops-Core FAST MT, `Fill: All` | 자식 8개 — 삽입물 2 + 야시경·마운트·바이저·헤드셋·SLAAP판 |
| Ops-Core FAST MT, `Fill: None` | 자식 0개 |
| SIG MCX, `Fill` 없음 | **자식 0개** — 자동은 무기를 안 건드린다 |

고른 것이 "가장 비싼 것" 규칙대로 나왔다. 앞·뒷판 모두
`ISB Experimental ESAPI Level V "Evernight"` (방어 **7등급**), 좌·우 사이드판 모두
`ESBI level IV`. 둘 다 다른 서버 모드가 넣은 아이템이다 — 디스크 `items.json` 에는
없고 **돌고 있는 서버의 DB** 에만 있다. 규칙이 런타임 DB 를 본다는 증거다.

헤드기어는 `mod_nvg` 안에 `mod_nvg`, 그 안에 `mod_coti` 까지 **3겹**이 붙었다.
`MaxDepth = 3` 이 거기서 멈췄다.

**처음에는 앞뒤가 갈렸다.** 앞판이 7등급을 가져가자 뒷판은 중복 금지에 걸려
6등급(GAC 4sss2)으로 내려갔다. 중복 금지는 헬멧에 야시경이 두 번 붙는 것을 막으려던
것이라, 방어판 칸은 예외로 돌렸다.

**큰 상자** (`Drops.aabbccdd0000000000000005`)

| 본 것 | 결과 |
| --- | --- |
| 큰 상자 격자 (`/client/items`) | `a1d0caffe0000000000c0de1` → **30×30 = 900칸** |
| 베낀 원본 `air_drop_common` | **10×12 = 120칸 그대로** — 바닐라는 안 건드렸다 |
| 4×4 방탄복 20개 → 큰 상자 | **20개 전부 담김.** 못 담은 것 0 |
| 같은 품목 → 보통 상자(…0002) | 6개만 담김 |

**`PostLoad` 에 넣었다가 서버를 못 켰다.** `DatabaseIntegrityService` 가 프로필을 읽은
뒤 늘어난 아이템을 찾아내 멈춰 세운다. `Preload` 로 옮겨 해결했다(§7.5).

### 8-C. 게임에서 본 것 (2026-10-30, TarkovStreets)

위의 조립기 시험을 **레이드에서 그대로 다시 했다.** 프리셋 둘을 미리 올려 두고
(큰 상자 / 보통 상자, 내용은 같다) 레이드 중에 불렀다.

```
02:18:53  드롭 예약 6ae3fe8d… → Weapon 큰 상자에 6개 (부속 40개 붙임).
02:18:55  6ae3fe8d… → 예약된 상자를 보낸다.            ← 2초

02:23:06  드롭 예약 6ae3ff8a… → Weapon 상자에 6개 (부속 40개 붙임).
02:23:09  6ae3ff8a… → 예약된 상자를 보낸다.            ← 3초
```

**부속 40개가 미리 센 것과 한 개도 안 틀렸다** — IOTV 13 + IOTV 13 + IOTV(없음) 0 +
리그 5 + 헬멧(가득) 9 + 헬멧(없음) 0 = 40. 못 담은 것도, 고친 것도 없었다.

| 본 것 | 결과 |
| --- | --- |
| 큰 상자가 게임에서 열리는가 | **열린다.** 서버가 DB 에 끼워 넣은 아이템을 클라이언트가 받아 갔다 |
| 30×30 격자 | 화면을 넘지만 **루팅 창 스크롤로 다 보인다** |
| 자동 채운 방어구 / 직접 고른 앞판 / 빈 몸 | 프리셋 ①②로 모두 확인 |

오늘 만든 셋이 게임까지 닿는 것을 여기서 처음 봤다.

### 8-D. 플레어와 한 레이드에서 공존한다 (2026-10-30, Lighthouse)

§7.14 가 "플레어는 손대지 않는 것이 공짜로 기본값" 이라고 한 것을 실제로 봤다.
**한 레이드 안에서 둘 다 왔다.**

```
04:41:08  드롭 예약 6ae41fe4… → Supply 상자에 14개.      ← 우리가 부른 것
04:41:12  6ae41fe4… → 예약된 상자를 보낸다.
                                                        (5분 뒤, 같은 레이드)
04:46:38  전리품 요청에 상자 id 가 없다 — 바닐라 답을 그대로 보낸다.   ← 플레어
```

| 봐야 할 것 | 결과 |
| --- | --- |
| 한 레이드에 우리 보급 + 플레어 보급 | **둘 다 왔다** (§7.10 대로 비행기 자리를 안 먹는다) |
| 플레어 상자가 바닐라 전리품인가 | 우리가 **바닐라 답을 그대로 흘려보냈다** — 로그가 그 자리를 찍는다 |
| 터지지 않는가 | `Unable to cast…` 는 **고치기 전 4번(03:42~03:45)이 전부**. 서버를 다시 켠 04:12 뒤로는 0번 |

`HijackFlareDrops`(토글을 켜면 플레어도 내 프리셋)는 **아직 못 만든다.** 서버에
도착하는 정보에 "이건 플레어다" 라는 표시가 없다(§13.3).

**아직 안 본 것**: `HijackFlareDrops`(만들기 전), 우리 드롭 뒤의 바닐라 보급기,
프로필 해시 대조.

## 9. 구현자에게 남긴 것

- §7.4 의 1·2·3 중 **무엇으로 될지.** 설계는 순서만 정했다. 실제 메서드 이름과 시그니처는
  `Assembly-CSharp.dll` 과 `spt-custom.dll` 을 디컴파일해 찾아야 한다.
- 에어드롭 상자 tpl 선택 (바닐라에 여러 개 있다면 어느 것인지).
- 격자 배치 알고리즘 (단순 첫자리 채우기로 충분하다. 최적 배치를 풀지 않는다).
- WPF 화면의 세부 배치·색. 다른 `src/` 산출물에 UI 선례가 없으므로 구현자가 정한다.
- 프리셋 파일 형식의 세부 (버전 필드를 둘지 등).
- **플레어 드롭을 무엇으로 알아볼지** (§7.14 의 `FlareWatcher`). 토글이 켜졌을 때만 쓰이므로
  1단계의 필수는 아니다. `AirdropFlareEvent`·`AirdropFlareSuccessEvent` 근처를 본다.
- 토글을 켠 채 플레어와 버튼을 **같은 레이드에서** 썼을 때 어느 프리셋을 쓸지. 대기열이 한
  칸이므로(§7.10) 실제로는 둘 중 하나만 성립한다. 구현자가 단순한 쪽으로 정한다.

## 10. 미확인 사항 — 설계의 약한 곳

1. ~~임의 좌표에 띄울 수 있는지 모른다~~ → **반은 풀렸고 반은 바뀌었다.** 띄우는 것은
   공개 메서드 하나로 된다(§7.4). 하지만 **임의 좌표는 안 된다** — 맵에 미리 박힌 보급
   지점 중 가장 가까운 것이다. "못 하면 모드가 성립하지 않는다" 는 걱정은 사라졌고, 대신
   **"가장 가까운 지점이 얼마나 가까운가" 가 새 미확인 사항**이 됐다(아래 9번).
2. ~~`AirdropCrashPatch` 가 무엇을 막는지 모른다~~ → **스폰 경로의 지뢰가 아니었다.**
   정확한 이름은 `SPT.Custom.Patches.FixAirdropCrashPatch` 로, **레이드 종료 시** 살아 있는
   동기화 객체를 치우는 패치다(상자가 공중에 있는 채로 나가면 터지던 것). 우리 드롭도 같은
   객체를 쓰므로 **그 보호를 함께 받는다.**
3. **`SptLoggerMiddleware` 가 특정 라우트의 로그를 끌 수 있는지 모른다.** 못 끄면 폴링
   주기를 늘리거나 웹소켓으로 가야 한다.
4-A. **SPT 의 HTTP 는 양방향 zlib 이다 (2026-10-29 실측).** 설계가 놓쳤던 것이라 적어 둔다.
    - **응답**: 본문이 zlib 으로 압축돼 오는데 **`Content-Encoding` 헤더가 없다.**
      그래서 `HttpClient` 의 자동 해제가 안 걸린다. 게임 클라이언트
      (`SPT.Common.Http.Client`)도 바이트로 받아 `Zlib.IsCompressed` 로 보고 직접 푼다.
    - **요청**: 본문도 zlib 으로 압축해 보내야 한다. 평범한 JSON 을 보내면 서버가
      **200 을 돌려주지만 본문을 못 읽어 빈 응답**이 온다 — 오류가 아니라 침묵이라
      더 헷갈린다.
    - 외부 창은 양쪽 다 직접 처리한다(`ServerClient.Compress` / `ReadAsync`).

4. ~~서버 커스텀 라우트의 인증 요구를 확인하지 않았다~~ → **밝혀졌다 (2026-10-29 실측).**
   게임 클라이언트가 보내는 것은 **`Cookie: PHPSESSID=<accountId>` 하나뿐**이고
   (`SPT.Common.Http.Client`), 그 값은 **프로필 파일 이름**(`user\profiles\<id>.json`)이다.
   외부 창은 프로필 폴더를 읽어 같은 쿠키를 보낸다 — 로그인 왕복이 필요 없다.
   **다만 `/airdrop-caller/*` 는 쿠키 없이 불러도 200 이 온다** — SPT 가 이 라우트들을
   인증으로 막지 않는다. 그래서 우리가 보내는 쿠키는 **보안이 아니라 신원**이다
   (어느 프로필의 프리셋인가). §7.13 이 "면제하지 않는다" 라고 쓴 것은 우리가 뺄 수
   있는 것을 안 뺐다는 뜻이 아니라, **막는 장치를 새로 만들지 않았다**는 뜻으로 읽어야
   맞다. `doc/PROCEDURE.md` 의 "웹 인증이 켜져 있어 API 조회가 안 된다" 는 메모는
   **웹 UI(6969 의 브라우저 화면)** 이야기지 게임 라우트가 아니다.
5. ~~에어드롭을 건드리는 모드가 있는지 전수로 보지 않았다~~ → **하나 있다. Dynamic Maps 다.**
   게임 로그의 `Enabled patch AirdropBoxOnBoxLandPatch` 가
   `plugins\mpstark-dynamicmaps\DynamicMaps.dll` 것으로, 상자가 착지하면 지도에 표시를
   찍는다. **우리 드롭도 같은 상자를 쓰므로 지도에 함께 뜬다** — 공짜로 얻는 편의다.
   (`Airburst` 는 이름만 비슷한 수류탄 모드였다)
6. ~~우리 상자를 어떤 값으로 식별할지 모른다~~ → **풀렸다.** 우리가 `InitAirdrop` 에 넘긴
   `lootTemplateId` 가 `POST /client/airdrop/loot` 의 `containerId` 로 그대로 돌아온다.
   알아볼 방법을 찾는 문제가 아니라 **이름을 붙여 보내는** 문제였다 (§7.5).
7. ~~`airdrop.json` 과 서버 DLL 의 필드 이름이 다르다~~ → **찾았다.** 설정은 세 군데에
   나뉘어 있다. `configs/airdrop.json` 은 **내용물**(`airdropTypeWeightings`, `loot.<type>`,
   `customAirdropMapping`)만, `globals.json` 의 `config.Airdrop` 은 **비행기·연출**
   (`PlaneAirdropFlareWait: 30`, `PlaneAirdropDuration: 60`, 낙하산 고도 등), 맵별
   `locations/<맵>/base.json` 의 `AirdropParameters[0]` 이 **횟수·확률**
   (`PlaneAirdropMax: 1`, `PlaneAirdropChance: 0.2`, 쿨다운 600~700초,
   `MinPlayersCountToSpawnAirdrop: 6`)이다. 우리는 셋 다 고치지 않는다.
8. ~~`MinPlayersCountToSpawnAirdrop: 6` — 바닐라 보급기가 안 오는 것 같다~~ →
   **틀린 추론이었다. 재니까 런타임 값은 1 이다.** 사람 1명 >= 1 이므로 시간 기반 갈래도
   조건을 통과한다 — **바닐라 보급기는 온다.** 바꾸는 곳도 찾았다:
   `SPTarkov.Server.Core.Services.Server.PostDbLoadService.SetLocationAirdropMinimumPlayers()`
   가 DB 를 읽은 뒤 **모든 맵**의 값을 1 로 낮춘다("6명은 싱글플레이에서 매우 있을 법하지
   않다" 는 주석까지 달려 있다). §8 의 "평소대로 보급기가 오는가" 는 기준으로 쓸 수 있다.
   **설정 파일만 보고 판단하면 틀린다**는 사례다.

## 10-A. 아이템 아이콘 — 파 본 결과 (2026-10-29)

창 목록에 아이템마다의 그림을 달 수 있는지 끝까지 뒤졌다. **지금 쓸 수 있는 것은
분류 아이콘뿐이고, 아이템 아이콘은 길이 둘 다 막혀 있거나 밖에 있다.**

### 번들에서 뽑기 — 안 된다

`items.json` 의 `_props.Prefab.path` 는 **3D 모델** 번들이다
(모르핀 → `item_morphine_loot.bundle`). 아이콘은 파일이 아니라 **게임이 모델을 렌더해
만든다.** 12GB·번들 3427개를 뒤져도 2D 아이콘은 안 나온다.

### 디스크 캐시 — 있는데 못 쓴다

**아이콘이 실제로 디스크에 있다.** `SPT_Runtime/user/sptappdata/live/<번호>.png`,
**9602개, 262MB.** 크기 분포가 EFT 격자 그대로라 아이템 아이콘이 맞다.

```
64x64 (1×1)   127x64 (2×1)   64x127 (1×2)
190x127 (3×2) 316x127 (5×2)  442x64 (7×1) …
```

문제는 **번호와 tpl 을 잇는 표가 없다**는 것이다. 같은 폴더의 `index.json` 은
`<부호 있는 32비트 수> → <파일 번호>` 8764쌍인데, 그 수가 무엇의 해시인지 못 찾았다 —
tpl·`Prefab.path`·`UsePrefab.path`·`_name` 어느 것의 Mono `string.GetHashCode` 도
아니었다. 게임이 아이템 상태(부착물 포함)까지 반영한 합성 키를 쓰는 것으로 보인다.
**해독하면 공짜로 쓸 수 있지만, 성공을 장담할 수 없고 게임이 캐시를 비우면 사라진다.**

### 외부 CDN — `Give Ui` 가 쓰는 길

`Give Ui.exe` 안을 보니 아이콘을 게임에서 꺼내는 것이 아니라 **밖에서 받는다.**

```
https://assets.tarkov.dev/%s-base-image.webp      (%s = tpl)
```

`give-ui.config.json` 의 `cacheFolder` 가 그 받은 것을 두는 자리다. **tpl 로 바로 가고
확실하다.** 걸리는 것 둘:

- **밖으로 나가는 통신이다.** 아이템 id 가 제3자에게 가고 파일을 받아 온다. 지금까지
  이 모드는 `127.0.0.1` 밖으로 나간 적이 없다. **사용자가 정할 일이다.**
- WPF 는 WebP 를 기본으로 못 읽는다. Windows 의 WebP 확장이 있어야 하거나, 받아서
  PNG 로 바꿔 두어야 한다.

### 그래서 지금

분류 아이콘(83개)을 단다. 같은 분류의 아이템은 같은 그림을 단다 — 아이템마다 다르지는
않지만 글자만 있는 것보다 훑기가 낫다.

## 12. 칸을 사용자가 직접 고르기 (2026-10-30, 만들었다)

자동으로 채우는 것(§7.5 "방어구는 비워서 보내지 않는다") 위에, **칸마다 쓸 수 있는
부속을 드롭다운으로 보여 주고 직접 고르게** 할 수 있는지 본 것이다. 결론부터:
**만들었다.** 방어구 셋에 한정하니 규모가 작았다.

### 12.1 규모 — DB 로 재 본 것

| 분류 | 칸 있는 품목 | 칸 평균 / 최대 | 한 칸 후보 최대 | 겹 깊이 |
| --- | --- | --- | --- | --- |
| 바디아머 | 42종 | 7.0 / 13 | 20 | 1 |
| 택티컬 리그 | 30종 | 6.4 / 11 | 20 | 1 |
| 헤드기어 | 64종 | 4.4 / 8 | 18 | **4** |

바디아머와 리그는 **평평하다** — 칸 13개에 드롭다운 13개면 끝난다. 검색창도 필요
없다(후보가 20개를 안 넘는다).

헤드기어만 다르다. 마운트 안에 또 칸이 있어 **4겹까지** 들어간다
(헬멧 → 야시경 마운트 → 야시경 → COTI). 실제로 `Fill: All` 로 떨어뜨려 보니
`mod_nvg` 안에 `mod_nvg`, 그 안에 `mod_coti` 가 붙었다. 그래서 헤드기어는
평평한 목록이 아니라 **접히는 트리**여야 한다.

### 12.2 계약

`ItemSpec` 에 칸별 지정을 더한다. `Fill` 은 그대로 둔다 — **안 적은 칸의 기본값**이
된다.

```jsonc
{
  "Tpl": "5b44cd8b86f774503d30cba2",
  "Fill": "Auto",
  "Slots": {
    "Front_plate": "656faf0ca0dce000a2020f77",   // 직접 고른 것
    "Back_plate": "",                             // 비워 두라는 뜻
    "mod_mount.mod_nvg": "..."                    // 겹친 칸은 점으로 잇는다
  }
}
```

- 적은 칸 → 그대로 쓴다.
- 안 적은 칸 → `Fill` 이 하던 대로.
- `""` → **비워 둔다.** `Auto` 가 채우는 것을 막는 유일한 방법이라 꼭 있어야 한다.

겹친 칸을 점으로 잇는 것이 요점이다. 사전 하나로 4겹까지 적을 수 있어 스키마가
늘지 않는다.

### 12.3 새 라우트

```
POST /airdrop-caller/slots  { tpl }
→ { slots: [ { path, label, required, kind, auto, candidates: [...] } ] }
```

- `path` — `Front_plate` 또는 `mod_mount.mod_nvg`
- `kind` — `soft` · `plate` · `other`. 창이 묶어서 보여 준다
- `auto` — **자동이 고를 tpl**. 드롭다운 맨 위에 "자동 — GAC 4sss2" 로 보인다
- `candidates[]` — tpl · 이름 · 분류 아이콘 · 방어 등급 · 핸드북 값 · 충돌 목록

`auto` 는 `SlotFiller.Best` 를 그대로 부른다. **두 곳이 다른 답을 내면 안 된다** —
창이 "자동: A" 라고 적어 놓고 상자에 B 가 들어 있으면 그게 제일 나쁘다.

### 12.4 창

"채우기" 칸 옆에 **"칸…"** 버튼. 방어구 줄에서만 켜진다. 누르면 작은 창:

```
Ops-Core FAST MT Super High Cut 헬멧            칸 7개
  [방탄] Helmet_top          ▾ 자동 — 티타늄 합금
  [방탄] Helmet_back         ▾ 자동 — 티타늄 합금
  [장비] mod_equipment_000   ▾ 자동 — 멀티 히트 안면 보호 바이저
  [야시경] mod_nvg           ▾ GPNVG-18                    ← 직접 고름
     └ mod_mount             ▾ 비움
  [장비] mod_equipment_001   ▾ 자동 — RAC 헤드셋
```

드롭다운 첫 줄은 늘 `자동`, 둘째는 `비움`, 그 뒤가 후보다.

### 12.5 미리 걸릴 것 셋

**`Count: 20` 이면 20개가 모두 같아진다.** 칸 지정은 줄 단위다. 하나만 다르게 하려면
줄을 나눠야 한다. 이상한 동작은 아니지만 창에 적어 줘야 한다.

**충돌.** 바이저와 야시경처럼 같이 못 다는 것이 있다(`ConflictingItems`). 창이 회색
처리하더라도 **서버가 마지막에 한 번 더 걸러야 한다** — `config.jsonc` 로 손으로
적어 넣는 길이 창을 안 거친다.

**칸에 안 맞는 tpl.** 거절하고 "고친 것" 에 적는다. 조용히 버리지 않는다(§7.5).

### 12.6 범위 — 방어구 셋만

무기까지 열지 않는다. 조준경 칸 하나에 후보가 수백 개라 검색창이 필요해지고, 총은
애초에 완성품 프리셋으로 고르는 쪽이 맞다. 무기는 지금처럼 `Fill` 로만 둔다.

### 12.7 만들고 나서 — 실제로 본 것 (2026-10-30)

레이드 없이 조립기를 돌린 것(`Drops.aabbccdd0000000000000006`)과, 돌고 있는 창을
UI Automation 으로 몰아 본 것이다.

| 본 것 | 결과 |
| --- | --- |
| 자동보다 **낮은** 것을 일부러 고름 (`Front_plate` → 6등급) | 6등급이 들어갔다. 자동(7등급)을 이겼다 |
| 빈 문자열 (`Back_plate` → `""`) | 그 칸이 비었다. 자동이 안 채웠다 |
| 그 칸에 못 다는 것 (`Left_side_plate` → 야시경) | 거절하고 "고친 것" 에 적혔다 |
| 겹친 칸 두 겹 (`mod_nvg` → 마운트, `mod_nvg.mod_nvg` → 도브테일) | 둘 다 붙었다 |
| `Fill: None` + 겹친 칸 지정 | 고른 자리까지만 길이 났고 나머지 칸은 비었다 |
| 창: "칸…" → 칸 11개, 방탄판/삽입물 구분, 자동이 고를 것 표시 | 보인다 |
| 창: 한 칸을 고르고 닫기 | 표의 버튼이 "칸 1" 로 바뀌고 알림이 떴다 |

처음 적어 둔 시험이 틀렸던 것도 하나 있다. 헬멧 마운트의 `mod_nvg` 에 GPNVG-18 을
적었는데 그 마운트는 도브테일 어댑터만 받는다. 서버가 거절하고 그대로 말해 줬다 —
**시험이 틀렸지 코드가 틀린 것이 아니었다.** 거절 문구가 없었으면 한참 엉뚱한 곳을
팠을 것이다.

### 12.8 그 김에 나온 버그 둘

**(ㄱ) "담을 곳" 목록이 처음부터 비어 있었다.** 사용자가 "담을 곳에 아무것도 안 뜬다"
고 한 것이 이것이다. 칸이 투명하게만 보여서 고장으로 안 보였다.

```xml
<!-- 이렇게 적혀 있었다 -->
ItemsSource="{Binding DataContext.ContainerChoices,
              RelativeSource={RelativeSource AncestorType=Window}}"
```

이 창은 **자기 `DataContext` 를 두지 않는다.** `Window.DataContext` 가 null 이라
`DataContext.ContainerChoices` 는 영영 안 풀린다. `DataContext.` 를 떼면 바인딩
원본이 창 자신이 되어 제대로 간다. 새로 넣은 "채우기" 칸도 같은 모양으로 적었다가
같이 비어 있었다.

**(ㄴ) 접힌 ComboBox 에 글자가 안 나온다.** `DisplayMemberPath` 를 쓰면 펼친 목록은
멀쩡한데 접힌 칸만 빈다. 우리 ComboBox `ControlTemplate` 이 `SelectionBoxItemTemplate`
을 제대로 못 받아서다. `ItemTemplate` 을 직접 주면 그 길로 흘러간다.

둘 다 **보이는 증상이 "아무것도 안 뜬다"** 라 바인딩 실패로 안 보인다. WPF 바인딩은
조용히 실패한다.

### 12.9 쓰면서 나온 것 (2026-10-30)

**"칸…" 은 잘린 글자가 아니었다.** 버튼에 적은 말이 말 그대로 `칸…` 이었다. 사용자가
칸을 넓혀 봐도 그대로라 고장으로 보였다. `고르기` / `칸 N개` 로 바꿨다. **창에 적는
말에 말줄임표를 쓰면 "뒤가 더 있다" 는 뜻으로 읽힌다.**

**창을 넓혀도 드롭다운이 안 늘어났다.** 드롭다운 열을 `260` 으로 박아 둬서 부속 이름이
계속 잘렸다. 이름 열을 `Auto` + `SharedSizeGroup` 으로 돌리고 남는 폭을 드롭다운이
가져가게 했다. 겹친 칸의 들여쓰기도 열에서 여백으로 옮겼다 — 열로 두면 그 폭만큼
줄마다 드롭다운이 다른 자리에서 시작한다.

## 13. 본문 없는 전리품 요청 — 플레어를 쏘자 터졌다 (2026-10-30)

§7.14 는 "플레어는 손대지 않는 것이 공짜로 기본값이 된다" 고 적어 뒀다. 의도는 맞았는데
**실제로는 손대는 대신 터뜨리고 있었다.** 레이드에서 플레어를 쏘자 세 번 연달아:

```
Error handling request: /client/airdrop/loot
Unable to cast object of type 'EmptyRequestData' to type 'GetAirdropLootRequest'
   at SPTarkov.Server.Core.DI.RouteAction`1…
```

요청 전체가 500 이 되어 **전리품이 통째로 날아간다.** §5 안티목표 2 에 정면으로 걸린다.

### 13.1 원인

`StaticRouter.HandleStaticAsync` 는 이렇게 생겼다.

```csharp
Type bodyType = routeAction.bodyType;
IRequestData info = null;
if (bodyType != null && !string.IsNullOrEmpty(body))
    info = (IRequestData)jsonUtil.Deserialize(body, bodyType);
if (info == null)
    info = new EmptyRequestData();
```

**본문이 비어 있으면 `bodyType` 이 있어도 `EmptyRequestData` 가 들어간다.** 그리고
`RouteAction<T>` 는 그것을 딱딱하게 받는다.

```csharp
base..ctor(url, async (…) => await typedAction(arg, (TRequest)info, …), typeof(TRequest));
//                                              ^^^^^^^^^^^ 여기서 터진다
```

바닐라 `LocationStaticRouter` 는 같은 자리를 **무르게** 받는다.

```csharp
new RouteAction("/client/airdrop/loot",
    async (url, info, sessionID, output, ct) =>
        await locationCallbacks.GetAirdropLoot(url, info as GetAirdropLootRequest, sessionID))
```

우리만 딱딱했다. 비제네릭 `RouteAction` 으로 바꾸고 `info as GetAirdropLootRequest` 로
받는다. **`bodyType` 은 그대로 넘긴다** — 빼면 본문이 있을 때도 `containerId` 를 영영
못 읽어 모드가 통째로 죽는다.

### 13.2 레이드 없이 재현하고 확인한다

플레어를 쏘지 않아도 된다. **본문 없이** 그 라우트를 때리면 같은 길을 탄다.

```
POST /client/airdrop/loot   Content-Length: 0
```

| | 고치기 전 | 고친 뒤 |
| --- | --- | --- |
| HTTP | 500 | **200** |
| 답 | 없음 | `air_drop_common` 상자 하나, 6,457바이트짜리 바닐라 전리품 |
| 로그 | `Unable to cast…` | `전리품 요청에 상자 id 가 없다 — 바닐라 답을 그대로 보낸다.` |

`tools` 밖의 한 번 쓰는 probe 라 저장소에 두지 않았지만, 같은 요청 한 줄이면 언제든
다시 잰다.

### 13.3 남는 것

**플레어 상자가 왜 본문을 안 보내는지는 아직 모른다.** 우리가 부른 상자는 `containerId`
를 보내 왔다(실측). 플레어 쪽만 비는 것이 클라이언트의 다른 경로 때문인지, 아니면
"상자 id 없이 묻는" 다른 상황이 또 있는지 안 봤다. **그래서 §7.14 의 `HijackFlareDrops`
는 여전히 만들 수 없다** — 서버에 도착하는 정보에 플레어라는 표시가 없다.

## 14. 못 그리는 아이템을 떨어뜨리면 조작이 굳는다 (2026-10-30)

플레어 시험을 하려고 신호권총과 **RSP-30 조명탄 여섯 색을 전부** 담아 떨어뜨렸다.
어느 색이 보급을 부르는지 몰라 "안전하게 다 넣자" 고 한 것이다. 그중
**Firework**(`675ea3d6312c0a5c4e04e317`)을 손에 드는 순간 **아이템이 안 그려지고
조작이 통째로 굳었다.**

Unity 쪽 `Player.log` 에 이것이 **9,630번** 쌓여 있었다.

```
NullReferenceException: Object reference not set to an instance of an object
  at EFT.MovementContext+CG_Class1396.method_3 (EFT.Player player)
  at EFT.Player.MouseLook (System.Boolean forceApplyToOriginalRibcage)

  at EFT.Player.DMD<EFT.Player::LateUpdate>
```

쓰이는데 조작만 안 먹는다 — 처음에 "로그가 돌고 있으니 멈춘 게 아니다" 라고 본 것이

### 14.1 이것은 우리 코드의 버그가 아니다. 우리가 만든 위험이다

조립기도 라우터도 시킨 대로 했다. 문제는 **우리가 아이템 DB 에 있는 것이면 무엇이든
떨어뜨릴 수 있다**는 것이다. 그 안에는 클라이언트가 그릴 수 없는 것도 있다 —
행사 때만 쓰이고 들어온 것들이 특히 그렇다. 세 개가 그 시기 id 다.

### 14.2 로그로 범인을 못 짚었다

`Player.log` 에서 여섯 tpl 을 세어 보니 `66d9f1ab`(Special Yellow)만 8번 나왔다.
그래서 그쪽을 의심했는데 **틀렸다** — 그 여덟 줄은 다른 모드(Flexible Builds)가

이름을 남기지 않았다. **사용자가 화면에서 직접 짚어 준 것이 맞았다.**

세어 본 횟수가 많다고 원인인 것이 아니다.

### 14.3 남은 숙제

창은 지금 아이템 DB 에 있는 것을 전부 보여 준다. **"이건 게임이 못 그릴 수 있다" 를
미리 알 방법이 서버에 있는지 아직 안 봤다.** 번들 목록(`/singleplayer/bundles`)으로
모드가 넣은 것은 가려낼 수 있을지 모르나, 기본 게임 에셋 안에 있는지는 서버가 모른다.
적어도 **한 번 굳힌 tpl 을 기억해 두고 다음에 경고하는** 정도는 할 수 있다.

## 15. 무기는 완성품으로 보낸다 (2026-10-30)

사용자가 창에서 **돌격소총이 `1x1` 로 보이는 것**을 보고 짚어 줬다. 표시만의 문제가
아니었다.

### 15.1 1×1 은 증상이고 원인은 빈 몸이었다

무기의 **템플릿 크기는 원래 1×1** 이다. 실제 크기는 붙은 부품의 `ExtraSize*` 에서
나온다. 그러니 1×1 로 보인다는 것은 **우리가 빈 몸을 들고 있다는 신호**였다.

SIG MCX 의 칸은 이렇게 생겼다.

| 칸 | |
| --- | --- |
| `mod_pistol_grip` | **필수** |
| `mod_reciever` | **필수** |
| `mod_charge` | **필수** |
| `mod_magazine` · `mod_stock` | 선택 |

`Fill: Auto` 는 방어구에만 손대므로 무기는 **자식 0개**로 나갔다. 필수 셋이 전부
비어 있었다. 실제로 떨어뜨린 MCX-SPEAR 가 **0.286 kg** 이었다(제대로면 4 kg 대).
화면에 보이던 부품 아이콘은 빈 칸 자리표시였다.

### 15.2 어떻게 놓쳤나

삽입물 없는 방어구를 **바로 앞에서 고쳐 놓고**(§7.5) 같은 종류의 결함을 무기에서는
"자동은 무기를 안 건드린다" 며 **설계대로라고 이 문서에 적었다.** 시험 설정에도
`SIG MCX — 안 건드려야 한다` 라고 써 놓고 **자식 0개를 합격으로 처리**했다.
probe 출력에 `MCX 1x1` 이 찍혀 있었는데 tpl 만 집어 가고 지나쳤다.

"무기는 범위 밖" 이라고 선을 긋는 것까지는 괜찮았다. **범위 밖으로 둔 결과가 무엇인지
안 본 것**이 잘못이다. 빠뜨리는 것과 망가진 것을 내보내는 것은 다르다.

### 15.3 고친 것

`PresetHelper.GetDefaultPreset(tpl)` — 바닐라 보급이 무기를 넣을 때 쓰는 완성품이다.

- `Auto` → 무기는 완성품, 방어구는 삽입물·방어판
- `All` → 완성품 + 남은 빈 칸까지
- `None` → 빈 몸 (일부러 그럴 때만)
- 칸에서 **직접 고른 것이 완성품보다 세다**

`ItemHelper.ReparentItemAndChildren` 으로 새 id 를 받는다. 프리셋 id 를 그대로 쓰면
한 상자에 같은 총 두 자루를 넣었을 때 id 가 겹친다.

창의 크기 표시도 완성품 기준으로 바꿨다. **조립기와 창이 같은 수를 말해야 한다.**
검색이 한 번에 400개까지 돌려주므로 tpl 마다 한 번만 재고 기억한다.

### 15.4 고친 뒤 (실측)

| 본 것 | 전 | 후 |
| --- | --- | --- |
| Modified SIG MCX-SPEAR | `1x1` | **`6x2`** |
| SIG MCX .300 AAC Blackout | `1x1` | **`4x2`** |
| SIG MCX .300 Blackout (RAL 8000) | `1x1` | **`5x2`** |
| IOTV 셋 | `3x4` `4x3` `4x4` | **그대로** |

실제로 떨어지는 것도 완성품이다. `Drops.…0004` 의 MCX 가 이렇게 나온다 — 손잡이,
탄창, 상부 총몸, 그 아래 총열 → 총구 어댑터 → 제퇴기, 가스블록, 총열덮개 →
가늠쇠, 가늠자, 개머리판, 장전 손잡이. **겹까지 그대로 선다.**

### 15.5 완성품이 없는 총 — 필수 칸만이라도 채운다 (2026-10-30)

§15.3 은 "기본 프리셋으로 세운다" 로 끝냈는데, **프리셋이 없는 총을 안 봤다.**
디스크 DB 기준으로 칸 있는 무기 152종 중 5종이 그렇다.

| 총 | 필수 칸 |
| --- | --- |
| FN SCAR-H X-17 7.62x51 | 4 (손잡이·총몸·개머리판·장전손잡이) |
| Kalashnikov PKTM 7.62x54R | 2 (손잡이·총열) |
| TheAKGuy AK-50 .50 BMG | 2 (손잡이·총열) |
| NSV "Utyos" 12.7x108 | 0 |
| AGS-30 30x29mm | 0 |

프리셋이 있다는 전제만 보고 없는 경우를 안 본 것이다. **같은 실수를 한 번 더 했다** —
§15.2 에 적은 "범위 밖으로 둔 결과를 안 봤다" 와 같은 모양이다.

`Auto` 의 규칙을 한 줄 고쳤다.

```csharp
SlotFill.Auto => deeper || required || (isArmor && isPlate),
//                         ^^^^^^^^ 종류를 가리지 않고 필수 칸은 채운다
```

완성품이 있는 물건은 그 칸이 이미 차 있어(`taken`) 여기까지 오지 않는다. 방어구의
삽입물도 `_required` 라 이 한 줄에 같이 걸린다 — 따로 적을 필요가 없어졌다.

**고친 뒤 (실측)**

| 총 | 전 | 후 |
| --- | --- | --- |
| FN SCAR-H X-17 | `1x1` | **`6x2`** |
| TheAKGuy AK-50 | `1x1` | **`7x2`** |
| Kalashnikov PKTM | `1x1` | **`3x1`** |
| SIG MCX(프리셋 있음) | `4x2` | **그대로** |

SCAR 는 손잡이·총몸·개머리판·장전손잡이가 서고, 총몸 아래로 총열과 레일까지
겹으로 붙는다.

**남은 것**: `mod_magazine` 은 `_required` 가 아니라 **빈 채로 간다.** 프리셋으로
세운 총은 프리셋에 탄창이 들어 있어 받는데, 이쪽은 못 받는다. 둘이 다르다.

### 15.6 탄창도 채운다 — 규칙에 낸 구멍 하나 (2026-10-30)

`mod_magazine` 은 `_required` 가 아니다. 그런데 **완성품으로 세운 총은 프리셋에
탄창이 들어 있어** 받는다. 필수 칸만 채우는 쪽(§15.5)만 빈손이 되면 같은 `자동` 인데
결과가 갈린다 — 쏘려면 탄창을 따로 챙겨야 한다.

```csharp
SlotFill.Auto => deeper || required || isMagazine || (isArmor && isPlate),
```

**"필수만" 이라는 규칙에 내는 구멍은 이 하나뿐이다.** 더 늘리면 "자동" 이 무엇을
하는지 말로 설명할 수 없게 된다.

**확인한 것**

| 본 것 | 결과 |
| --- | --- |
| SCAR-H X-17(프리셋 없음)의 `mod_magazine` | **찬다** — AR-10 X-25 50발 드럼 |
| SIG MCX(프리셋 있음)의 탄창 수 | **1개** — 프리셋 것 하나뿐, 겹치지 않는다 |
| SCAR 크기 | `6x2` 그대로(드럼은 격자를 안 넓힌다) |

프리셋이 이미 채운 칸은 `taken` 이라 여기까지 오지 않는다. 그래서 탄창이 둘 달리는
일은 없다.

### 15.7 방어구가 들어갈 칸은 자동도 채운다 (2026-10-30)

사용자가 게임에서 **헬멧에 방탄판만 들어가고 나머지는 안 붙는 것**을 보고 짚어 줬다.
두 가지가 겹쳐 있었다.

**(ㄱ) 창이 또 거짓말을 했다.** 서버는 그 칸들을 `(빈 칸)` 으로 제대로 돌려주는데,
창이 `auto`(= 채운다면 무엇을 고를까)를 `chosen`(= 실제로 무엇이 들어가는가) 자리에
적고 있었다. 이제 비는 칸은 **"자동 — 안 채운다"** 로 적는다.

**(ㄴ) 규칙이 칸 이름에 기대고 있었다.** 방어판 칸을 `IsRemovablePlateSlot` 으로
가렸는데, 헬멧의 SLAAP 방탄판은 `mod_equipment_002`, 측면 보호대는
`mod_equipment_000` 이라 거기 안 걸린다. **장식이 아니라 방어력인데 바닥에 버리고
있었다.** 이름 대신 **들어갈 물건이 막아 주는가**로 가른다.

```csharp
SlotFill.Auto => deeper || required || isMagazine || Protects(auto),
```

`isArmor && isPlate` 는 뺐다 — 방어판은 어차피 등급을 들고 있어 같이 걸린다.

**고친 뒤 (FAST MT, 실측)**

| 칸 | 들어가는 것 | |
| --- | --- | --- |
| `Helmet_top` · `Helmet_back` | Hybrid composite materials (4/24) | 완성품이 넣은 것 |
| `mod_equipment_000` | ComTac VI 헤드셋 (등급 3) | 새로 찬다 |
| `mod_equipment_001` | AirFrame Chops (등급 3) | 새로 찬다 |
| `mod_equipment_002` | SLAAP 방탄판 (등급 5) | 새로 찬다 |
| `mod_nvg` | CULTIST 마스크 (등급 5) | 새로 찬다 |
| `mod_mount` | — | 등급이 없어 비운다 |

**삽입물이 Titanium alloy(등급 5, 42,275원)가 아닌 것은 맞다.** 후보 목록에서 그것이
1위인데도 Hybrid composite 가 들어간다 — **완성품(기본 프리셋)이 그 칸을 이미 채웠기
때문**이다. 막힌 것이 아니라 완성품이 이긴 것이고, 게임에서 사용자가 본 `24/24` 와
정확히 같다. §12.3 의 "창과 상자가 같은 것을 말해야 한다" 가 이제 지켜진다.

야시경 칸에 마스크가 들어가는 것도 규칙대로다 — 그 칸 후보 중 가장 비싼 것이
마스크고 마스크는 방어구다. 야시경을 달려면 칸에서 직접 고르거나 `가득` 으로 간다.

## 16. 낙하산이 안 사라지고 상자가 땅을 뚫는다 (2026-10-30, 측정됨)

사용자가 세 가지를 보고했다 — **낙하산이 안 사라짐**, **맵·미니맵에 보급 표시 안 됨**,
**낙하산 효과음이 반복 재생**. 그리고 뒤에 하나 더: **상자가 땅을 뚫고 들어가 사라짐**.

### 16.1 틀린 가설 — 겹침

바닐라는 `InitAirdrop` 앞뒤로 두 줄을 더 한다(`ServerAirdropManager.ManualUpdate`).

```csharp
_currentAirdropsCount++;
UpdateAirdropTimers(PlaneAirdropCooldown);
Singleton<GameWorld>.Instance.InitAirdrop(...);
```

우리는 가운데만 부른다. 그래서 우리 상자가 하늘에 있는 동안 맵이 자기 보급기를
띄울 수 있다고 보고, **겹침**을 의심했다.

**틀렸다.** 계측을 넣고 재 보니 증상이 난 판에서 비행기도 상자도 **하나뿐**이었고
맵이 센 보급은 **0** 이었다. 겹친 적이 없다.

### 16.2 측정 — `ParachuteEndOpen` 에서 안 넘어간다

보고에 상자마다의 낙하 단계를 실어 2초마다 찍었다.

```
Fall              24번   07:53:29 ~ 07:54:15   (46초)
ParachuteEndOpen  44번   07:54:17 ~ 07:55:44   (87초, 그대로 계속)
```

`Contact` 에도 `Landed` 에도 **도달하지 못한다.**

### 16.3 세 증상이 한 원인이었다

`ParachuteEndOpen` 은 `ParashuteLanding` 이 상자를 계속 아래로 내리는 구간이고,
거기서 빠져나가는 길은 `ServerAirDrop.CollisionEnter` **하나뿐**이다.

```csharp
if ((_descending && GetPlayerByCollider(collider) != null) || !_descending
    || LootLayer || PlayerLayer || TriggersMask || DefaultLayerMask) return;
_fallingStage = EAirdropFallingStage.Contact;
```

충돌이 안 잡히면:

| 증상 | 까닭 |
| --- | --- |
| 땅을 뚫고 사라진다 | 멈춰 세우는 것이 없어 계속 내려간다 |
| 낙하산이 안 닫힌다 | `CloseParachute` 는 `Contact`·`Landed` 에서만 불린다 |
| 효과음이 반복된다 | `PlaySqueakSoundLoop` 가 `ParachuteEndOpen` 에서 돈다 |
| 맵에 표시가 안 된다 | 상자가 `Landed` 로 자리를 잡은 적이 없다 |

~~**넷이 한 뿌리다.** 따로 고칠 것이 아니다.~~

**이 줄은 틀렸다 — §16.5.** 하나가 아니라 **셋**이었다.

### 16.4 아직 모르는 것 — 우리 것인가

이게 **우리 드롭만의 문제인지, 이 설치본에서 보급이 원래 그런지** 아직 모른다.
가르는 방법은 손에 있다 — **플레어를 쏘는 것**이다. 플레어 보급은 우리가 안 건드리는
바닐라 경로인데(§8-D), 계측은 하늘의 **모든** 상자를 세므로 그쪽 단계도 같이 찍힌다.

| 플레어 상자가 | 뜻 |
| --- | --- |
| `Landed` 까지 간다 | 우리 쪽 차이다. 낙하 지점 고르는 방식이 첫 용의자 |
| 똑같이 멈춘다 | 보급 자체가 깨져 있다. 우리 탓이 아니고 고칠 데도 다르다 |

우리가 다르게 하는 것은 **낙하 지점을 고르는 방식**이다 — 바닐라는 authored 지점 중
무작위, 우리는 `takeNearbyPoint: true` 로 **플레이어에게 가장 가까운 점**을 집는다.
둘 다 `_airdropPoints` 의 authored 지점이지만, 가까운 쪽을 계속 집다 보면 사용자가
서 있는 자리에 따라 평소 안 쓰이던 지점이 뽑힐 수 있다.

사용자가 "정상적으로 떨어진 적도 있다" 고 했으므로 **어디에 내려앉느냐에 달린 문제**로
보인다. 같은 자리에서 둘을 비교하는 것이 가장 깨끗하다.

### 16.5 한 뿌리가 아니었다 — 셋이다 (2026-10-30, 측정됨)

§16.3 의 "넷이 한 뿌리" 는 **틀렸다.** 계측을 더 넣고 보니 세 갈래였다.

| 시각 | 상자 | 엔진 단계 | 눈으로 본 것 |
| --- | --- | --- | --- |
| 07:53 | 큰 | `ParachuteEndOpen` (영영) | 땅 뚫고 사라짐 + 낙하산 남음 |
| 07:57 | 보통 | `Landed` | 착지 + 낙하산 사라짐 |
| 08:01 | 큰 | `Landed` | 착지 + 낙하산 사라짐 |
| 08:11 | 보통 | `Landed` | **착지 + 낙하산 남음** |
| 09:01 | 보통 | `Landed(먼지켜짐)` | 착지 + 낙하산 사라짐, **소리만 계속** |

08:11 이 §16.3 을 깬다. `Landed` 까지 갔는데도 낙하산이 남았다 — 충돌을 못 잡은
것이 원인이라면 일어날 수 없는 조합이다. 그래서 갈래가 셋이다.

| 갈래 | 증상 | 상태 |
| --- | --- | --- |
| ① 충돌을 못 잡는다 | `ParachuteEndOpen` 에 멈춰 땅을 뚫는다 | **미해결.** 자리에 달린 문제로 보인다(§16.4). 재현이 드물다 |
| ② `Landed` 인데 낙하산이 남는다 | `CloseParachute` 가 한 번도 안 불린다 | **미해결.** 아래 한 번 겨눔 `if` 가 범인이다 |
| ③ 소리가 안 멈춘다 | 착지는 정상, 반복 소리만 계속 | **고쳤다 — §16.6** |

②의 자리:

```csharp
case EAirdropFallingStage.Landed:
    if (_startFallingStage != _fallingStage && !_airdropDust.activeSelf)
    { ...; PlayLandingSound(); CloseParachute(); }
```

`Landed` 분기 전체가 이 `if` 하나에 걸려 있고, **한 번 참이면 먼지가 켜져 다시는
참이 안 된다.** 그래서 저 두 조건 중 하나가 첫 `Landed` 프레임에 거짓이면
`CloseParachute` 가 영영 안 불린다. 어느 쪽이 거짓이었는지를 보려고 보고에
`_startFallingStage` 와 먼지 상태를 실었다. 09:01 판은 `시작Fall,다름,먼지켜짐` —
**정상 경로**였다. ②는 아직 다시 잡지 못했다.

### 16.6 소리는 바닐라가 안 끈다 (2026-10-30, 고쳤다)

09:01 판은 착지도 낙하산도 정상이었고 **소리만** 남았다. 그래서 ③은 ①·②와 다른
원인이다. `ClientAirDrop.ManualUpdate` 의 꼬리가 그것이다.

```csharp
if (_loopSoundSource != null && LoopSoundSource.PlayBackState != Playing)
{
    if (_signalFire) PlayFlareSound();   // looped: true
    else ReleaseSoundSource();
}
```

착지하면 `PlayLandingSound` 가 낙하산 소리를 `Stop()` 하고 쿵 소리를 한 번 낸다.
**그 쿵 소리가 끝나는 순간** 위 꼬리가 `PlayFlareSound` 로 연막 소리를 `looped: true`
로 켠다. 그 뒤로는 멈출 길이 없다.

- 반복 재생 중에는 `PlayBackState` 가 늘 `Playing` 이라 `ReleaseSoundSource` 쪽으로
  갈 수 없다. `_signalFire` 가 거짓이 돼도 마찬가지다 — 꼬리의 `if` 자체를 못 넘는다.
- 연막은 `PlaneAirdropSmoke` = **600초**나 탄다(이 설치본 `globals.json`).
- 그 시간이 지나면 `ServerAirDrop` 이 `_syncObject.IsStatic = true` 를 걸어
  `ManualUpdate` 자체가 멈춘다. 끌 기회가 사라진다.

**바닐라에서도 그렇다.** 우리가 만든 버그가 아니라, 우리 보급이 플레이어 발밑에
떨어지는 탓에 들리게 된 바닐라 버그다.

**고친 방법.** 플러그인이 매 프레임 보고 있으니, 먼지가 켜진(= 착지 분기가 한 번 돈)
상자를 설정값(기본 2초) 뒤에 한 번 `ReleaseSoundSource()` 해 준다. 그러면
`_loopSoundSource` 가 null 이 되어 꼬리의 **첫** 조건이 거짓이 되고, 다시 켜지지
않는다 — 낙하산 소리는 `ParachuteStartOpen`/`EndOpen` 분기에서만 켜지니 되살아날
길도 없다. 연기와 불꽃은 건드리지 않는다. 2초를 두는 것은 착지의 쿵 소리를 삼키지
않기 위해서다. F12 의 `소리` 묶음에서 음수로 두면 바닐라대로 돌아간다.

**고친 뒤 실측 (2026-10-30 10:27).** 상자는 `ParachuteEndOpen` 을 거쳐
`Landed(시작Fall,다름,먼지켜짐)@-644,-56,391` 로 앉았고, 게임 로그에
`착지한 상자의 반복 소리를 끊었다` 가 한 번 찍혔다. 사용자 확인 — **착지 뒤 소리가
끊기고 낙하산도 사라졌다.** 같은 판에서 `Common 상자에 13개` 도 다시 맞았다(§7.5).

이 판의 y 값이 음수인 것은 증상이 아니다. 그 자리의 지면이 `y ≈ -56` 이다 —
`ParachuteEndOpenHeight` = 180 이라 **지면에서 180m 안에 들어오면** 그 단계로 바뀌니,
단계만 보고 "땅을 뚫었다" 고 읽으면 안 된다. ①을 가르는 기준은 y 값이 아니라
`Landed` 에 **도달하는가** 다.

### 16.7 ①의 기계 — 재는 자와 멈추는 자가 다르다 (2026-10-30)

디컴파일을 더 읽어 ①의 **구조**를 짚었다. 단계를 넘기는 판단과 상자를 멈추는 판단이
**서로 다른 것을 본다.**

| 하는 일 | 보는 것 |
| --- | --- |
| `Fall` → `ParachuteStartOpen` → `ParachuteEndOpen` | `GetRaycastPoint` — `Physics.RaycastAll(..., LayersMaskController.TerrainLowPoly)` |
| `ParachuteEndOpen` → `Contact` | `CollisionEnter` — 유니티 **물리 충돌**, 그중 Loot·Player·Triggers·**Default** 층은 무시 |
| `Contact` → `Landed` | `CalcExtents` — 네 귀퉁이에서 **아래로 2m** 레이캐스트 |

낙하산은 **저폴리 지형**을 기준으로 펴지는데, 멈추는 것은 **물리 충돌**에 달려 있고
그 충돌은 Default 층을 통째로 무시한다. 건물·구조물·소품은 대부분 Default 다. 그래서
"저폴리 지형은 180m 안에 있지만 그 사이에 멈춰 세울 것이 없는 자리" 가 생길 수 있고,
그 자리에서는 `ParashuteLanding` 이 상자를 영원히 내린다.

```csharp
public void ParashuteLanding(float deltaTime)
{
    SyncObjectTransform.position += (Vector3.down * ParachuteSpeed + WindVector()) * deltaTime;
}
```

브레이크가 이 함수 안에 없다. `CollisionEnter` 하나뿐이다.

우리가 바닐라와 다르게 하는 것이 **지점 고르기**(`takeNearbyPoint: true`)이므로, 평소
안 쓰이던 authored 지점이 뽑히면 이 자리를 밟을 확률이 올라간다. 우리가 만든 버그는
아니지만 **우리가 더 자주 밟게 만든다.**

### 16.8 세 가지를 플러그인이 메운다 (2026-10-30)

바닐라 파일은 고치지 않는다. 플러그인이 매 프레임 상자를 보고 빈 곳만 메운다
(`TendCrates`).

| 갈래 | 메우는 방법 | 설정 (F12) |
| --- | --- | --- |
| ③ 소리 | 앉은 뒤 n초에 `ReleaseSoundSource()` 한 번 | `소리 / 착지 뒤 반복 소리 끄기(초)` 기본 2 |
| ② 낙하산 | `Landed` 인데 낙하산이 1초 넘게 남으면 `CloseParachute()` | `구조 / 남은 낙하산 접기` 기본 켬 |
| ① 지나침 | `ParachuteEndOpen` 에서 n미터보다 더 내려가면 지면을 찾아 앉힌다 | `구조 / 막힌 것으로 보는 낙하 거리(m)` 기본 200 |

**②는 원인을 모르고도 메운다.** `CloseParachute` 에는 `_startClosingParachute` 자체
잠금이 있어 두 번 불러도 안전하고, 정상 판에서는 이미 닫혀 있어 `activeSelf` 가
거짓이라 우리 쪽이 돌지 않는다. 대신 첫 `Landed` 프레임의 두 조건을 로그에 한 번
남겨 다음 번에는 **원인**을 알 수 있게 했다.

```
[AirdropCaller] 앉았다 — 시작Fall, 먼지켜짐, 낙하산닫힘.
```

**①은 지면을 다시 찾아 앉힌다.** 요령은 `CollisionEnter` 에 **무시당하지 않는 층의
collider** 를 넘겨 주는 것이다 — 바닐라가 단계 전환에 쓰는 것과 같은
`TerrainLowPoly` 를 레이캐스트해 그 collider 를 쓴다. `CalcExtents` 가 2m 만 재므로
**자리를 먼저 옮기고** 부르고, 클라이언트가 한 프레임 동안 옛 자리로 끌어내리지 않게
`_destinationPosition` 도 같이 고친다. 아래에서 지면을 못 찾으면 위도 본다(이미
지나친 경우). 위아래 600m 안에 지면이 없으면 손대지 않고 로그만 남긴다.

200m 를 쓰는 근거: `ParachuteEndOpen` 은 지면이 `ParachuteEndOpenHeight`(=180) 안에
들어와야 시작하므로 정상이면 그 단계에서 180m 안에 멈춘다. 실측도 그렇다 — 09:01 판
174m, 10:27 판 180m.

**계측도 늘렸다.** 보고의 단계 문자열에 상자 **아래에 지면이 있는지**를 붙인다
(`,지면-56` 또는 `,지면없음`). ① 이 다시 나면 "밑에 땅이 있었는데도 못 멈췄나,
아니면 땅 자체가 없었나" 가 바로 갈린다.

아직 **재현을 못 해 실측으로 확인하지 못했다.** 둘 다 드물게 나오므로, 다음에 날 때
위 로그 줄로 확인한다.

### 16.9 ②의 원인 — 남의 패치가 착지 분기를 끊었다 (2026-10-30, 측정됨)

②를 재현했고 **원인을 잡았다.** 우리 것이 아니었다.

새 보고 줄이 답을 줬다.

```
앉았다 — 시작Fall, 앉기전먼지꺼짐, 먼지켜짐, 낙하산남음, 안접음.
```

바닐라 조건 **둘 다 참**이었다(`시작Fall` ≠ `Landed`, 앉기 전 먼지 꺼짐). 그런데
먼지는 켜졌고 `CloseParachute` 는 안 불렸다. 분기 중간에서 **예외가 터졌다**는 뜻이다.
`Player.log` 에 있었다.

```
MethodAccessException: Method `GamePanelHUDCompass.GamePanelHUDCompassPlugin.RaycastGround(…)'
  is inaccessible from method `DTFType_GamePanelHUDCompassPlugin_RaycastGround.RaycastGround()'
  at DTFType_GamePanelHUDCompassPlugin_RaycastGround.RaycastGround ()
  at (wrapper dynamic-method) EFT.Airdrop.ClientAirDrop.DMD<ClientAirDrop::CheckSurface>(…)
  at EFT.Airdrop.ClientAirDrop.ManualUpdate (System.Single deltaTime)
  at EFT.SynchronizableObjects.SynchronizableObject.ManualUpdate (System.Single deltaTime)
```

**Game Panel HUD 나침반(4.1.6 포팅본)** 이다. 디컴파일로 확인했다.

```csharp
EFTHelpers._AirdropLogicClassHelper.RaycastGround.Add(this, "RaycastGround", (HarmonyPatchType)2);
//                                                                                           ↑ 2 = Postfix
private static void RaycastGround(AirdropSynchronizableObject ___airdropSynchronizableObject_0)
```

`ClientAirDrop.CheckSurface` 에 Postfix 를 걸었는데, 그쪽이 만든 트램폴린 타입이 자기
`private static` 메서드를 못 불러 **매 착지마다** 터진다. Postfix 의 예외는 패치된
메서드 밖으로 나가 `ManualUpdate` 를 중단시킨다.

```csharp
_airdropDust.SetActive(value: true);   // 여기까지 된다 → "먼지켜짐"
_airdropDust.…Play();
CheckSurface();                        // 여기서 터진다
PlayLandingSound();                    // 못 돈다 → 낙하산 소리가 안 멈춘다
CloseParachute();                      // 못 돈다 → 낙하산이 남는다
```

**이 하나가 사용자의 첫 보고 셋을 설명한다** — 낙하산 잔존, 효과음 반복,
그리고 **맵·미니맵에 보급품 표시 안 됨**.

표시 쪽은 내가 처음에 원인을 잘못 짚었다(아래 정정 참고). 표시는 **착지가 끝까지
처리되는가**에 달려 있다. 예외가 착지 분기를 끊은 판에서는 그 처리가 안 끝나 표시도
안 됐고, 고친 뒤 정상 착지하는 판에서는 표시된다(사용자 실측 2026-10-31).

#### 왜 어떤 판은 멀쩡했나

`case Contact:` 에도 `CloseParachute()` 가 있고 **거기엔 조건이 없다.**

| 닿는 방식 | `Contact` 단계 | 결과 |
| --- | --- | --- |
| 한 점 | `OnOnePointContact` → `RotateAfterDrop` 코루틴 → **여러 프레임** | `case Contact:` 가 돌아 낙하산이 접힌다 → 멀쩡해 보인다 |
| 두·세 점 | `CollisionEnter` 안에서 곧바로 `Landed` → **프레임 없음** | 접을 기회가 `Landed` 분기뿐이고 거기서 터진다 → ② |

상자가 어떻게 기울어 닿았느냐로 갈렸다. 실측 비율은 두 번 중 한 번꼴이었다
(13:08·13:17 판 각 1건).

#### 설정으로는 못 막는다 (실측)

`com.kmyuhkyuk.GamePanelHUDCompass.cfg` 에 `Compass Static Airdrop display` 가 있지만
**끄는 것으로 해결되지 않는다.** 패치는 `Awake` 에서 설정과 무관하게 걸리고, 예외는
그쪽 코드에 닿기도 전에 트램폴린에서 터진다.

#### 고친 방법 — Finalizer 로 삼킨다

`SurfaceGuard` 가 `CheckSurface` 에 Harmony **Finalizer** 하나를 걸어 예외를 없던
것으로 만든다(`null` 반환). 그러면 바닐라가 끝까지 돌아 **착지음도 나고 낙하산도
스스로 접힌다.** 우리 보급만이 아니라 **바닐라·플레어 보급도** 같이 고쳐진다.

이 모드의 첫 Harmony 패치다. 지금까지 공개 메서드만 불러 왔고 그것이 설계상 미덕이었지만,
남의 Postfix 가 바닐라 메서드를 끊는 것은 밖에서 막을 길이 이것뿐이다. 범위는 한
메서드의 예외 하나이고, 삼킨 것은 로그에 적는다(처음 세 번만, 그 뒤엔 조용히).

우리 쪽 보수(`TendCrates`)는 그대로 둔다. Finalizer 가 못 걸리는 상황에서도 증상은
가려야 하고, 둘이 겹쳐도 `CloseParachute` 는 자체 잠금이 있어 안전하다.

#### 정정 — 맵 표시는 이것으로 같이 고쳐진다 (2026-10-31)

나는 처음에 이렇게 적었다: "나침반 표시는 돌아오지 않는다. 그쪽 코드는 애초에 불리지
못한다 — 포팅본이 고쳐져야 한다." **틀렸다.**

사용자 실측 — **정상 착지가 되면 맵·미니맵에 표시된다.** 표시가 안 됐던 것은 낙하산이
안 접히거나 소리가 계속되던 그 판들, 즉 **착지 완료 처리가 끊긴** 판들이었다. 그러니
표시는 별개 문제가 아니라 같은 원인의 세 번째 증상이고, Finalizer 로 같이 고쳐진다.

내가 틀린 경로: 디컴파일에서 나침반 모드의 `ShowAirdrop` 이 안 불리는 것을 보고,
"사용자가 말한 표시" 를 그 HUD 표시로 **단정**했다. 사용자는 맵·미니맵을 말했는데
내가 확인하지 않고 한쪽으로 몰았다. 나침반 HUD 자체의 표시가 어떤지는 **나는 재지
않았다** — 그것은 여전히 확인되지 않은 별개 항목이다.

정확한 고리(무엇이 "착지 완료" 를 표시 쪽에 알리는가)는 아직 짚지 않았다. 증상이
사라졌으므로 더 파지 않는다.

#### 고친 뒤 실측 (2026-10-31)

```
[AirdropCaller] CheckSurface 의 남의 패치 예외를 삼키도록 걸었다.
[AirdropCaller] CheckSurface 에서 남의 패치가 터졌다. 삼킨다 (1번째) —
  MethodAccessException: Method `GamePanelHUDCompass…RaycastGround(…)' is inaccessible …
[AirdropCaller] 앉았다 — 시작Fall, 앉기전먼지꺼짐, 먼지켜짐, 낙하산남음, 접는중.
[AirdropCaller] 착지한 상자의 반복 소리를 끊었다.
```

사용자 확인 — **착지의 쿵 소리가 나고 낙하산이 저절로 접혔다.**

**쿵 소리가 결정적인 증거다.** `PlayLandingSound()` 는 `CheckSurface()` **뒤**에 있고
그 예외는 **매 착지마다** 터졌으므로, 고치기 전에는 어느 판에서도 쿵 소리가 날 수
없었다. 그것이 들린다는 것은 실행이 `CheckSurface` 를 넘어갔다는 뜻이다 — 상자가
한 점으로 닿았는지 두 점으로 닿았는지(§16.9)와 **무관한** 판정이다. 그래서 착지
한 번으로 충분하다.

`접는중` 이 나오고 `우리가 접었다` 경고가 없는 것도 맞물린다. `TendCrates` 의
낙하산 접기는 이제 **할 일이 없다** — 그래도 남겨 둔다. Finalizer 가 못 걸리는
설치본에서도 증상은 가려야 한다.

소리 끊기는 여전히 돈다. 그쪽은 남의 패치와 무관한 **바닐라 자체의 문제**이기
때문이다(§16.6) — 착지음이 끝나면 연막 소리가 반복으로 켜지고 바닐라는 그것을
영영 끄지 않는다.

**남은 것은 ① 하나다.** 2026-10-31 기준 재현되지 않았다. 계측(`,지면없음`)과
구조(`앉혔다`)는 깔려 있다.

### 16.10 ①은 닫지 않고 **지켜보는 것으로 둔다** (2026-10-31)

고친 뒤의 실측이다.

| 센 것 | 수 |
| --- | --- |
| `앉았다` (새 플러그인으로 앉은 상자) | 6 |
| 그중 `접는중` (바닐라가 스스로 접었다) | 6 |
| `안접음` = ② | **0** |
| `우리가 접었다` (우리 보수가 나설 일) | **0** |
| `안 멈췄다`·`앉혔다` = ① | **0** |

사용자도 다섯 번 넘게 떨어뜨려 전부 정상이라고 확인했다. ①은 `드롭 예약` 40여 건 중
**2026-10-30 07:53 한 번**뿐이다.

#### "다른 것과 같이 고쳐진 것 아닌가" — 아니다

그렇게 보고 싶지만 기계적으로 불가능하다. Finalizer 가 막은 예외는 `CheckSurface` 에서
터지고, `CheckSurface` 는 **`Landed` 분기 안에서만** 불린다(`ClientAirDrop` 안에
호출 지점이 그 하나다). 즉 **앉은 다음**의 일이다. ①은 애초에 `Landed` 에 닿지
못하는 증상이므로 그 예외가 원인일 수 없다.

이번에 넣은 다른 것들도 ①의 경로를 건드리지 않는다 — 내용물 채우기(서버), 소리 끊기,
낙하산 접기는 모두 하강·충돌과 무관하다. ① 구조(§16.8)는 **증상이 났을 때 건지는**
것이지 안 나게 하는 것이 아니고, 났으면 `앉혔다` 가 로그에 남는다. 그 줄이 0건이니
**조용히 구조된 것도 아니다.**

#### 그래서 남기는 판정

①은 **고쳐지지 않았고, 재현되지 않았다.** 둘은 다른 말이다. 원인 가설은 §16.7 그대로다
— 단계 전환은 `TerrainLowPoly` 레이캐스트로, 정지는 Default 층을 무시하는 물리
충돌로 하니 그 둘이 어긋나는 **자리**가 있다. 40여 건에 한 번이라는 빈도도 "특정
지점" 가설과 어울린다.

더 파지 않는다. 추측으로 손대면 멀쩡한 착지를 망칠 수 있고, 다시 나면 그때 답이 로그에
남게 해 뒀다 — 하강 중 `,지면없음`, 그리고 구조할 때 `앉혔다 … (collider 이름, 층 번호)`.
**그 collider 이름과 층 번호가 ①의 마지막 조각이다.** 상자도 그 자리에서 건져진다.

## 17. 프리셋을 모든 프로필에서 쓴다 (2026-11-06, 사용자 요청)

`presets/<profileId>/<id>.json` 이다(`PresetStore.DirFor`). **§7.11 이 그렇게 정했다** —

## 18. 지금 입고 있는 것을 프리셋으로 뽑는다 (2026-11-06, 사용자 요청)

로그인한 플레이어의 **장착 장비 전체**(방어구·주/부/근접 무기·리그/가방 **안의 것까지**)를
프리셋으로 만든다.

### 18.1 지금 계약으로 표현된다 — 바꿀 것이 없다

소스를 읽어 확인했다. `ItemSpec` 이 이미 셋을 들고 있다.

| 뽑을 것 | 쓰는 것 | 근거 |
| --- | --- | --- |
| 가방·리그·파우치 **안의 아이템** | `ItemSpec.Items` (재귀) | "이 품목 **안에** 넣을 것. 격자를 가진 컨테이너여야 한다" |
| 방어구의 방어판·삽입물 | `Slots` / `Fill` | §12 |
| **무기 부착물** | `Slots` (점으로 잇는 경로) | `SlotFiller` 가 완성품 프리셋으로 무기를 세운 뒤, **"사용자가 그 칸을 직접 골랐으면 완성품보다 그쪽이 세다"**. 칸 선택 **창**만 방어구 셋으로 좁혔을 뿐(§12.6) 계약은 일반적이다 |

즉 §18 은 **새 계약이 아니라 변환기**다 — 프로필의 장비 트리를 `ItemSpec` 트리로 옮긴다.

### 18.2 규모 — 실측 (2026-11-06, 로그인 프로필)

장비 루트 밑 1단 슬롯 **15개**, 트리 전체 **379개**, 최대 깊이 **6**.

| 슬롯 | 하위 | 깊이 |
| --- | --- | --- |
| SecuredContainer | **178** | 3 |
| ArmBand | 38 | 2 |
| FirstPrimaryWeapon | 30 | 4 |
| TacticalVest | 29 | 2 |
| SecondPrimaryWeapon | 28 | 4 |
| Holster | 27 | 5 |
| ArmorVest | 13 | 1 |
| Pockets | 10 | 1 |
| Headwear | 9 | 3 |
| Backpack | 2 | 1 |

`ItemSpec` 의 재귀가 깊이 6 을 담는다. 문제는 크기가 아니라 **무엇을 뺄지**다.

### 18.3 정해진 것 (2026-11-06)

1. **보안 컨테이너는 뺀다** — 사용자 결정. 혼자 **178개**이고 타르코프에서 죽어도 남는 칸이라
   보급 상자로 떨어뜨리는 것과 성격이 다르다. `skipped` 에 적어 뺐다는 것을 말한다.
2. **주머니(Pockets)는 넣는다** — 사용자 결정. 실측 10개로 작다.
3. **탄은 지금 계약으로 장전된 채 못 담는다 — 따로 품목으로 넣는다.** 2026-11-06 에 두 길이
   다 막힌 것을 확인했다:
   - `Slots` 는 **경로 → tpl 하나**다. 탄은 `slotId: "cartridges"` 에 **정수 색인**으로 들어가고
     한 탄창에 묶음이 여럿일 수 있다(실측: 같은 탄창에 색인 0 에 4발, 1 에 9발). **수량과 색인을
     담을 자리가 없다.**
   - `Fill` 은 **탄창 칸까지만** 채운다(§15.6 이 "필수만" 규칙에 낸 유일한 구멍이다). 탄은 넣지 않는다 — 그 코드가
     직접 적어 놨다: "완성품으로 세운 총은 프리셋에 탄창이 들어 있어 받는다 … **쏘려면 탄창을
     따로 챙겨야 한다**"(`SlotFiller.cs:401-403`).

   그래서 뽑기는 **탄을 별도 `ItemSpec` 줄로** 내보낸다(tpl + 총 발수). 장전된 탄창을 그대로
   재현하려면 `ItemSpec` 에 탄 전용 표현(색인·수량)을 더해야 하는데, 그것은 이 요청의 범위를
   넘으므로 **하지 않는다**. STM 쪽이 같은 벽에 부딪혀 같은 결론을 냈다(열린 항목 4 — 탄의
   `location` 은 격자 좌표가 아니라 정수 색인이다).
4. **상자 한 칸이 모자라면.** 보급 상자는 10×12=120칸이다(§7.5). 379개를 평면으로 풀면 넘친다 —
   §7.5 가 이미 답을 갖고 있다: **컨테이너를 넣고 그 안에 담는다**(`ItemSpec.Items`). 뽑기는
   가방·리그를 그대로 컨테이너로 살려 내므로 자연히 그 모양이 된다.
5. **같은 tpl 이 여러 칸에 있을 때** 묶을지 줄을 나눌지 — **묶는 쪽**을 권한다(상자 칸을 덜 쓴다). 아직 정하지 않았다.

### 18.4 새 라우트

```
POST /airdrop-caller/extract   { include: ["weapons","armor","rig","backpack", ...] }
→ { preset: { name, icon, bigCrate, items: [ItemSpec...] }, skipped: [...] }
```

- **저장하지 않는다.** 창이 받아서 보여 주고, 사람이 이름을 붙여 저장한다. 뽑자마자 목록이
  늘어나면 실수로 지우기 어렵다.
- `skipped` 에 뺀 것을 적는다(보안 컨테이너, 값을 못 매긴 것 등). **조용히 버리지 않는다**(§7.5).

### 18.5 미리 걸릴 것

- **프로필을 읽기만 한다.** §7.6 의 "프로필에 쓰지 않는다" 는 **쓰기** 금지이므로 어긋나지 않는다.
- 뽑은 프리셋의 tpl 이 **모드 아이템**이면 그 모드를 뺐을 때 조립이 실패한다. 거절하고 `skipped`
  에 적는다.
- `Count` 는 줄 단위다(§12.5). 같은 tpl 이 여러 칸에 있으면 묶을지 줄을 나눌지 정해야 한다 —
  **묶는 쪽**을 권한다(상자 칸을 덜 쓴다).

### 19.3 검증하다 고친 것 — 조용히 버리는 자리 둘

## 20. 용기의 격자를 전부 연다 — 그리고 실제로 재 봤다 (2026-11-07 고침 / 2026-11-08 검증)

§18(장비 뽑기)이 처음으로 **용기를 통째로** 상자에 넣으면서 묵은 결함이 드러났다. 경위는
[HANDOVER-2026-11-07.md](../HANDOVER-2026-11-07.md) §2-A, 고침은 `b8c77eea`.

### 20.1 무엇이 틀렸나

`CrateBuilder.TryOpenContainer` 가 `grids.FirstOrDefault()` 로 **첫 격자만** 열었다. 가방은
격자가 하나라 멀쩡했고, 격자가 여러 개인 리그·워벨트·주머니만 나머지 칸을 못 썼다.

| 용기 | 격자 | 전체 칸 | 첫 격자만 |
| --- | --- | --- | --- |
| 워벨트 | 11개 | 25칸 | **6칸** |
| 주머니 | 4개 | 8칸 | **2칸** |
| BD4 리그 | 4개 | 8칸 | **2칸** |

그래서 뽑은 장비를 상자로 보내면 **15가지가 `(자리 없음)`** 으로 빠졌다. 상자는 497/900 으로
넉넉했는데도. `OpenContainer` 로 바꿔 **격자마다 그릇을 하나씩** 만든다 — `Settle` 이 이미
"그릇을 차례로 두드린다" 라서 호출부는 그대로다. 격자마다 **자기 지도**를 만드는 것이 핵심이다:
`GetContainerMapping` 은 여러 격자를 하나로 합쳐 버려 칸 수는 맞아 보여도 `SlotId` 가 한 격자를
가리킨다.

### 20.2 검증 — 돌고 있는 서버의 조립기로 쟀다 (2026-11-08)

고침을 설치하고도 **하루 동안 검증이 미뤄져 있었다**(조립기는 레이드나 config 드롭으로만 돈다고
보았고, `config.jsonc` 는 기동 때 한 번만 읽히므로 시험 드롭을 넣으려면 서버를 다시 켜야 한다).

**다시 켤 필요가 없었다.** `/airdrop-caller/queue` 가 **예약받을 때 조립을 끝내고** `placed` 를
돌려준다 — 레이드 중이면 그것으로 조립기를 그대로 돌려 볼 수 있다. 부르는 수단이 없어
**[tools/call-airdrop.mjs](../../tools/call-airdrop.mjs)** 를 만들었다(https + 자체 서명 인증서,
`PHPSESSID` 쿠키, **요청·응답 양쪽 zlib** — 창이 하는 왕복과 같다. curl 로는 안 된다).

| 시험 | 넣은 것 | 바라는 답(고친 뒤) | **받은 답** | 고치기 전이라면 |
| --- | --- | --- | --- | --- |
| 격자 4개 리그 | `rig_bankrobber`(4격자·8칸) + 1x1 8개 | 1+8 = **9** | **`placed: 9`, 못 담은 것 0** | 1+2 = 3 |
| 격자 19개 워벨트 | `rig_beltab`(19격자·25칸) + 1x1 **30개** | 1+25 = **26**, 넘친 5개는 보고 | **`placed: 26`, `544fb3f3… (자리 없음) ×5`** | 1+2 = 3 |

두 번째가 §19.4 의 **"격자 넘침 거절이 제대로 뜨는지"** 도 같이 닫는다 — 조용히 버리지 않고
개수까지 적어 돌아온다.

### 20.3 `BigCrate` 의 `FirstOrDefault()` 는 같은 결함이 아니다 — 재 보았다

같은 모양의 코드가 `BigCrate.cs` 에도 있다(베낀 상자의 **첫 격자**만 키운다). 베끼는 원본
`6223349b3136504a544d1608`(`air_drop_common`)을 DB 에서 재 보니 **격자 1개(10×12=120칸)** 다.
키울 격자가 하나뿐이라 고칠 것이 없다. 추측으로 "여기도 같은 버그" 라고 적지 않으려고 쟀다.

### 20.4 값을 치른 것 — 예약은 **취소하기 전에 떨어질 수 있다**

두 시험 모두 예약이므로 끝나고 `/airdrop-caller/cancel` 로 비울 생각이었다. 첫 번째는 비워졌다.
**두 번째는 비우기 전에 실물이 되었다** — 18초 뒤 레이드에 비행기가 떠서(`하늘: 비행기 1, 상자 1`)
`예약된 상자를 보낸다` 로 소비됐고, `cancel` 은 `취소할 예약이 없다` 로 돌아왔다.

즉 **레이드 중에 `queue` 를 시험 삼아 쏘면 그 레이드에 상자가 떨어진다.** 조립 결과만 보고 싶어도
`queue` 는 조립과 예약을 함께 한다 — 떼어 놓을 길이 지금 계약에는 없다. 다음에 재려면 둘 중
하나다: **레이드 밖**에서 `config.jsonc` 에 시험 드롭을 적고 서버를 다시 켜거나(`Drops` 는 기동 때
한 번만 읽힌다), 조립만 하고 예약하지 않는 **마른 조립(dry-run)** 을 `queue` 에 더하는 것이다.

> 덤으로 §19.4 의 **"상자에 실제로 떨어뜨려 보기"** 는 이 사고로 **일어났다** — 워벨트 1개와
> 모르핀 25개가 든 상자가 Lighthouse 에 떨어졌다. 상자를 열어 25개가 다 보이는지는 게임에서만
> 확인된다.

## 21. 마른 조립 — 조립만 하고 예약하지 않는 길 (2026-11-12)

§20.4 의 숙제를 그대로 집었다. **조립과 예약을 떼어 놓았다.**

### 21.1 계약

`POST /airdrop-caller/queue` 의 본문에 `dryRun: true` 를 더한다. 답에도 `dryRun` 이 실려 돌아온다.

| | 평소 | `dryRun: true` |
| --- | --- | --- |
| 빗장 | 모드 꺼짐 · 게임 꺼짐 · 레이드 밖 · 보급 지점 0 · 상자가 하늘에 · 이미 예약 · 쿨다운 | **모드 꺼짐 하나뿐** |
| 조립 | 한다 | 한다 |
| 큐에 넣기 | 넣는다 | **넣지 않는다** |
| 쿨다운 | 쓴다 | **쓰지 않는다** |
| `dropId` | 준다 | **주지 않는다**(플러그인이 꺼내 갈 것이 없다) |
| 돌려주는 값 | `placed`·`attached`·`skipped`·`adjusted` | 같다 |

빗장을 건너뛰는 근거는 하나다 — 그 빗장들은 전부 **예약이 실물이 되는 것**을 지키려고 있다.
예약하지 않으면 지킬 것이 없다. 남긴 `ModEnabled` 는 사람이 끈 것이라 조립도 하지 않는 쪽이 맞다.

판정은 `src/AirdropCaller.Server/QueueGate.cs` 한 곳에 있고, SPT 어셈블리를 쓰지 않아
`src/AirdropCaller.Tests` 가 그 파일만 링크해 **시험 10개**로 지킨다(평소 빗장 7가지와,
마른 조립이 게임 꺼짐·쿨다운·기존 예약을 지나가는 것, 모드를 끄면 둘 다 막히는 것).

### 21.2 창

아래 띠에 **`조립만 보기`** 단추를 더했다. `떨어뜨리기` 와 달리 **레이드·쿨다운·예약과 무관하게**
담을 품목만 있으면 눌린다. 결과 문구는 예약과 섞지 않는다 —
`조립해 봤다 — 2개를 담았다. 예약하지 않았다 — 떨어지지 않는다.`
서버가 `dryRun: true` 로 답하지 않으면 **예약된 것으로 말한다**(떨어질 수 있다는 것을 숨기지 않는다).

### 21.3 실측 (2026-11-12, 게임은 꺼진 채)

서버만 띄우고 라우트에 직접 물었다.

```text
— 상태 —        canQueue=false hasPending=false blockedBy=게임이 안 켜져 있다.
— 마른 조립 —    ok=true dryRun=true dropId=없음 placed=2
— 그 뒤 상태 —   hasPending=false cooldownSeconds=0
— 평소 예약 —    ok=false reason=게임이 안 켜져 있다.
```

서버 로그에도 `[AirdropCaller] 마른 조립 → Common 상자에 2개 — 예약하지 않았다.` 가 남는다.
**조립은 되고 예약은 남지 않는다**는 것이 이것으로 확인됐다.

### 21.4 창을 스스로 찍게 했다 — `--shot`

`AirdropCaller.exe --shot <저장경로.png> [기다릴초]` 로 부르면 창을 사람에게 보이지 않고
PNG 로 찍고 끝낸다(ProfilePorter 에서 화면 여섯 군데를 고친 그 스위치와 같은 것, 2026-11-09).
서버가 꺼져 있어도 찍힌다 — 상태줄에 "서버에 붙지 못했다" 가 뜬 모습 그대로다.
인자가 없으면 평소대로 창이 뜬다. 이번 단추 배치도 이것으로 확인했다(1100x660).

### 21.5 아직 확인하지 못한 것 (일부는 §23 에서 닫혔다)

- **인게임에서 `조립만 보기` 를 눌러 본 적은 없다.** 라우트는 껐다 켠 서버로 확인했고,
  단추는 같은 라우트에 `dryRun: true` 를 실어 보낸다.
- 레이드 **중에** 마른 조립을 했을 때 그 레이드에 아무 일도 없는지 — 코드상 큐를 건드리지 않지만
  게임에서 본 적은 없다. §20.4 가 값을 치른 자리라 다음 레이드에서 한 번 보는 것이 좋다.

## 22. 얼마나 찼는지 말해 준다 — 칸 사용량 (2026-11-12)

### 22.1 왜

지금까지 창이 할 수 있는 말은 **"몇 개 담았다 / 못 담았다"** 뿐이었다. **얼마나 남았는지**는
못 담는 일이 실제로 벌어진 뒤에야 알았다 — 방탄복 20개를 120칸 상자에 넣고 "자리 없음" 이
열네 줄로 돌아온 적이 있다(§CrateBuilder 주석). 마른 조립(§21)과 함께 쓰면 **부르기 전에** 안다.

### 22.2 무엇

`queue` 의 답에 `cellsUsed`·`cellsTotal` 을 더했다. 평소 예약과 마른 조립 **둘 다** 실어 준다.

- 세는 것은 **상자 자기 격자**다. 안에 넣은 가방·리그의 속칸은 세지 않는다 — 사람이 보고 싶은
  것은 "이 상자에 더 들어가나" 이고, 속칸까지 섞으면 900칸짜리 큰 상자에서 숫자가 뜻을 잃는다.
- 셈은 `src/AirdropCaller.Server/GridUsage.cs` 한 곳이다. 칸 지도는 SPT 의
  `TryFillContainerMapWithItem` 이 채운 그대로라 **0 이 빈 칸**이라는 규칙 하나만 쓴다.
  상자가 격자를 여러 개 가지면 합쳐 센다.
- `cellsTotal` 이 0 이면 **모른다는 뜻**이고 창은 아무 말도 하지 않는다(`칸 수를 모른다`).
- 서버 로그에도 붙는다: `… 상자에 2개 · 칸 2/120 (2%) — 예약하지 않았다`.

창의 결과 문구:

```text
조립해 봤다 — 2개를 담았다. 칸 2/120 (2%). 예약하지 않았다 — 떨어지지 않는다.
```

시험은 `GridUsageTests` 11개(빈 격자·일부만 찬 격자·0 이 아닌 값·격자 여럿·격자 없음·백분율
반올림 다섯 가지·칸 수를 모를 때). `QueueGateTests` 10개와 합쳐 **21개**다.

### 22.3 설치 스크립트 — 서버가 떠 있을 때

`install-airdropcaller-server.ps1` 에 `-AllowServerRunning` 을 더했다. 서버가 떠 있으면 DLL 이
잠겨 **덮어쓰기가 조용히 실패한다**(깔린 줄 알고 넘어가는 것이 가장 나쁘다). 그래서 기본은
거부하고, 이 스위치를 주면 **돌고 있는 DLL 을 이름만 바꿔 치우고**(`.dll.locked-<시각>`)
새것을 넣는다. SPT 는 `mods` 에서 `.dll` 만 읽으므로 치운 파일은 로드되지 않는다.
**돌고 있는 서버는 옛 코드를 그대로 쓴다** — 새것은 다음 서버 기동부터다.

## 23. 서버를 다시 켜고 재 봤다 (2026-11-12 20:35)

- **네 번을 잇달아 조립했는데 `hasPending=false`·`cooldown=0`** 이다. 마른 조립이 예약도
  쿨다운도 건드리지 않는다는 것이 반복 호출로 확인됐다(§21.5 의 미확인 항목도 닫혔다).
- 서버 로그(UTC)에도 같은 줄이 남는다:
  `[AirdropCaller] 마른 조립 → Common 큰 상자에 200개 · 칸 200/900 (22%) — 예약하지 않았다.`

### 23.1 그래도 아직 못 본 것

- **인게임**: 창의 `조립만 보기` 단추를 레이드 중에 눌러 본 적은 없다. 라우트는 위처럼
  확인했고 단추는 같은 라우트에 `dryRun: true` 를 실어 보낸다.
- `IcebreakerOffMapGuard` 의 고친 판(§[fixes](../fixes/2026-11-11-icebreaker-offmap-guard.md) §6)은
  **게임 기동이 있어야** 확인된다 — 지금 게임은 꺼져 있다. 다음 기동 로그에서
  `걸었다:` 두 줄과 `[PerfCensus]` 0회를 본다.

## 24. 끌어 맞춘 창 모양을 기억한다 (2026-11-13, 사용자 요청)

창 크기·자리, 세 칸(프리셋·품목·아이템 찾기)의 너비, 품목 표의 칸 너비를 **닫을 때 적고 열 때
되돌린다.** 매번 같은 손질을 다시 하지 않게 하는 것이고, 덤으로 §5-2 에 적어 둔 "프리셋 이름이
잘린다·단추가 두 줄로 접힌다" 가 **사람이 한 번 넓혀 두면 그대로 남는다.**

### 24.1 어디에 적나

설정 파일 하나다 — `airdrop-caller.config.json` 의 `layout`
([`WindowLayout.cs`](../../src/AirdropCaller.App/WindowLayout.cs)). 프리셋·즐겨찾기와 같은 자리이고
서버에는 아무것도 보내지 않는다. **이것은 설정이 아니라 그 사람이 쓰던 배치**다.

### 24.2 너비를 **문자열**로 적는 이유

WPF 의 너비는 픽셀일 수도 별(`*`, 남는 자리를 나눠 갖기)일 수도 있다. 숫자로만 적으면 끌지 않은
칸까지 전부 픽셀로 굳어 **창을 넓혀도 가운데가 늘어나지 않는다.** 그래서 WPF 가 말하는 그대로
적는다 — `"210"`·`"*"`·`"1.5*"`. 가운데 칸은 남는 자리를 받으므로 아예 적지 않는다.

읽는 쪽은 **읽지 못하는 값을 만나면 그 칸만 건너뛴다**(XAML 기본값이 남는다). 설정이 손으로
고쳐지거나 옛 판일 수 있어, 한 칸 때문에 창이 안 뜨면 안 된다.

### 24.3 조심한 것 셋

| | |
| --- | --- |
| **화면 밖이면 자리를 되돌리지 않는다** | 모니터를 떼어 내면 창이 보이지 않는 곳에 뜬다. `VirtualScreen` 안일 때만 쓴다 |
| **최대화는 크기를 되돌린 뒤에 건다** | 사람이 최대화를 풀면 적어 둔 크기로 돌아간다. 최대화 중에 닫으면 `RestoreBounds` 를 적는다 |
| **`--shot` 에서는 적지 않는다** | 찍는 창은 화면 밖(-4000,-4000)에 띄운다. 닫으며 그 자리를 적으면 다음에 사람이 열었을 때 창이 보이지 않는다 (`MainWindow.SuppressLayoutSave`) |

### 24.4 재 본 것 (2026-11-13)

게시 폴더에 `layout` 을 손으로 넣고 `--shot` 으로 찍었다 — 설치본과 사용자의 설정은 건드리지 않았다.

| 넣은 것 | 나온 것 |
| --- | --- |
| `width 900 · height 520` (기본은 1100x660) | **900x520 으로 찍혔다** |
| `presetColumn "320"` (기본 210) | 프리셋 칸이 넓어져 **이름이 안 잘리고 가로 스크롤바가 사라졌다.** 단추 넷도 한 줄에 선다 |
| `searchColumn "240"` (기본 360) | 오른쪽 칸이 좁아졌다 |
| `itemColumns` 둘 | 품목 표의 그 칸들이 지정한 너비로 섰다 |

`--shot` 뒤에도 설정 파일의 `layout` 이 그대로였다 — **찍는 길이 덮어쓰지 않는다**는 것도 이것으로 확인됐다.

### 24.5 아직 확인하지 못한 것

- **사람이 끌어 맞춘 뒤 닫고 다시 여는 길은 보지 않았다.** 위 실측은 *되돌리기* 쪽만 본 것이고,
  *적기* 쪽은 `--shot` 이 일부러 건너뛴다. 창을 끌어 맞추고 닫았다가 다시 열어 그대로인지 본다.
- 칸 고르기 창(`SlotWindow`)은 그대로다 — 이번 범위가 아니다.

## 25. 레이드 중에 `조립만 보기` 를 눌러 봤다 (2026-11-13) — §23.1 이 닫혔다

§21.5·§23.1 이 "라우트로만 확인했고 레이드 중에 눌러 본 적은 없다" 로 남겨 둔 자리다.
사용자가 **Sandbox_high 레이드 중에** 눌렀고 화면을 찍어 보내 주었다.

창의 상태줄:

```text
레이드 중 — Sandbox_high        보급 지점 0개
조립해 봤다 — 76개를 담았다. 칸 548/900 (61%). 방어판·부속 188개를 붙였다. 예약하지 않았다 — 떨어지지 않는다.
```

서버 로그가 같은 말을 한다:

```text
[AirdropCaller] 마른 조립 → Common 큰 상자에 76개 (부속 188개 붙임) · 칸 548/900 (61%) — 예약하지 않았다.
```

그 직후 `/airdrop-caller/state` 를 물었다:

```json
{"inRaid":true,"map":"Sandbox_high","hasPending":false,"cooldownSeconds":0,
 "canQueue":false,"blockedBy":"이 맵에서는 보급기가 뜨지 않는다."}
```

- **레이드 중에 눌러도 그 레이드에 아무 일도 없다** — 예약도 쿨다운도 서지 않았다(§20.4 가 값을 치른 자리).
- **§21.1 의 계약이 그대로 보인다.** 이 맵은 보급 지점이 0개라 평소 예약은 `canQueue=false` 로 막혀
  있는데, 마른 조립은 **그 빗장을 지나** 조립까지 했다. 빗장이 지키는 것은 "예약이 실물이 되는 것"
  뿐이라는 설계가 화면으로 확인됐다.
- **`보급 지점 0개` 는 결함이 아니다** — Sandbox_high(그라운드 제로)에 보급 지점이 없는 것이고,
  서버가 그 이유를 문장으로 돌려준다.
