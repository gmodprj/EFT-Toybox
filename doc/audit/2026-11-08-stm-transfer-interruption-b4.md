# 스태시 교환 — 끊김 실험 (계획 6 B4, 2026-11-08)

전송 도중 서버를 끊어 복구 판정 **세 가지를 모두 실제로 만들었다**. `StopAndReport` 는 이번이 처음이다.

게임은 띄우지 않았다 — 서버만 올리고 `tools/stm-call.mjs` 로 라우트를 직접 쏘았다.
프로필 9개와 `stm-teammates` db 전체를 먼저 백업하고, 실험이 끝난 뒤 **전부 되돌렸다**(§5).

## 0. 끊는 방법 — 시각이 아니라 **사건**으로

인계문서는 "쏘고 N ms 에 `taskkill`" 로 적혀 있었다. 그대로 하면 절단면이 추측이 된다(한 번은
저장 전, 한 번은 저장 후에 떨어진다). 그래서 **파일이 쓰이는 순간**에 끊는 도구를 만들었다 —
[tools/kill-spt-on-write.ps1](../../tools/kill-spt-on-write.ps1).
`FileSystemWatcher.WaitForChanged` 로 그 파일의 쓰기를 기다리다 `Stop-Process -Force` 한다.

전송의 쓰기 순서(설계 §6-8, `StmStashTransferService`)가 그대로 절단면 세 개를 준다:

```
Prepare(db) → BeginSourceWrite(db) → 출처 프로필 저장 → RecordDestinationItemIds(db)
            → BeginDestinationWrite(db) → 목적지 프로필 저장 → MarkCommitted(db) → Verify(디스크 재독) → 닫기
```

| 실험 | 무엇이 쓰이는 순간에 끊었나 | 그 시점의 실물 |
|---|---|---|
| 1 | 저널 **db** (= `Prepare`) | 아직 아무것도 안 움직였다 |
| 2 | **출처** 프로필 json | 출처에서만 빠졌다 |
| 3 | **목적지** 프로필 json | 양쪽 저장이 다 끝났다 |

`-Settle` 은 사건 뒤 그 파일의 **마지막 바이트가 `}`** 가 될 때까지 1ms 간격으로 기다린 뒤 끊는다
(프로필을 쓰는 도중에 죽여 반토막 파일을 만들지 않으려는 것). 실험 2·3 에서 9~12ms 기다렸고
두 프로필 모두 **성하게** 파싱됐다.

## 1. 실험 1 — RollBack

끊김: 저널 db 가 쓰인 지 **6ms** 뒤(07:37:47.251 KST). 프로필 두 개는 수정 시각조차 그대로.

기동 로그:

```
[STM] 끝나지 않은 전송 'db5bd0485e2a4f10abcb0da86ca813c4' 을(를) RollBack 로 닫았다(실물은 이미 일관된 상태).
```

저널은 다시 `{"entries":[]}`, 아이템 2개는 출처에 그대로. **기대와 같다.**

## 2. 실험 2 — StopAndReport (처음)

끊김: 출처 프로필이 **다 쓰인 뒤 21ms**. 그 순간의 사실 — 출처 1,741개(2개 빠짐) / 목적지
403개(안 받음) = **양쪽 다 없음**.

기동 로그(Error 한 줄, 줄바꿈만 넣었다):

```
[STM] 끝나지 않은 전송을 자동으로 정할 수 없어 두 프로필의 팀원 편집을 막는다.
항목 'dfcfd4ff9ebc45c3a5ab4808bbe683cc' / 종류 'stash-transfer' / 단계 Prepared / 시작 2026-11-07 23:28:17Z(UTC) /
출처 프로필 '6adc26693f5b5290609ea366' / 목적지 프로필 '6aeedfe7e12f66949c9c74dc' /
아이템 [6aebcdd18461f86ad47dc598, 6aebcdd18461f86ad47dc599] / 목적지 기록 id [같은 둘]. 저널 문서
'stm-transfer-journal.json' 는 데이터베이스 파일 'E:\...\stm-teammates\6adc26693f5b5290609ea366.db' 안에 있다.
아이템이 복제됐거나 사라졌을 수 있다: 두 프로필의 장비·스태시를 직접 확인해 바로잡은 뒤 이 항목을 닫아야 편집이 풀린다.
```

세 가지를 더 봤다.

1. **열린 항목이 남았다** — `tools/dump-stm-journal.ps1` 로 읽은 그 항목:
   `stage: "Prepared"`, `sourceWriteStarted: true`, **`destinationWriteStarted: true`**,
   `destinationItemIds` 기록됨. 즉 **"목적지 쓰기 시작" 까지 적힌 뒤 그 저장이 끝나기 전에** 끊겼다.
   단계만 보면 `Prepared` 인데 두 사실은 둘 다 참인 모양 — 머리 주석이 말한 "단계만으로는 구별할 수
   없다" 가 실물로 나왔다. 판정은 실물(양쪽 다 없음)을 보고 멈췄다.
2. **관문이 막았다** — 다른 아이템으로 전송을 쏘니
   `이 팀원에게 끝나지 않은 전송 기록이 있어 옮기지 않았습니다. 그 기록을 닫은 뒤 다시 하세요.`
3. **출구가 열렸다** — `/stm/members/close-transfer` 로 닫았다.
   `acknowledged:false` → `경고를 확인하지 않아 닫지 않았습니다` / `acknowledged:true` → `err:0`,
   그 뒤 저널은 비고 전송이 다시 된다. (`reportedStopped` 조건대로 **보고된 항목만** 닫힌다.)

## 3. 실험 3 — RollForward

끊김: 목적지 프로필이 다 쓰인 뒤 **18ms**. 그 순간 출처 1,740개 / 목적지 404개(아이템 가짐).

기동 로그:

```
[STM] 끝나지 않은 전송 'de01d9f61fc24e00aa754d85b5b9f9cb' 을(를) RollForward 로 닫았다(실물은 이미 일관된 상태).
```

**두 번째 저장이 끝난 뒤 18ms 가 지나도 항목이 아직 열려 있었다** — `MarkCommitted` → `Verify`
(프로필 두 개를 디스크에서 다시 읽는다, 1.6MB + 147KB)가 그만큼은 걸린다는 뜻이다. 그 창을
우리가 처음 쟀다. (18ms 는 이번 측정값이고 하한이 아니다.)

## 4. 만들지 못한 모양 — "양쪽 다 가짐"

`StopAndReport` 로 가는 또 하나의 길인 **복제**(양쪽이 다 가진 상태)는 **이 순서로는 끊어서 만들 수
없다.** 빼는 쪽이 먼저이기 때문이다(설계 §6-8) — 끊기면 늘 "출처만" 또는 "양쪽 다 없음" 으로 떨어진다.
복제가 나오려면 목적지 저장이 성공한 뒤 출처 저장이 **되돌려지는** 다른 종류의 실패가 필요하다.
그 모양은 단위 시험(`TransferJournalPolicy`)에만 있고 실물로는 아직 없다.

## 5. 되돌린 것

실험 2 는 아이템 2개를 디스크에서 **실제로 잃고**, 실험 3 은 1개를 실제로 옮겼다. 그래서 서버를
닫고 `backup/b4-before-2026-11-08/`(프로필 9개 + db 전체)에서 **전부 되돌렸다.** 복원 뒤 실측:

```
프로필 9 / 아이템 5104 / 중복 11건 / 플레이어 포함 0건      ← 실험 전과 같은 값
6aebcdd18461f86ad47dc598 · 599 · 6ae27eac0eb61dba84048c4a → 모두 6adc2669(Nomad) 에만
node tools/check-stm-installed.mjs  → OK — 설치본이 빌드와 같다
node tools/check-install-records.mjs → OK — 0/0
```

## 6. 값을 치르고 얻은 것

- **SPT 는 프로필을 "지우고 다시 만드는" 식으로 저장한다.** 감시 사건이 `Changed` 가 아니라
  **`Deleted`** 로 떴다. 프로필 저장을 파일로 감시하려면 `Deleted`·`Created` 도 사건으로 봐야 한다.
- **전송 라우트는 팀원을 숫자 `aid` 로만 찾는다.** `profileId` 만 보내면
  `그 팀원을 찾지 못해 옮기지 않았습니다` 로 거부된다(`StmProfileMemberResolver.ResolveFrom` 이
  `int.TryParse` 로 시작한다). 첫 시도가 여기서 헛돌았다 — 그래서 저널이 열리지도 않았고,
  감시 도구는 아무 사건도 못 봤다. **거부도 "안 움직임" 의 한 종류다.**
- **끊김 실험은 끝나고 치우는 것까지가 실험이다.** 실험 2 의 상태는 "아이템이 사라진 프로필" 이고,
  그대로 두면 사용자의 스태시가 두 칸 비어 있다. 백업을 먼저 뜨지 않았다면 되돌릴 수 없었다.
