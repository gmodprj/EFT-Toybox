# 스태시 교환 — 전송 뒤 파일 대조 (2026-11-08)

[HANDOVER-2026-11-07-2.md](../HANDOVER-2026-11-07-2.md) §2 가 "아직 확인하지 않은 것" 으로 남긴
**전송 뒤의 프로필·저널 대조**를 했다. 화면이 아니라 **디스크의 파일**만 봤다.

새 레이드를 돌 필요가 없었다 — SPT 가 주기적으로 떠 두는
`user/profiles/backups/<UTC 시각>/` 이 그대로 **전송 전 스냅샷**이다(폴더 이름은 UTC, 안의 파일은
복사 시점의 수정 시각을 그대로 들고 있다). 그래서 어제(2026-11-07) 저녁의 전송을 지금 대조할 수 있었다.

## 1. 무엇이 일어났나 (서버 로그, UTC)

`spt20261107.log` 의 `스태시 전송 완료` 줄 **17개** — 아이템 **52개**(안에 든 것까지).

| 방향 | 횟수 | 아이템 |
|---|---|---|
| 플레이어 → 팀원 | 12 | 33 |
| 팀원 → 플레이어 | 5 | 19 |

상대는 Wraith(`6aeedfe7`)와 Banshee(`6ae5870e`), 플레이어는 Nomad(`6adc2669`).

## 2. 세 구간을 id 수준으로 대조했다

"건너간 id" = 전 스냅샷에서 A 에 있고 후 스냅샷에서 B 에 있는 id(전 스냅샷에서 이미 양쪽에 있던
것은 기준선으로 뺀다). **아이템 id 는 그대로 건너가는 설계**라서 이 셈이 성립한다.

| 구간(UTC) | 로그가 말한 것 | 대조 결과 |
|---|---|---|
| 11:05:30 → 11:18:46 | 플레이어→팀원 6회, 20개 | Nomad → Wraith **20개** · 받는 쪽 20/20 · **빼는 쪽에 0** |
| 11:25:10 → 11:46:40 | 팀원→플레이어 19개, 되돌려 보낸 2개 | Wraith → Nomad **17개**(19−2) · 받는 쪽 17/17 · **빼는 쪽에 0** |
| 11:52:34 → 12:13:53 | 플레이어→팀원 2회, 4개 | Nomad → Wraith **4개** · 받는 쪽 4/4 · **빼는 쪽에 0** |

세 구간 모두 **로그의 개수와 파일의 개수가 정확히 같다.** 한쪽만 보면 복제를 통과시키므로 양쪽을
봤다 — 받는 쪽에 전부 있고 빼는 쪽에 하나도 남지 않았다.

두 번째 구간의 17 vs 19 는 손실이 아니다. 같은 구간 안에서 11:39:20 에 2개가 팀원→플레이어로 왔고
11:39:24 에 **그 2개가 되돌아갔다** — 스냅샷 기준으로는 제자리이므로 "건너간 id" 에 들지 않는다.
로그의 한 줄(`플레이어 → 팀원 … 고른 1개, 안에 든 것까지 2개`)이 그 왕복을 적고 있다.

**대조하지 못한 7개** — 맨 처음 두 건(10:23:13 의 2개, 10:23:36 의 5개, 상대는 Banshee)은
가장 오래된 백업(`10-26-38`, 안의 Banshee 파일은 10:23 에 저장됨)이 **이미 그 전송 뒤**라서
전 스냅샷이 없다. 아래 중복 검사만 이 7개를 덮는다.

## 3. 복제는 생기지 않았다 (프로필 전체)

프로필 9개의 아이템 id 를 모아 **둘 이상의 프로필이 같은 id 를 가진 건수**를 네 스냅샷에서 셌다.

| 스냅샷 | 아이템 | 중복 id | 그중 플레이어가 낀 것 |
|---|---|---|---|
| 10-26-38 | 5,086 | 11 | **0** |
| 11-52-34 | 5,143 | 11 | **0** |
| 12-13-53 | 5,093 | 11 | **0** |
| 13-46-01 | 5,104 | 11 | **0** |
| 지금 | 5,104 | 11 | **0** |

**11건은 전송과 무관하다** — 전송이 한 건도 없던 시점부터 그대로이고, 전부 팀원 프로필끼리
공유하는 SPT 프로필 틀의 기본 장비다(5~8개 프로필이 같은 id 를 든다). 플레이어 프로필이 낀 중복은
**어느 시점에도 0건**이다. 즉 전송이 만든 복제는 없다.

## 4. 전송 저널은 비어 있다

`stm-transfer-journal.json` 은 암호화 DB(LiteDB + AES-GCM) 안의 레코드라 눈으로 볼 수단이 없었다.
읽기 전용 도구를 만들었다 — [tools/dump-stm-journal.ps1](../../tools/dump-stm-journal.ps1).
`.db` 를 **복사해서** 열므로 서버가 돌고 있어도, 파일이 잠겨 있어도 된다.

```
pwsh -File tools/dump-stm-journal.ps1 -ProfileId 6adc26693f5b5290609ea366
  == 6adc26693f5b5290609ea366  — stm-transfer-journal.json
     항목 0개                         (원문: {"entries":[]})
```

문서가 **있다**는 것은 `Prepare` 가 항목을 적었다는 뜻이고, `entries` 가 **비었다**는 것은 그 항목이
전부 닫혔다는 뜻이다(`Verify` → `CloseIf` 가 항목을 지운다 —
[StmTransferJournal.cs](../../src/SptTeamManager/server/Services/StmTransferJournal.cs) `CloseIf`).
닫지 못한 항목은 남고 `[STM] 전송 '…'` 오류 줄이 난다 — 로그에 **그런 줄이 한 줄도 없다.**
17건 전부가 열렸다 닫혔다.

## 5. 남은 것

- **B4 끊김 실험** — 전송 도중 서버를 끊어 `RollForward`·`RollBack`·`StopAndReport` 를 보는 것.
  이 대조는 "끊기지 않은 전송" 만 덮는다. 이제 저널을 들여다볼 수단이 있으니 끊긴 뒤의 항목도
  눈으로 볼 수 있다(§4 의 도구).
- 맨 처음 7개의 구간 대조(§2) — 전 스냅샷이 없어 못 한다. 다음 전송 때는 **백업 폴더 시각을 먼저
  확인하고** 전송하면 구간이 깨끗하게 잡힌다.
