# 계획 5 — 프로필 팀원의 스태시·장비를 플레이어 것과 똑같이 다룬다

작성 2026-11-03. 사용자 지시가 이 계획의 한 줄 목표다:

> **프로필 팀원의 스태시와 장비(보안 컨테이너 포함)는 로그인한 플레이어의 것과 무조건 동일하게 동작해야 한다.**

지금 편집기가 할 수 있는 것은 **슬롯에 통째로 끼우고 빼기** 뿐이다. 아래 §1 이 플레이어 화면과 다른
점 전부이고, §2 가 "되는 방법" 이다 — 셋 중 둘은 **필요한 코드가 이미 레포 안에 있다**.
전제와 읽는 법은 [STM-HANDOVER](../STM-HANDOVER.md), 설계는
[specs/2026-10-31-spt-team-manager-design.md](../specs/2026-10-31-spt-team-manager-design.md).

## 1. 지금 다른 것 (2026-11-03 인게임 실측)

| | 조작 | 팀원 편집기 | 막는 자리 | 증거(그날 화면 문구) |
|---|---|---|---|---|
| 1 | 가방·리그·주머니 **칸(격자)에 넣기** | **안 됨** | `ProfileGearEditPolicy` 의 목적지 판정이 **슬롯 어휘**만 안다 | `슬롯 'GridView (1)' 은(는) 아는 장착 슬롯 이름이 아니어서 편집하지 않습니다.` |
| 2 | 묶음 **나누기·합치기**(탄 860발에서 50발만) | **안 됨** | `GearEditBatchPlanner` 가 새 id 를 거절한다. 그 뒤의 디스크 재독 대조도 "id 집합이 같다" 에 기댄다 | `편집 중 새로 생긴 아이템 '6ae9a1ba…' 이(가) 있어 저장하지 않습니다.` |
| 3 | **보안 컨테이너 칸** | **화면에 아예 없다** | EFT 의 그 장비 편집 화면이 그 칸을 그리지 않는다(우리가 숨긴 것이 아니다) | 화면에 주무기1·2·권총집·칼집·전술 조끼·완장·주머니·특수 슬롯·배낭만 있다 |
| 4 | 한 번에 **맞바꾸기**(A 자리에 B, B 자리에 A) | **거절** | 순서 고리 - 중간 자리가 필요하다(2026-11-03 에 들어간 규칙) | `순서를 정할 수 없어 저장하지 않습니다.` |
| 5 | 아이템 **컨텍스트 메뉴**(탄창 비우기·장전·검사) | 없다 | 편집기가 드래그만 다룬다 | 사용자: "탄창제거 등의 커맨드가 출력 안 됨" |

**차이가 아닌 것 하나.** 보안 컨테이너·주머니·완장·칼집 **자체**를 장비 칸에서 떼는 것은 거부하는데,
**플레이어 화면도 그것을 못 한다**. 같게 만들어야 하는 것은 **그 안의 내용물**이고, 그것은 1번에 속한다.

## 2. 되는 방법 — 재료는 이미 있다

- **좌표는 화면이 이미 알고 있다.** `EditorItemState.LayoutKey` 가 칸 위치를 들고 있고, 지금은
  "저장되지 않는 변화" 로 **세기만** 한다(`GearEditPlan.LayoutOnlyCount`). 전선에 싣지 않았을 뿐이다.
- **격자에 놓는 서버 코드도 이미 있다.** `StmGearEditService.TryPlaceInStash` 가 용기 템플릿의 `Grids`
  에서 칸 크기를 읽고 `InventoryHelper.GetContainerMap` + `PlaceItemInContainer` 로 **빈 자리를 찾아**
  `ParentId`·`SlotId`·`Location` 셋을 쓴다. 스태시 루트에 묶여 있을 뿐, **용기 아무거나로 일반화**하면 된다.
- **수량을 다루는 코드도 PIT 에 있다.** `AddCartridgesToMagazine`·`CreateCartridges`(쪼개기·만들기),
  `GetItemStackCount`. 우리가 새로 발명할 것은 "복제가 없다는 증명" 쪽이다.

## 3. Task 쪼개기 — **§6 이 이것을 대체한다**(아래를 먼저 읽어라)

### Task 1 — 격자 목적지 (가방·리그·주머니·보안 컨테이너 **안**)
- **전선**: `StmGearEditItem` 에 선택 항목 `location`(x·y·rotation). **없으면 서버가 자리를 찾는다** -
  지금 벗기기와 같은 동작이고, 클라이언트가 좌표를 못 줄 때의 안전한 기본값이다.
- **정책**: 목적지가 **그 용기의 격자**면 허용한다. 격자 이름의 권위는 **그 용기 템플릿의 `Grids`** 이고,
  슬롯 어휘(`GearSlotFacts`)와 **같은 방식**으로 서버가 사실을 실어 준다(격자가 받는 종류 필터 포함).
  읽지 못하면 거부(닫힌 쪽, 불변식 2).
- **서비스**: `TryPlaceInStash` → `TryPlaceInContainer(containerId, gridName, …)` 로 일반화한다.
  자리를 못 찾으면 **전체 취소**(지금과 같다). 격자 자리 찾기의 집은 계속 하나다.
- **재독 대조**: 좌표 기대가 네 갈래가 된다 - 스태시 격자(있음)·**용기 격자(있음)**·탄 자리(색인)·그 밖의 슬롯(없음).
- **관문**: 가득 찬 리그에 넣기 → 거절 + 아무것도 안 바뀜(관문 8 이 여기서 닫힌다), 겹치는 좌표 없음,
  리그에서 꺼낸 것을 **같은 칸으로 되돌리기**.

### Task 2 — 보안 컨테이너 패널을 편집기에 그린다
- 화면에 칸이 없으면 내용물을 드래그할 수 없다. STM 모드에서만 패널 하나를 더한다(용병 화면은 그대로).
- 컨테이너 **자체**는 계속 못 뗀다(플레이어와 같다). 레이드 사망 때 보안 컨테이너 내용물이 남는다는
  계획 2 의 약속과 충돌하지 않는지 함께 본다 - 편집으로 넣은 것도 그 약속을 받는다.

### Task 3 — 수량(쪼개기·합치기)
- 전선에 `count`. **쪼개는 것은 서버가 한다** - 클라이언트가 만든 새 id 를 받으면 그 자체가 복제 경로다.
- 디스크 재독 대조를 "id 집합" 에서 **"id 집합 + tpl 별 수량 합"** 으로 넓힌다. 저널은 여전히 쓰지 않는다
  (한 프로필 안의 이동이다).
- 이 계획에서 **가장 위험한 자리**다. 수량이 새면 그대로 복제다. 테스트를 먼저 쓰고, 인게임 관문에서
  "편집 전후 그 프로필의 tpl 별 총 수량이 같다" 를 `tools/stm-profile-diff.mjs` 에 더해 기계가 보게 한다.

### Task 4 — 한 번에 맞바꾸기
- 지금은 고리로 거절한다. **중간 자리를 쓰는 2단계**로 서버가 풀어 준다(그 팀원 스태시를 임시 경유).
  임시 경유가 실패하면 전체 취소다. 풀 수 없는 고리는 그대로 거절한다.

### Task 5 — 컨텍스트 메뉴
- Task 1·3 이 끝나면 탄창 비우기·채우기는 **드래그로** 된다. 그래도 남는 것(검사·장전 애니메이션 등)만
  메뉴로 다룬다. 이 Task 는 앞 넷이 끝난 뒤에 범위를 다시 잰다.

## 4. 넓혀도 바뀌지 않는 것

1. **출처는 그 팀원의 것뿐.** 플레이어 스태시는 영원히 출처가 아니다(설계 §6-4·§6-5).
2. **쓰기는 한 번** + 디스크 재독 대조. 반쯤 적용된 상태를 만들지 않는다.
3. **떼어낼 수 없는 자리**(주머니·보안 컨테이너·완장·칼집·영구 조각)는 그대로 지킨다 - 플레이어 화면도 같다.
4. **고리 금지**, **자리 지어내기 금지**(좌표는 화면이 주거나 SPT 가 찾는다), **테스트 먼저**.
5. 거절은 **사유와 함께**. 조용히 버리는 변화를 만들지 않는다.

## 5. 이 계획이 끝났다고 말할 수 있는 조건

프로필 팀원 하나를 골라 **플레이어 자신의 인벤토리에서 하는 것과 같은 조작**을 화면에서 한 바퀴 돌릴 수 있다:
리그 칸에 탄창 넣기, 가방에서 꺼내 끼우기, 보안 컨테이너에 열쇠 넣기, 탄박스에서 탄 50발만 떼어 탄창 채우기,
두 자리 맞바꾸기. 그리고 **편집 전후 프로필의 아이템 id 집합과 tpl 별 수량 합이 모두 설명된다**
(`tools/stm-profile-diff.mjs`).

## 6. 다시 쓴 계획 (2026-11-03 저녁) — **조작을 하나씩 세지 않는다**

사용자가 못을 박았다: **"로그인한 플레이어 프로필의 스태시 및 장비창에서 가능한 동작은 하나도 빠짐없이
동료창에서 가능해야 한다."** §3 은 조작을 하나씩 세어 열어 주는 계획이었고, 그 방식으로는 이 요구를
만족할 수 없다 - 세다 보면 늘 빠진다(열기·나누기·합치기·장전·접기·태그·검사·버리기…).

### 6-1. 지금 설계가 막는 지점은 **두 곳뿐**이다

실측으로 좁혔다.

1. **화면의 조작 메뉴.** 편집기는 이미 **진짜 EFT `InventoryController`** 를 들고 있다
   (`TryCreateStmGearEditorProfile` 이 `editorProfile` + `editorInventoryController` 를 만들고
   `ItemUiContext.Configure` 에 넘긴다). 즉 **분할·합치기·열기·장전은 화면 쪽에서 이미 가능한 동작**이다.
   막는 것은 우리가 넘긴 **컨텍스트 타입** `EItemUiContextType.TransferItemsScreen` 이다(PIT 에서 그대로
   물려받았다) - 그래서 오른쪽 클릭 메뉴가 `상세정보·버리기·SEARCH IN STASH·ITEM INFO` 넷으로 얇고,
   **탄박스 열기와 묶음 나누기가 아예 없다**. 메뉴를 만드는 것은 `GetItemContextInteractions` 이고,
   게임 어셈블리에 `EItemUiContextType.Inventory` 가 있다(바이트로 확인).
2. **저장 경로가 "이동" 만 표현한다.** `GearEditBatchPlanner` → `/stm/members/edit-gear` 는
   "이 아이템을 이 부모의 이 슬롯으로" 의 목록이다. 분할·합치기는 **아이템 id 가 생기고 사라지는** 조작이라
   이 모양으로는 적을 수 없다(그래서 `편집 중 새로 생긴 아이템 …` 으로 거절된다).

### 6-2. 되는 방법 — **최종 상태를 제출하고, 보존을 증명한다**

조작의 종류를 서버가 알 필요가 없다. 편집기가 끝난 뒤의 **그 팀원 인벤토리 전체**를 제출하고, 서버는
"이 변화가 정당한가" 만 본다. 그러면 **어떤 조작이든** - 지금 것도, 다음 패치에서 EFT 가 더하는 것도 - 그대로 통과한다.

받아들이는 조건(전부 기계가 본다):
- **바깥에서 들어온 id 가 없다.** 제출된 모든 id 는 편집 시작 때 그 팀원의 것이었거나, **분할로 생긴 것**이다.
- **tpl 별 총 수량이 같다.** 묶음을 나누고 합쳐도 총합은 그대로다 - 복제는 여기서 걸린다.
- **구조가 그대로다.** 주머니·보안 컨테이너·완장·칼집·인식표는 제자리에 있다(`IsStructuralSlot`).
- **두 트리가 멀쩡하다.** 고리 없음, 루트 둘 유지, 모든 아이템이 두 루트 중 하나에 매달려 있다.
- **플레이어 프로필은 한 글자도 안 바뀐다**(출처가 그 팀원의 것뿐이라는 규칙의 다른 표현).
- 그리고 지금처럼 **쓰기 한 번 + 디스크 재독 대조**.

이것이 PIT 의 "제출된 것이 곧 새 상태" 와 다른 점: PIT 는 제출된 것만 보고 **빠진 것을 아무도 찾지 않는다**.
위 조건은 **빠진 것과 끼어든 것을 둘 다** 본다(이미 있는 `CheckStashConservation` 의 확장이다).

### 6-3. Task (이 순서로)

| Task | 무엇 | 끝났다고 말할 수 있는 것 |
|---|---|---|
| **A** | 컨텍스트 타입을 플레이어 화면의 것으로 바꾸고 메뉴를 연다 | 탄박스 열기·묶음 나누기·장전이 **메뉴에 뜬다** |
| **B** | 최종 상태 제출 라우트(`/stm/members/apply-inventory`)와 §6-2 의 보존 검사 | 나눈 탄을 탄창에 넣고 저장하면 **저장된다** |
| **C** | 보안 컨테이너 패널을 편집기에 그린다 | 보안 컨테이너 칸이 보이고 내용물을 넣고 뺀다 |
| **D** | 옛 경로(`edit-gear`) 정리 | 두 경로가 공존하지 않는다 - 하나만 남는다 |
| **E** | 인게임 관문 한 바퀴 | 플레이어 화면에서 하던 조작을 팀원 화면에서 **하나씩 따라 해 본다** |

**위험이 옮겨 간다는 것을 적어 둔다.** 지금은 "서버가 최종 집합을 만든다" 가 안전장치였다. B 이후에는
**클라이언트가 최종 집합을 제출**하므로, 안전은 전적으로 §6-2 의 검사에 달린다. 그래서 B 는 검사부터
테스트로 쓰고(복제·소실·구조 손상·외부 id 를 각각 거절하는 테스트), 그 다음에 라우트를 연다.
