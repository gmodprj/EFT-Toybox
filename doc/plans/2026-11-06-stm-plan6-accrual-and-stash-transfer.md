작성 2026-11-06. 사용자 요청 1·2 다. 요청 3(Airdrop)·4(새 export/import 모드)는 **다른 코드베이스라

## 1. 지금 할 수 있게 된 이유

**저널 복구 경로가 2026-11-06 에 증명됐다.** 구매를 쏘고 127ms 에 서버를 끊어 `Committed` 로 열린
항목을 만들었고, 다음 기동이 `끝나지 않은 전송 '58e99ccc…' 을(를) RollForward 로 닫았다` 를 찍었다.
복구 뒤 돈·아이템이 그대로였고 복제 0 이다(WORKLOG "전송 저널 복구 경로").

설계 §6-5 가 스태시 전송을 1차에서 뺀 이유가 "저널이 실전에서 검증된 뒤에 붙인다" 였으므로,
**B부의 전제가 풀렸다.**

## 2. 반드시 지킬 것 (인계 문서 §3 의 불변식 11가지에 더해)

1. **더하는 쪽은 여기서 처음 쓴다.** 지금까지 STM 이 프로필에 한 것은 **빼기**와 **한 프로필 안의
   이동**뿐이다. A부는 설계 §4 가 "유령 재산"·"조용히 망가진다" 로 못박은 자리를 건드린다.
2. **경험치는 되돌릴 수 없다**(설계 §6-6 1번). 한 번 적립되면 끝이다. 그래서 A부는 **멱등 키가
   먼저**고 적립이 나중이다.
3. **숫자의 출처는 클라이언트다**(§6-6). 서버는 봇이 무엇을 했는지 모른다. 클라이언트가 팀원별로
   세어 넘기고 서버가 카운터 키로 번역한다 — 새로 만드는 것은 **번역 층**이다.
4. **B부는 §6-4 의 "출처는 본인 스태시뿐" 을 처음으로 깬다.** 그래서 §6-5 가 정한 규칙을 그대로
   따른다: **별개 화면**, 건넨 순간 소유가 넘어간다, **3단 저널**을 쓴다.
5. **원시 카운터만 쓴다**(§5-8). 생존률·K/D·평균 생존 시간은 게임이 계산한다. 비율을 직접 쓰면
   그 프로필로 로그인했을 때 어긋난다.

## 4. B부 — 플레이어 ↔ 팀원 스태시 교환 (설계 §6-5)

### 규칙 (설계가 이미 정해 둔 것)

- **별개 화면이다.** 장비 편집기에 섞지 않는다.
- **건넨 순간 소유가 넘어간다.** 중간 상태를 두지 않는다.
- **3단 저널을 쓴다.** 프로필 둘을 고치는 조작이므로 §6-8 그대로:
  `Prepare` → `BeginSourceWrite`(빼는 쪽 먼저) → `RecordDestinationItemIds` →
  `BeginDestinationWrite` → `MarkCommitted` → `Verify`.
