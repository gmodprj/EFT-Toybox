# 계획 4 — 프로필 팀원의 장비 꾸러미 (저장된 빌드로 입히기)

작성 2026-11-02. **AI 타입(전술) 변경은 같은 날 끝났다**(아래 §0). 이 문서가 다루는 것은 남은 절반,
**장비 꾸러미**다. 전제와 읽는 법은 [STM-HANDOVER](../STM-HANDOVER.md), 설계는
[specs/2026-10-31-spt-team-manager-design.md](../specs/2026-10-31-spt-team-manager-design.md).

> **이것이 설계 §6-5 가 미뤄 둔 그 조작이다.** 플레이어의 돈과 팀원의 프로필을 **한 번에** 고친다.
> 지금까지 STM 의 모든 쓰기는 프로필 **하나** 안에서 끝났다(장비 편집은 그 팀원 안의 이동이다).
> 그래서 [전송 저널](../WORKLOG.md)(`StmTransferJournal`)이 **처음으로 실제 호출자를 갖는다** —
> 열린 항목 6 이 여기서 닫힌다.

## 0. 먼저 끝난 것 — AI 타입 (2026-11-02)

전술은 **이미 저장되고 투입 경로까지 흐르고 있었다**. 등록 문서의 `Tactic` →
`FriendlyTeammateMatchCallbacks` 의 팀원 상세 응답 → 클라이언트 `botsTactic[aid]` →
`profileTactic[profileId]` → `BotFollowerPlayer.CombatTactic`. **바꿀 길만 막혀 있었다.** 연 것:

| 허용 목록의 집 하나 | `FriendlyTeammateService.TacticOptions` 를 `internal` 로 승격(§3-4 의 허용 범위) |

| 화면 | 용병과 같은 한 줄: `장비 편집 | AI 타입`(`TryShowStmProfileControlRow`) |

테스트 511 → 513(전술 갱신 5개 추가, 거부 열거가 줄며 3개 감소). **인게임 미확인.**

## 1. 사용자가 정한 것 (2026-11-02)

| 질문 | 답 | 그래서 |
|---|---|---|
| 꾸러미에 보일 "프리셋" | **저장된 장비 빌드** | EFT 의 장비 프리셋. 팀원 프로필의 빌드와 플레이어의 빌드를 **나눠서** 보여 준다 |
| 물건 출처 | **전부 새로 구매** | 플레이어 스태시를 건드리지 않는다. 복제 위험이 가장 작고 되돌리기가 쉽다 |
| 팀원이 입고 있던 헌 장비 | **그 팀원 스태시로** | 장비 편집기가 이미 쓰는 길이다. 프로필 사이를 오가지 않는다 |

이 셋 덕분에 **프로필 사이를 넘는 것은 돈뿐이다.** 물건은 상인에게서 새로 생겨 팀원 프로필로 바로 들어가고,
헌 장비는 그 팀원 안에서만 움직인다. 설계 §6-5 가 걱정한 "아이템이 두 프로필에 동시에 존재하는 창"이 열리지 않는다.

## 2. 불변식 (새 코드 전에 읽어라)

인계 문서 §3 의 1~10 이 그대로 적용된다. 이 계획에서 특히 걸리는 것:

1. **살아 있는 객체(`member.Pmc`)는 복제 뒤에 만진다.** 구매한 물건을 팀원 프로필에 넣는 것도 같다.
2. **의심스러우면 쓰지 않는다.** 가격을 못 매기거나 상인이 거절하면 **아무것도 쓰지 않고** 멈춘다.
3. **"확인" 은 디스크에서 다시 읽는 것이다.** 저장 뒤 재독 대조는 장비 편집과 같은 수준으로 한다.
4. **돈은 플레이어 프로필에서만 나간다.** 팀원 프로필의 돈은 건드리지 않는다(그 프로필의 재산이다).
5. **저널을 쓴다.** 호출 순서 계약은 WORKLOG 에 적힌 그대로:
   `Prepare` → `BeginSourceWrite`(플레이어 돈) → `RecordDestinationItemIds`(살 물건의 id) →
   `BeginDestinationWrite`(팀원 프로필) → `MarkCommitted` → `Verify`.
   **이 계획이 저널의 첫 사용자다** — 기동 복구와 막힌 팀원 출구 UI 도 여기서 처음 실물로 확인된다.

## 4. 하지 않는 것 (지금)

- **플레이어 스태시에서 꺼내 쓰기.** 사용자가 "전부 새로 구매" 를 골랐다. 나중에 열면 그때 물건이
  두 프로필에 걸치므로 저널의 전체 경로가 처음으로 필요해진다.
- **보험·수리.** 여전히 거부다(`ProfileMemberOperationPolicy`).
- **이름·의상·숙련.** 그 프로필의 것이다. 사용자가 요청하지도 않았다.

## 5. 가장 위험한 자리

1. **돈을 뺀 뒤 물건을 넣기 전에 죽는 것.** 저널의 존재 이유다. 기동 복구가 실제로 도는 것을 **이 계획에서
   처음** 본다 — 관문에서 서버를 일부러 죽여 확인한다.
2. **상인 가격이 플레이어의 거래 등급·평판에 따라 다른 것.** 미리 보여 준 가격과 실제 청구가 어긋나면
   사용자는 속았다고 느낀다. 가격은 **구매 직전에 다시 매기고**, 달라졌으면 거절하고 다시 보여 준다
   (PIT 의 키트 흐름이 이미 `TeammateHireQuoteExpired` 로 같은 일을 한다 - 문구를 빌린다).
3. **빌드에 들어 있는 아이템이 상인에게 없는 경우**(퀘스트 보상 전용 등). 부분 구매로 어중간하게
   입히지 않는다 — 전체 거절이 기본이고, 무엇이 없어서인지 말한다.

## 6. Task 5 — 인게임 관문 (사람이 하는 절차)

Task 1~4 는 **코드로만** 끝났다. 아래는 돈과 아이템이 실제로 움직이는 것을 처음 확인하는 절차다.
순서를 지켜라 — 2번을 건너뛰면 무엇이 틀어졌는지 뒤에서 알 수 없다.

### 0. 준비 (빠뜨리면 되돌릴 수 없다)
1. 게임과 서버를 **모두 닫는다**.
2. `E:\Spt\SPT_Runtime\user\profiles\` 전체를 `backup/2026-11-0X-before-kit/` 로 복사한다.
   프로필 JSON 이 유일한 증거이자 유일한 복구 수단이다.
3. 서버를 켠다. 기동 로그에서 세 가지를 본다:
   - `PitFireTeam loaded`
   - `어휘가 어긋났다` 가 **없다**(장비 뿌리 칸·필수 무기 슬롯 두 검사)
   - `끝나지 않은 전송` 보고가 **없다**

### 1. 목록 (Task 1·4) — **2026-11-02 끝났다**
팀원 상세 화면에 버튼이 **둘**이다: `내 장비 꾸러미`, `팀원 장비 꾸러미`. 둘 다 게임의 기본 장비
프리셋 화면을 열고, 실리는 빌드만 갈라진다(자체 목록 창은 없다 - 걷어냈다).

확인된 것: 두 버튼이 열린다 / 팀원 빌드가 그려진다 / 닫은 뒤 플레이어 자신의 프리셋이 원래대로다.
로그 증거는 `[STM] 기본 화면에 팀원 빌드 N개를 실었다` 와 `[STM] 기본 화면의 빌드 목록을 플레이어의
것으로 되돌렸다` 가 **짝으로** 찍히는 것이다. 되돌리기가 빠진 짝이 있으면 그 자리에서 멈춰라 —
플레이어 자신의 프리셋 화면에 남의 빌드가 남는다.

빌드가 하나도 없으면 그 프로필로 로그인해 장비 프리셋을 먼저 저장한다.

### 2. 값 (Task 2) — **사기 전에 적어 둔다**
빌드를 하나 고르고 창의 네 줄을 **그대로 적는다**: 값, 가진 돈, 살 물건 수, 바뀌는 칸.
그리고 구매를 **누르지 말고** 창을 닫은 뒤, 프로필 JSON 에서 다음을 적는다:
- 플레이어의 루블 합(스태시 안, 잠긴 컨테이너 밖)
- 팀원의 장비 트리 아이템 id 집합
- 팀원의 스태시 아이템 id 집합

### 3. 구매 (Task 3) — **2026-11-02 통과**
다시 열어 같은 빌드를 고르고 구매 → 확인창 → 산다. 토스트의 금액이 2번에 적은 값과 같은가.

값은 **구매 직전에 다시 매긴다**. 실제로 같은 빌드가 4,578,702 → 4,578,428 로 흔들렸고 청구는
다시 매긴 값으로 갔다. 그래서 확인 창을 오래 열어 두지 말고 뜬 김에 누르는 쪽이 낫다.

### 4. 대조 (이것이 관문의 본체다)
서버를 닫고(저장을 확실히 내린 뒤) 프로필 JSON 을 다시 읽어 네 가지를 본다:
1. 플레이어의 루블 합이 **정확히 그 금액만큼** 줄었다. 다른 아이템 id 는 하나도 사라지지 않았다.
2. 팀원의 장비 트리에 **새 id** 가 생겼고, 그 id 가 플레이어 쪽에는 **없다**(복제 아님).
3. 2번에 적어 둔 팀원의 헌 장비 id 가 **그 팀원 스태시 트리 안**에 있다(사라지지 않았다).
4. 서버 로그에 `꾸러미 구매 완료` 한 줄과, `확인` 실패 줄이 **없다**.

### 5. 저널 (열린 항목 6 의 실물 확인)
여기까지 통과했으면 저널이 처음으로 한 바퀴 돈 것이다. 다음 기동 로그에 **끝나지 않은 전송 보고가
없어야** 한다(있으면 `Verify` 가 닫지 못했다는 뜻이다).

끊긴 경우를 일부러 보고 싶으면: 구매를 누른 **직후** 서버를 강제 종료하고 다시 켠다. 돈만 나간
상태면 기동 로그가 `끝나지 않은 전송을 자동으로 정할 수 없어…` 로 보고하고 그 팀원의 편집이 막힌다 —
상세 화면에 막힘 안내와 `이 기록 닫기` 가 뜨는지 본다. **이 실험은 백업을 뜬 뒤에만 한다.**

### 6. 실패하면
두 프로필의 장비·스태시·돈을 직접 확인하고, 되돌릴 수 없으면 0번의 백업으로 프로필을 되돌린다.
무엇이 어긋났는지(위 1~4 중 어느 줄인지)를 WORKLOG 에 적는다 - 그것이 다음 수정의 출발점이다.
