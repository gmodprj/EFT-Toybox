# 스태시 교환창에서 가방 안의 것을 끌면 아무 일도 안 일어난다 (2026-11-13)

**증상(사용자 제보).** 스태시 교환창 안에서

1. 내 스태시 → **박스/가방을 열고** → 복수 선택 → 팀원 스태시로 옮김 → **반영 안 됨**
2. 같은 것을 **내 스태시 쪽**으로 옮김 → **반영 안 됨**
3. 내 스태시로 옮긴 뒤 다시 팀원 쪽으로 옮김 → **반영 안 됨**

## 1. 서버 로그가 갈라 주었다 — **요청 자체가 가지 않았다**

| 시각(UTC) | 라우트 |
| --- | --- |
| 03:54:05 | `/stm/members/stash-transfer` → `스태시 전송 완료: 플레이어 → 팀원 … 고른 1개` |
| 03:54:19 · 03:54:46 · 03:56:01 · 03:56:06 · 03:56:48 · 03:58:28 | **`/stm/members/stash-pair` 뿐** |

전송이 성공한 것은 **바닥에 놓인 것 하나를 건넨 03:54:05 한 번**이고, 제보한 시도들에는
`stash-transfer` 가 **하나도 없다**. 게임 로그에도 STM 경고·오류가 0건이다.
서버가 거절한 것이 아니라 **클라이언트가 그 드롭을 전송으로 보지 않았다.**

## 2. 왜 — 정책이고, 코드가 그렇게 적고 있었다

드롭을 가로채는 관문은 `StmTransferHandlesDrop` 이고, 끌어온 것이 그 스태시의 것인지는
`StmTransferSideOwns` 가 본다. 그 함수는 **서버가 준 `side.Items` 목록**과 id 를 맞춰 보는데,
그 목록은 **스태시 바닥에 놓인 것**뿐이다. 함수 머리에 그렇게 적혀 있다:

> 그 스태시의 **바닥에 놓인 것**인가. 가방 안의 것을 따로 건네는 길은 열지 않는다(B1 정책).

창의 안내문도 같은 말을 한다 — *"스태시 바닥에 놓인 것만 건넬 수 있고, 가방을 건네면 안에 든
것은 따라갑니다."*

**그래서 세 경우가 모두 설명된다.**

| 제보 | 무슨 일이 일어났나 |
| --- | --- |
| ① 가방 안의 것 → 반대쪽 | 관문이 거른다 → EFT 의 원래 처리가 돈다 → 두 격자는 **서로 다른 컨트롤러**라 옮겨지지 않는다 |
| ② 가방 안의 것 → 같은 쪽 | 관문이 거른다(같은 쪽은 원래 우리 일이 아니다) → EFT 가 **복제 프로필 안에서** 옮긴다 → 서버로 가지 않으니 다음 새로 고침에 사라진다 |
| ③ ② 뒤에 다시 반대쪽 | ②가 저장되지 않았으니 그 아이템은 여전히 바닥에 없다 → ①과 같다 |

**이 창의 두 격자는 서버가 준 목록으로 세운 복제 프로필이다**(`TryBuildStmTransferGrid`).
거기서 일어난 이동은 어디에도 저장되지 않는다.

## 3. 고친 것 — 조용한 것을 말하게 했다

정책 자체는 그대로 두고, **전송으로 보지 않는 드롭이 우리 창 안에서 일어나면 이유를 적고 막는다**
(`StmTransferBlocksDrop`). 막는 이유는 ②가 더 나쁘기 때문이다 — 원래 코드가 돌면 화면에서는
**옮겨진 것처럼 보이다가** 다음 새로 고침에 사라진다. 조용히 틀린 그림을 보여 주는 쪽이
아무것도 안 움직이는 쪽보다 나쁘다.

| 어떤 드롭 | 이제 상태줄에 뜨는 말 |
| --- | --- |
| 가방·상자 안의 것 | `가방·상자 안의 것은 따로 건널 수 없습니다 — 가방째 건네면 안에 든 것이 함께 갑니다.` |
| 바닥에 있는 것을 같은 쪽에 | `같은 쪽 안에서 옮기는 것은 이 창이 저장하지 않습니다 — 반대쪽으로 끌어야 건네집니다.` |

우리 창 **밖**의 드롭(편집기·플레이어 자신의 스태시 화면)은 한 줄도 바뀌지 않는다 —
관문이 먼저 그것을 가린다.

- `dotnet build client/pitFireTeam.csproj -c Release -p:BuildProjectReferences=false` → **경고 0 · 오류 0**
- **설치하지 못했다** — 제보 시점에 게임이 돌고 있어 DLL 이 잠겼다.

## 4. 열었다 (2026-11-13) — 그리고 **아래 §5 의 비용 추정은 틀렸다**

사용자가 "열어다오" 로 정했다. 열고 보니 **§5 에서 넷이라고 센 것 중 둘은 이미 돼 있었다.**

| §5 가 센 것 | 실제 |
| --- | --- |
| ① 서버가 자손까지 내려주기 | **이미 내려준다.** `stash-pair` 응답의 `tree` 가 **스태시 트리 전체**다(`Items` 는 바닥 요약일 뿐이고, 창은 `tree` 로 격자를 세운다 — 그래서 가방이 열렸던 것이다) |
| ② 부모에서 떼어 내기 | **이미 된다.** 서버는 지울 때 **id 로** 지우고(`RemoveAll`), **고른 것만** 받는 쪽 스태시 바닥에 자리를 잡아 준다. 안에 든 것은 부모를 따라간다 |
| ③ 총량 보존 정의 | **바꿀 것이 없었다.** 보존의 단위는 `Closure(고른 것 + 자손)` 이고, 가방 안의 것을 고르면 그 하나와 그 자손이 단위가 된다. 디스크 대조도 id 기준이다 |
| ④ 저널 | **바꿀 것이 없었다.** 항목은 옮긴 id 목록이라 깊이와 무관하다 |

**정말로 막고 있던 것은 두 자리뿐이었다.**

1. **서버 판정** — `StashTransferPolicy` 가 `부모 == 스태시 루트 && 칸 == hideout` 을 요구했다.
   이제 **조상을 따라 올라가 스태시 루트에 닿으면** 받는다(`IsInStash`). 입고 있는 것·총에 달린
   것은 스태시 트리에 매달려 있지 않아 **여전히 거절**이고, 스태시 루트 자체도 거절이다.
2. **창의 관문** — `StmTransferSideOwns` 가 바닥 요약(`Items`)에서 id 를 찾았다. 이제 **트리(`Tree`)**
   에서 찾는다. 창이 그려 주는 것과 건널 수 있는 것이 **같아졌다** — 이 어긋남이 이번 제보의 뿌리였다.

**새로 막은 것 하나** — 가방과 **그 안의 것**을 함께 고르면 거절한다. 둘 다 받으면 고른 것마다
받는 쪽 바닥에 자리를 잡으므로 안의 것이 가방에서 **빠져나온다**. 고른 사람이 뜻한 바인지 알 수
없어 조용히 한쪽을 버리지 않는다.

| | |
| --- | --- |
| 시험 | `StashTransferPolicyTests` 에 4개를 더해 **687개 전부 통과**(가방 안의 것, 가방 안의 가방, 스태시 밖, 겹쳐 고르기) |
| 빌드 | 클라이언트·서버 둘 다 **경고 0 · 오류 0** |
| 설치 | 클라이언트 `SptTeamManager.dll`(md5 `d9edb8a6…`) · 서버 `SptTeamManager.Server.dll`(md5 `d894219c…`) — **설치본과 빌드 결과의 md5 가 같다.** 옛 것은 `backup/stm-dll-2026-11-13/` 에 |
| 서버 | **끄지 않았다.** 돌고 있어 DLL 이 잠겨 옛 것을 `.locked-20261113-131840` 로 치우고 새것을 넣었다 — **새 서버 코드는 다음 서버 기동부터** 돈다. 치운 파일은 서버를 끈 뒤 지운다 |
| 안내문 | "스태시 바닥에 놓인 것만 건넬 수 있고" → "가방·상자 안의 것도 건널 수 있고" |

**아직 인게임에서 보지 않았다.** 서버를 다시 켠 뒤, 가방 안의 것을 골라 반대쪽으로 끌어
① 실제로 건너가는지 ② 보내는 쪽 가방에서 사라지는지 ③ 받는 쪽 바닥에 놓이는지를 본다.

## 5. (지난 추정) 가방 안의 것을 건널 수 있게 하려면

이번 수정은 "왜 안 되는지 말해 준다" 까지다. **되게 하는 것은 B1 정책을 바꾸는 일**이라
따로 정해야 한다. 열 경우 손댈 자리는 이렇다.

1. **서버** — `stash-pair` 가 바닥 것만 내려준다. 가방 속 자손까지 내려주고,
   `stash-transfer` 가 **부모에서 떼어 내는** 경로를 가져야 한다(지금은 바닥에서 집어 옮긴다).
2. **총량 보존** — 지금 보존 검사는 바닥 목록 기준이다. 자손을 옮기면 **보내는 쪽 가방의 내용이
   줄어드는 것**이 정상이 되므로, 무엇이 줄어도 되는지 다시 정의해야 한다.
3. **저널** — 전송 저널의 항목 모양(무엇을 어디서 떼어 어디에 놓았는지)이 한 겹 깊어진다.
4. **화면** — 지금 격자는 바닥만 그린다. 가방을 열어 들어가는 길
   (ProfilePorter 세부 보기 창이 이미 가진 그 길)을 이 창에도 내야 한다.

**싸게 가는 길도 있다** — 가방을 **통째로** 건넨 뒤 받는 쪽에서 꺼내는 것이다. 지금도 되고,
안내문이 이미 그렇게 말한다. 옮길 것이 가방 하나면 이쪽이 더 빠르다.

## 6. 옮긴 것이 **게임 화면에서는 안 사라진다** (2026-11-13) — 복제가 아니라 묵은 화면이었다

사용자 제보: 가방 안의 것을 건넸더니 **받는 쪽에는 놓였는데 보내는 쪽 가방에 그대로 남아 있다.**
교환창을 나와 캐릭터 화면에서 다시 열어도 남아 있어 "이동이 아니라 복사" 로 보였다.

### 디스크로 먼저 갈랐다 — **복제가 아니다**

옮긴 id 넷을 `user/profiles/` **전체**에서 셌다.

| id | 보내는 쪽(Nomad) | 받는 쪽(Sarge) | 그 밖 |
| --- | --- | --- | --- |
| `6af46035…334b` · `…3321` · `…368c` · `…33dd` | **0** | **1** | 없음 |

게임이 그 뒤로 프로필을 두 번 저장했는데도(14:24 · 14:27) 그대로 0이다. **디스크에서는 제대로
이동했고 총량도 지켜졌다.** 서버 로그의 `스태시 전송 완료` 와 보존 검사도 그 말과 맞는다.

### 그러면 화면의 그것은 무엇인가

**돌고 있는 게임이 들고 있는 옛 사본**이다. 이 전송은 서버 쪽 프로필을 고치는데,
교환창은 그 변경을 **게임에 알려 주지 않았다** — 코드에 `ProfileUpdatesHandler` 호출이 **0건**이었다.
같은 코드의 보험 기능은 그 길로 게임에 밀어 넣고 있다.

**보이는 것만의 문제가 아니다.** 그 유령을 게임에서 쓰면 서버에 없는 물건을 가리키는 조작이
올라간다 — 거기서부터는 오류가 나거나, 최악의 경우 진짜 복제가 된다.

> 이것은 **오늘 연 "가방 안의 것" 때문이 아니다.** 교환 기능이 처음부터 그랬고, 바닥에 놓인 것을
> 옮길 때도 마찬가지였다. 오늘 길이 넓어지면서 눈에 띈 것뿐이다.

### 고친 것 — 전송 직후 게임에 밀어 넣는다

보험이 쓰는 그 길을 그대로 쓴다(`ProfileUpdatesHandler.UpdateProfile` + `StashChangesResponse`).

| 방향 | 게임에 보내는 것 |
| --- | --- |
| 플레이어 → 팀원 (잃는 쪽) | `del` = 옮긴 id 전부(안에 든 것까지) |
| 팀원 → 플레이어 (받는 쪽) | `new` = 옮겨진 뒤의 모양 그대로(부모·칸·좌표까지) |

그 재료는 서버가 응답에 싣는다 — `movedIds` 와 `playerItems` 를 더했다.

**실패해도 숨기지 않는다.** 전송은 이미 끝나 있으므로 예외를 던지지 않고, 대신 상태줄에
`다만 게임 화면에는 다시 켜야 반영됩니다 — 그 전에는 만지지 마세요.` 를 덧붙인다. 조용히
넘어가면 사용자가 유령을 만진다.

덤으로, 격자를 다시 세울 때 **열어 둔 가방·상자 창을 먼저 닫는다**(`CloseLoadoutEditorChildWindows`).
그 창들은 지울 트리의 아이템을 들고 있어 닫지 않으면 옛 내용을 그대로 보여 준다.

| | |
| --- | --- |
| 시험 | 687개 전부 통과(이 변경은 Unity·EFT 타입이라 단위 시험 자리가 없다) |
| 빌드 | 클라이언트·서버 둘 다 경고 0 · 오류 0 |
| 설치 | 클라이언트 md5 `f47abfc2…` · 서버 md5 `a27d5f5a…` — 설치본과 빌드 결과가 같다 |
| 끄지 않았다 | 게임·서버가 둘 다 돌고 있어 **잠긴 DLL 을 `.locked-<시각>` 으로 치우고** 넣었다. **둘 다 다시 켜야 적용된다** |

### 인게임에서 닫혔다 (2026-11-13)

게임·서버를 다시 켠 뒤 사용자가 봤다 — **가방 안의 것을 건네니 바로 사라졌고, 반대 방향도 정상**이다.

로그 셋이 같은 말을 한다.

| 어디 | 무엇 |
| --- | --- |
| 게임 로그 | `돌고 있는 게임에 반영했다 — 더한 것 0, 지운 것 9` (플레이어 → 팀원) · `더한 것 3, 지운 것 0` (팀원 → 플레이어). STM 경고·오류 **0건** |
| 서버 로그 | `스태시 전송 완료: 플레이어 → 팀원 … 고른 9개` · `팀원 → 플레이어 … 고른 3개` |
| 디스크 | 양쪽을 **왕복한** 아이템(`6af46035…342b`)이 `user/profiles/` 전체에서 **플레이어 프로필에만 1개**. 복제도 유실도 없다 |

밀어 넣기가 **양방향 모두** 걸렸다는 것이 이것으로 확인됐다. 치워 둔 `.locked-*` 둘도 지웠다.

### 그래도 남는 것

- **단위 시험이 없는 자리다.** `ProfileUpdatesHandler` 는 Unity·EFT 타입이라 `SptTeamManager.Tests`
  가 링크할 수 없다. 관문은 위의 인게임 확인과 로그 세 줄뿐이니, 이 길을 고칠 때는 같은 방법으로
  다시 본다.
- 밀어 넣기가 실패하면 상태줄에 `다시 켜야 반영됩니다 — 그 전에는 만지지 마세요` 가 뜨고
  로그에 `돌고 있는 게임에 알리지 못했다` 와 이유가 남는다. **그 경우는 아직 본 적이 없다.**
