# 저장이 디스크 확인에서 되돌려진다 — 탄 20발이 어디서 났나 (2026-11-13)

**증상(사용자 제보).** Talon 의 장비 편집에서 저장(또는 `꾸러미로 저장`)을 누르면
`저장한 내용을 디스크에서 다시 읽어 확인하지 못해 원래대로 되돌렸습니다` 가 **누를 때마다** 떴다.

**먼저 분명히 할 것 — 아무것도 쓰이지 않았다.** 안전장치가 걸려 원래대로 되돌렸고 프로필은 그대로다.

## 1. 서버 로그가 수치까지 적고 있었다

```text
[STM] 인벤토리 저장: 프로필 '6aeedffb…' 두 트리 205 → 207개(두 트리 밖 16개는 그대로)
[STM] 인벤토리 저장 확인 실패(프로필 '6aeedffb…'): 디스크의 상태가 보존 판정을 통과하지 못했다:
      '6937dbee0dd9015d14925d3d' 의 수가 680 에서 700 로 늘어 저장하지 않습니다.
```

그 tpl 은 **12/70 AP-20 Slug 사보트 변형**(12게이지 탄, 스택 상한 360)이다. **20발이 늘었다.**

## 2. 왜 제출 단계는 통과하고 디스크 단계만 걸렸나

둘은 **같은 판정**(`ProfileInventoryApplyPolicy.Validate`)을 쓴다. 그런데 **보는 것이 달랐다.**

| 단계 | 본 것 |
| --- | --- |
| 제출 | **제출본**(`after`) |
| 디스크 | 제출본 **+ `PreservedItemIds`** — 편집기가 보여 주지 않아 제출본에 없던 아이템을 원래대로 되붙인 것 |

그래서 **제출본에서는 줄어든 것처럼 보이던 수가 보존으로 되돌아오면서 총량이 늘 수 있다.**
제출 단계는 그것을 보지 못하고 통과시키고, 디스크 단계가 뒤늦게 잡아 **쓰고 나서 되돌린다.**

> 편집기가 모든 아이템을 싣지는 못한다(EFT 가 읽지 못하는 것이 있다). 그런 것을 제출본에 없다고
> 지우면 안 되므로 **보존**하는데(2026-11-03 사고), 그 보존이 보존 판정의 눈을 가린 것이다.

## 3. 고친 것 — 두 검사가 같은 것을 보게 맞췄다

**쓰기 직전에 최종 상태(제출본 + 보존)로 한 번 더 본다.** 걸리면 **아무것도 쓰지 않고** 거절한다 —
늦게 잡아 되돌리는 것보다 낫고, 사용자에게 가는 말도 "되돌렸다" 가 아니라 그 사유 그대로다.

디스크 검사는 **그대로 둔다**(이중 안전장치).

## 4. 아직 모르는 것 — **20발은 어디서 났나**

이번 수정은 **늦게 잡히던 것을 일찍 잡게** 한 것이지, 20발이 생긴 원인을 밝힌 것이 아니다.
그래서 보존 판정이 걸릴 때 **tpl 별 내역**을 함께 적게 했다:

```text
[STM] 보존 내역(프로필 '…') — 수가 달라진 tpl 2종, 보존된 아이템 n개:
    6937dbee…: 680 → 700 (+20), 그중 보존된 것 20
```

`그중 보존된 것` 이 핵심이다 — 늘어난 몫이 **보존된 아이템에서 온 것인지**가 한 줄로 갈린다.
다음에 같은 일이 나면 그 줄만 보면 된다.

## 5. 상태

- 시험 **695개 전부 통과**. 빌드 경고 0 · 오류 0. 설치했다(서버 md5 는 PR 참고).
  서버가 돌고 있어 치우고 넣었다 — **다시 켜야 산다.**
- **재현 절차를 모른다.** 사용자가 그 편집에서 무엇을 했는지(탄창 채우기·더미 나누기 등)가
  아직 없다. 다음 재현에서 위 내역 줄과 함께 받으면 좁혀진다.

## 6. 그 탄이 무엇이고, 680발이 어디에 있나 (2026-11-13)

`6937dbee0dd9015d14925d3d` = **12/70 AP-20 Slug 사보트(Sabot) 변형** — 12게이지, 스택 상한 360.
**바닐라 아이템이 아니다**(`SPT_Data/.../items.json` 에 없다). 모드가 더한 것이고,
정의를 들고 있는 것은 `kazusa-SimpleItemModifier` 의 스냅샷이다(이름 끝의 `(101.68/61)` 은
피해/관통을 붙여 주는 쪽의 표기다). 그 밖에 `Amonya`·`BlueheadsAIOTrader`·`EquipmentIsEternal` 이
같은 id 를 참조한다.

Talon 프로필에서 그 탄은 **스택 4개 / 합계 680발**이고, 자리는 이렇다.

| 몇 발 | 어디 |
| --- | --- |
| 300 | 전술 조끼 칸 1 |
| 360 | 전술 조끼 칸 3 |
| 10 | **탄창 안**(`slotId = cartridges`) |
| 10 | **탄창 안**(`slotId = cartridges`) |

680 은 거절 당시의 "전" 값과 정확히 같다.

### 그래서 +20 은 **탄창 두 개를 10발씩 채운 것**으로 보인다

이미 탄창 둘이 **각각 10발**을 물고 있고, 늘어난 양이 **정확히 20**이다. 탄창 하나가 10발이니
**10 × 2**가 맞아떨어진다. 조끼의 300·360 에서 꺼내 채웠다면 총량은 그대로여야 하는데 늘었으니,
**출처 더미가 줄지 않은 채 탄창만 채워진** 모양이다.

**다음 재현 후보(아직 해 보지 않았다)**: Talon 의 편집기에서 **VR80 탄창 두 개를 10발씩 채우고**
저장해 본다. 이번 기동부터는 쓰기 전에 거절되고, 로그의 `보존 내역` 줄이
`그중 보존된 것` 으로 **출처가 보존된 아이템이었는지**까지 말해 준다.
