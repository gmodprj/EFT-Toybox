# `apply-inventory` 는 격자 칸 겹침을 거절하지 않는다 — 실측 (2026-11-06)

관문 8(스태시 격자 자리 찾기)을 라우트로 돌려 보려다 나온 결과다. **결함 신고가 아니라 그물의
구멍을 수치로 못박는 기록**이다 — 코드가 그러기로 적어 놓은 것이기도 하다.

## 한 줄

`/stm/members/apply-inventory` 에 **같은 칸 좌표**를 보내면 서버가 받아들여 **디스크에 쓴다.**
로그는 정상 저장으로 찍히고 경고도 없다.

## 어떻게 쟀나

전제부터 지켰다(관문 목록 머리글의 0번).

| | |
| --- | --- |
| 프로필 백업 | `backup/2026-11-06-before-stm-gate8/` 7개, **md5 7개 전부 일치** |
| 설치본 md5 | 클라이언트 `355ADC71` · 서버 `D7001316` — 인계 문서 기록과 같다 |
| 상태 | **게임은 닫혀 있고 서버만 떠 있다**(`SPT.Server.exe` 만 보인다) |
| 대상 | Hawk `6ae70e1b28569fc69cf98f01`(aid `1559354`) — 로그인한 프로필이 아니다 |

`gear-stash` 로 트리를 읽고, 프로필의 두 트리(288개)를 그대로 제출본으로 만들었다. 거기서

## 결과

응답은 `{"err":0,"errmsg":null}` 였고 **디스크에서 둘 다 `(2,0)` 이었다.** 서버 로그도 평범한 저장이다:

```
[2026-11-06 10:26:52][STM] 인벤토리 저장: 프로필 '6ae70e1b…'(aid 1559354) 두 트리 288 → 288개
```

거절 문구도, 경고도 없다. **보존 검사는 통과한다** — id 가 사라지거나 끼어들지 않았고 수량도 그대로다.
겹침은 보존의 문제가 아니라 **좌표의 문제**이고, 거기를 보는 코드가 없다.

## 왜 그런가 — 설계가 그렇게 적어 놨다

`shared/ProfileInventoryApplyPolicy.cs:262`:

> 격자(가방·리그·주머니·스태시의 칸)가 먼저다. 여러 개를 담으므로 점유를 묻지 않고,
> **자리가 실제로 남아 있는지는 좌표의 문제라 여기서 셈하지 않는다(EFT 편집기가 센다).**

그 격자 분기는 **종류 필터**(`AllowedTemplateIds`)와 **제외 필터**(`ExcludedTemplateIds`)만 본다.
칸 점유는 일반 슬롯에서만 묻는다. 즉 **의도된 범위**이고 코드와 주석은 어긋나지 않는다.

## 그래서 무엇이 틀린 기록인가

인계 문서가 이 서버 검사를 **"라우트를 직접 부르는 호출자에 대한 그물"** 이라고 적었는데, 그 표현이
너무 넓다. 그물에는 **좌표 구멍이 있다.** 정확히는:

| 누가 | 칸 겹침을 막는 것 |
| --- | --- |
| 게임 화면(EFT 편집기) | **막는다** — 관문 E 화면 절반 9번에서 게임 자체 호환 툴팁이 먼저 막았다 |
| 라우트 직접 호출 | **막지 않는다** — 이 문서가 그것이다 |

## 관문 8 에 주는 답

관문 8 이 묻는 것("벗긴 것이 서로 겹치지 않는 좌표에 놓이는가")은 **서버에서 답할 수 없다.**
편집기 저장이 `apply-inventory`(최종 상태)로 바뀌면서 좌표를 클라이언트가 보내고, 서버의 자리 찾기
(`StmGearEditService.TryPlaceInContainer`)는 이제 **꾸러미 구매만** 쓴다(`StmGearEditService.cs:179`).
그래서 **관문 8 은 게임에서만 닫힌다.**

서버 자리 찾기가 실제로 도는 증거는 따로 있다 — 2026-11-06 의 꾸러미 구매가 31개를 사
**30개를 그 팀원 스태시로** 보내며 그 함수를 썼고 디스크 재독까지 통과했다.

## 되돌렸다

원래 좌표로 다시 제출해 되돌리고 백업과 대조했다 — **아이템 295개, 사라진 id 0 · 새 id 0 ·
값이 다른 아이템 0.** 프로필에 남은 변화가 없다.

## 열어 둔 질문 (고치지 않았다)

- **고칠 값이 있나.** 게임 화면이 막아 주므로 평소 경로에서는 안 난다. 다만 이 그물의 목적이
  "라우트 호출자" 라면 좌표도 보는 것이 일관적이다.
- 고친다면 **극성을 조심해야 한다.** 열린 항목 10 이 적어 둔 그 함정이다 — 모델하지 못하는 자리를
  "모름" 으로 거절하면 정상 저장이 막힌다. 겹침은 "틀렸다고 증명된 것" 이므로 그 극성과는 맞지만,
  셈을 하려면 접힘(`SizeReduceRight`)과 부착물(`ExtraSize*`)까지 EFT 와 똑같이 재야 한다.
- **그 셈을 두 번째로 구현하는 것 자체가 위험하다.** `StmGearEditService.cs:566` 이 그렇게 적어
  놨다: "격자 자리를 찾는 판정이 두 곳에 생기면 한쪽만 고쳐져 아이템이 겹쳐 놓인다." 이 문서를 쓰며
  감사용으로 그 셈을 손으로 만들어 봤는데 **접힘을 빼먹어 겹침 76건을 거짓으로 보고했다**(접힘을
  넣어도 24건이 남았다 — 부착물 크기까지는 못 맞췄다). 서버가 셈하려면 SPT 의
  `InventoryHelper.GetContainerMap`/`PlaceItemInContainer` 를 그대로 불러야 한다.
